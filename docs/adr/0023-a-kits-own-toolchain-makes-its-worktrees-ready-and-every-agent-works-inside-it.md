# A kit's own toolchain makes its worktrees ready and every agent works inside it

Deciders: the user, whose rulings in sluice's session of 2026-10-11 and 12 (37713ae2) set the split this record applies to crew; proposed by the toolchain workstream on 2026-10-12, and accepted only on the user's yes.
Amends: the `bolt-teams` design (2026-10-05), whose new worktrees run the kit's `crew-prepare`; `agents-work-inside-crews-devenv-shell` (2026-10-09), whose hook is the repository's and never the plugin's; record 0015, on how a carrying fix reaches the bolt, for point 6.
Sources: the user's words in session 37713ae2, quoted below; sluice's `phase-2-git-state` worktree, read 2026-10-12 (`.prototools`, `.moon/toolchains.yml`, `devenv.nix`, uncommitted) and its `docs/plans/phase-1-integrations.md` (sections 2, 3 and 7); sluice's record 0012; crew's `plan.py` `PLACE` (5142add), `.claude/hooks/devenv-shell`, `plugin/bin/crew-role`; the kit survey and the probes below.

## Context and problem statement

**How a worktree is made ready today.** When crew makes a bolt's, unit's or fix's worktree it runs `<kit>/.devenv/profile/bin/crew-prepare` from the kit's main checkout's devenv profile, since a new worktree has no devenv of its own. crew reaches into another repository's profile for a script named after crew. The user: "this is bad design".

**How an agent reaches its kit's tools today.** Only crew's and swancloud's checkouts put a session in their devenv shell, each through its own copy of a repository SessionStart hook (crew's written by hand, swancloud's generated by its `devenv.nix`). The fleet keeps direnv's hook off in Claude sessions and herdr panes (swancloud's `modules/home-shell.nix`), so in every other kit an agent runs the host's tools unless it wraps each command in `devenv shell --`, as switchboard's and breadboard's CLAUDE.md tell it to.

**Where sluice has gone.** The user: "We have a defined separation between Devy and V (the main set of system-level tools) and Proto tools (the application-level things)", and "I feel like we're giving things up by not using Proto's toolchain with Moon." sluice's working tree now has devenv carry the system tools (git, moon 2.6.1 and proto 0.63.1 from moonrepo's releases), `.prototools` pin the application toolchain (Rust), moon read that pin (`versionFromPrototools: true`), devenv's shell activate it, and `MOON_TOOLCHAIN_FORCE_GLOBALS` go, since forcing globals loses per-project pins, dependency installs and cache keys over tool versions. Its argument for one entry point: every launcher, "crew's role environment, worktrunk hooks, sluice's policy, CI", gets the same tools from one setup, because "what sluice tests with must be what the agent built with".

**What sluice asks of crew.** `SLUICE_AGENT` set to the agent's crew name (core.1 keeps crew's name out of sluice's code; the user agreed the name); a bolt's worktree brought level when sluice moves its branch, since moving a checked-out branch leaves that worktree's index and files behind; and, in the user's words, "we should try to move CREW outside of SLUICE's control to a design where we don't check out the bolt branch as a work tree".

switchboard is the one kit with a `crew-prepare`, and each of its suite scripts already runs the same `bun install --frozen-lockfile` before it starts.

**Probes, moon 2.6.1 in a scratch workspace with bun pinned to 1.2.23 in `.prototools`:**
- `moon setup` installed proto (0.62.2, moon's own default when none is pinned) and bun 1.2.23, and installed no dependencies.
- The first `moon exec` installed them, as the `InstallDependencies(javascript)` action ahead of the task, by `zsh -c "bun install"`. That found the host's bun 1.3.13 on the PATH the login shell set, not the pinned 1.2.23, because proto's directories were not on PATH: a dependency install uses the pinned tool only inside a shell that activates proto.
- `moon docker setup` installs dependencies only from a docker scaffold's manifest; moon 2.6.1 has no other command that installs them alone.
- With no toolchain configured, as crew has, moon 2.6.1 sets nothing up and runs the shell's `python3` through its `system` toolchain, with `MOON_TOOLCHAIN_FORCE_GLOBALS` set or not.
- crew's suite passes on moon 2.6.1 (`t-suite`, `t-merge-gate`, both tiers).
- crew's tests run on devenv's python 3.14.7, while every agent runs crew on the host's `python3`, 3.13.15 on mac-studio (`/run/current-system/sw/bin/python3`).
- The box enables nix-ld (swancloud's `modules/workspace-box/prebuilt.nix`), so a binary proto installs runs there.

## Decision drivers

- One setup per kit, entered the same way by every launcher: an agent's session, a person's terminal, worktrunk's hooks, sluice, CI.
- crew names no kit's script and reads no kit's profile; a kit is ready because its own toolchain says so.
- crew's tests run on what crew runs on.
- crew stays outside sluice's control: nothing crew holds should break when sluice moves a bolt's branch.

## Decision outcome

1. **The split, as sluice has it.** devenv owns the system tools: git, nix, moon and proto themselves, and whatever a host runs that the kit does not choose. proto, through moon, owns the application toolchain, with `.prototools` the one pin, read by moon with `versionFromPrototools: true`, and `.moon/toolchains.yml` pinning `proto.version` to devenv's proto so moon never fetches its own. devenv's shell activates the pinned toolchain on entry. `MOON_TOOLCHAIN_FORCE_GLOBALS` goes. A repository without devenv is sluice's fallback case, not crew's.

2. **A new worktree is made ready by the kit's own toolchain.** When crew makes a bolt's, unit's or fix's worktree, on the team's host, and the worktree holds both `devenv.nix` and `.moon/workspace.yml`, crew runs `devenv shell -- moon setup` in it: devenv builds the worktree's own shell, which the agent's session then enters warm, and moon installs what `.prototools` pins. Dependencies are installed as the kit's moon toolchain config says, by moon, before the first task that needs them, in the agent's shell, which activates proto; crew runs no install of its own, since moon has none to run outside a task. crew runs the step again when it finds the worktree already there, since `moon setup` is a check once the pins are installed; a setup that fails refuses crew's command in the kit's words (`read.1`). A kit without both files gets nothing from crew: no script, no fallback, its agents starting in the kit's shell (point 3) or on the host's tools. `crew-prepare` goes; switchboard moves its `bun install` into moon's JavaScript toolchain config (bun pinned in `.prototools`, `installArgs: ['--frozen-lockfile']`).

3. **Every session works inside its checkout's toolchain, through one hook in crew's plugin.** crew's plugin carries the SessionStart hook crew's repository carries now, its words made any kit's: at every start, a session whose project directory sits in a git checkout with `devenv.nix` at its root enters that checkout's devenv shell once and appends what the shell set to `CLAUDE_ENV_FILE`. It covers every session on a host that loads crew's plugin, crew's agents in every kit and the user's own sessions alike, because one entry for every launcher is the point; crew's and swancloud's repository copies go. What the shell is stays the checkout's, in its `devenv.nix`: the plugin only enters it. crew-role still starts `claude` bare: a herdr resume is a bare `claude --resume` that a wrapper would lose, and a wrapper would hold a pane's start for the evaluation.

4. **crew on moon, and its Python where crew runs.** crew's devenv carries moon 2.6.1 from moonrepo's release, as sluice's does (built on this branch). crew pins no application tool: every agent runs crew's command and hooks outside crew's shell, on the host's `python3`, and `gather.py` is piped to hosts as they are, so crew's interpreter is a system tool by the split's own definition. devenv keeps Python and pytest, pinned to the minor the fleet runs, 3.13, so the tests run on what crew runs on. crew carries no `.prototools` and no `.moon/toolchains.yml`, and devenv adds proto, when crew first pins an application tool. `code.1` names moon's source and Python's pin.

5. **sluice's two near requests.** Every agent crew starts carries `SLUICE_AGENT`, the same as `CREW_AGENT`: crew-role sets it and the session-start hook gives it back on a resume (built on this branch; `teams.6`). Until point 6 is built, in a kit that merges through sluice (`.config/crew.toml`'s `sluice = true`, `teams.5`), crew brings the bolt's worktree level when sluice moves its branch: when it reads that a unit's merge stage has ended, it runs `git read-tree -m -u <old> HEAD` there, the two-way merge `git checkout` does, which keeps untracked files and refuses rather than overwrite a change; a refusal is said to the conductor with its paths. crew does it rather than the conductor's memory (`roles.3`).

6. **No worktree holds a bolt's branch.** `crew bolt give` makes `bolt/<bolt>` as a branch and `<kit>/bolts/<bolt>` as a checkout of it detached at its head, and crew moves that checkout to the branch's head (`git switch --detach`, which refuses over a local change) whenever it reads that the branch moved. Units and fixes branch from `bolt/<bolt>` as now. The landing rebases a landing branch onto main, `land/<bolt>` cut in the bolt's checkout from the bolt's head, or the carrying fix's own branch, through the kit's hooks, so `plan.8`'s rebase runs on a branch sluice does not protect. A carrying fix is no longer crew's move of `bolt/<bolt>`: it becomes what lands. The bolt's branch goes with the bolt.

   What this breaks, each answered in the change that builds it:
   - `plan.8`, `teams.5` and record 0015: the bolt's branch never moves to a carrying fix, and `crew bolt land`'s check that main holds the bolt reads the landing branch's head.
   - `plan.9` and the tidy: crew knows a bolt's checkout by "directly in `<kit>/bolts/`, detached, its folder a bolt a plan holds" instead of "on `bolt/<folder>`", a weaker mark under `read.4`, since a detached checkout names no branch.
   - A kit that merges with `wt merge bolt/<bolt>`: worktrunk runs post-merge in the target's worktree, and with none in the kit's main checkout, so crew's bolt verification would run main's `bolt-verify.sh` and main's devenv on the bolt's revision. crew runs the bolt's post-merge hooks itself from the bolt's checkout once it has moved, as it does after a carry, and a kit's post-merge skips a bolt target. In a kit on sluice, sluice's verdict on the tree it lands is the verification.
   - The conductor's, ops's and main-ops's briefs, which say `bolt/<bolt>` in `<kit>/bolts/<bolt>`; ops deploys from a checkout crew moves under it, so ops proves the head crew last moved it to, and says which.
   - With no worktree holding the branch, git no longer stops a hand checkout of it elsewhere; sluice's hook stops a move, not a checkout.

### Consequences

- crew names no kit script and reads no kit's profile; a kit with neither devenv nor moon gets nothing, and moves to them when it chooses.
- A new worktree costs a devenv evaluation in crew's command, about 20 s cold, which the agent's session reuses; `moon setup` is quick once a shared `PROTO_HOME` holds the pins.
- Every Claude session on a crew host in a devenv checkout waits for its shell at its start, the user's own included, and gets the kit's tools from its first command without `devenv shell --`.
- Dependency installs need the network in the agent's session, as `crew-prepare`'s did in crew's command.
- crew's tests stop running on a Python no host runs crew on.

## Considered options

For making a worktree ready:
- Keep `crew-prepare`: the user's "bad design".
- worktrunk's `pre-start` hook, run by crew in the worktree (`wt hook pre-start --yes`, as sluice does in its own places): the kit's own words, but each host must approve each kit's hooks, and `--yes` is what crew's rules keep agents from.
- A command named in the kit's `.config/crew.toml`: crew still runs a kit script, under another name.
- devenv installs the dependencies on shell entry: the application's install in the system layer.

For putting agents in the shell:
- Each kit carries the repository hook: a copy per kit, which drift (crew's is handwritten, swancloud's generated), and none yet in the box's kits.
- crew-role wraps `claude` in `devenv shell --`: lost on a herdr resume, and it holds the pane's start.
- The fleet's home configuration installs the hook in each Claude account's settings: the same behaviour, kept outside crew's suite and in one settings file per account.

For crew's Python:
- proto's Python through moon's Python toolchain, with uv and a lock for pytest: a pinned interpreter that no host runs crew on, a virtual environment per worktree, and a version in moon's hash that `devenv.lock`, an input of every task, already gives.

For the bolt's worktree:
- Keep the branch checked out and level it after each move (point 5) for good: crew stays inside sluice's control, and a refused levelling leaves a checkout ops deploys from out of step with its branch.
- A crew-owned branch the checkout sits on, fast-forwarded by crew when the bolt moves: a second branch per bolt to keep in step.
