# Plan rules

The rules for the plan, proposals, stages, worktrees and every write to a flywheel's branch. `core.md` binds here too; the how-to is README's The plan, Proposals and State sections. Why a drop keeps unmerged work is record 0003; why a change is archived at merge is 0006.

## Rules

- **[plan.1]** Every write runs `recfix --check` on each `.rec` file it changed and crew's own rules (a unit's bolt in the same repo, `After` within one bolt, no cycle) before committing, and its change function re-checks every precondition against the tip it is applied to, since it replays.
- **[plan.2]** Every commit on a flywheel's branch has a subject ending ` (<agent>)` and a `Crew-Entry:` trailer naming its run-record entry, and carries the host's uncarried run record; a carry-only commit names no entry.
- **[plan.3]** A proposal holds only the plan commands a proposal may hold, parsed by the command line's own grammar and applied by the same functions as a direct run; it is checked by applying each `Do` in order to a copy at the tip, one refusal refuses the whole, and approval applies every `Do` the user read and kept in order at the tip and closes the proposal in one commit, or changes nothing; a unit new to the bolt the user cleared on the card is left out with every command that only concerns it, a kept command that names it refuses the whole, and the approval records what was cleared.
- **[plan.4]** A proposal is numbered once, never removed, its `Do` lines never changed; it closes only as approved or dropped, and one that touches a held bolt is approved only after that bolt's conductor has agreed.
- **[plan.5]** Work a held bolt needs before it can be proven or land is placed in that bolt ahead of its first unmerged unit, marked `--unblocks`; a proposal that marks a unit so and places it elsewhere is refused.
- **[plan.6]** A unit that has merged or landed is never amended, split, moved or dropped; a unit marked `Amended` reads amended, then construct, and its code, verify and merge are refused until its construct has committed again, with no approval asked.
- **[plan.7]** A unit's name is its OpenSpec change's name, refused when the kit's main already holds a change by that name, open or archived.
- **[plan.8]** A bolt is cut from GitHub's main fetched at that moment, meets main only at its landing, which rebases it onto main in its own worktree through the kit's hooks, and a landing is refused while the kit's main on its host is behind GitHub's; when the landing's rebase conflicts nothing lands, the team's fix carries the bolt's commits onto main with the conflict resolved, crew makes that the bolt's head, and no agent moves a bolt's branch by hand.
- **[plan.9]** crew removes only worktrees it made, directly under `<kit>/bolts/` or `<kit>/places/` on a `bolt/`, `unit/`, `chore/` or `fix/` branch, once their work is finished, and removes each through the kit's own worktree tool so the kit's remove hooks run and what the kit stood up for that worktree goes with it, a hook that fails keeping the worktree, named; a worktree with modified or non-ignored untracked files, a locked one, the main checkout and a hand-made one are never removed, and nothing is removed while a plan the kit's work goes in cannot be read.
- **[plan.10]** A branch holding commits whose patch the bolt or main lacks, judged by `git cherry`, is kept and named when its worktree goes; a branch holding nothing beyond its target is removed.
- **[plan.11]** A chore is planned maintenance built inside a bolt by code, verify and merge, with no construct and no review, and changes nothing a spec says must be true; it is a Unit record of the plan marked `Kind: chore`, its stage read from its trailer on main or the bolt and its place, and `After` holds for it as for any unit (`plan.13`), its code being what a dependent builds on.
- **[plan.12]** A command reads each kit once and fetches the state branch once, however many steps it has, and stage facts read without `openspec` agree with openspec's on the same worktree.
- **[plan.13]** `After` names a unit whose code the dependent builds on, a contour that exists only once that unit's code exists, or a unit a forecast conflict between the two put it after; the dependent's construct starts only once each has finished construct, never waiting on a merge, and the dependent merges only after each has merged into the bolt; `After` is never set by hand for shared files or for product order, which is the file's.
- **[plan.14]** A landing records the sha main holds afterwards and deploys nothing; a deploy is one act by the kit's deployer under the environment's policy, to one environment, over every landing since that environment's last deployed state, recorded in the run record as it runs with its contents, the kit's after-deploy checks and their outcomes, and every after-deploy step of the landings it carries with its doer and state; a `manual` environment's deploy is a rail row with a card held to approve, a step that is the user's is a rail row with a card until the user marks it done, and promotion to the next environment is a deploy to it.
- **[plan.15]** An amendment the user approves runs the unit's construct again by that approval's own act, on the team's host with the amendment's words, ending the unit's agent where it stands when it is past construct, and withdraws the unit's stale card through its owner's notice; a conductor brought back finds an amended unit with no construct running and starts it; nothing waits on anyone remembering.
- **[plan.16]** A bolt lands by one procedure, main-level ops's: the user's approval of the bolt's landing card, which its conductor posts once ops's proof is clean at the bolt's head and passes on with `crew tell`, or the user's words in ops's pane, is the word to land and to push; ops fetches the kit's main, merges the bolt through the kit's hooks, pushes main without force, runs `crew bolt land`, and for crew brings every host's checkout up to main; nothing else is a word to land, and a landing deploys nothing.

## Details

**[plan.1]** Rules out: a write that skips `recfix`; a precondition checked once before the replay loop. Source: `plan.py` 263–328, 390–406, 488–500. `land` checks every file a commit holds, the carried `runs/<host>/` files among them; a signal's or capture's markdown is checked by its frontmatter, read as one record.

**[plan.2]** Rules out: a commit with no trailer; two acts in one commit with one entry. Source: `flywheel-state` spec "A commit names its run-record entry"; `plan.py` 449–535.

**[plan.3]** Rules out: a proposal as prose; `bolt give` in a `Do`; a half-applied approval; a cleared unit's `--after` left standing. Not ruled out: the approval of a subset the user chose on the card, unit by unit (ADR 0018). Not built: `_open.md`. Source: `plan-proposals` spec; design "Each plan command becomes three parts"; `plan.py` 1122–1165, 1797–1845.

**[plan.4]** Rules out: editing `proposals.rec`; reusing a number; approving over a missing agreement. Source: `plan-proposals` spec; `plan.py` 1498–1510, 1710–1774.

**[plan.5]** Rules out: an `--unblocks` unit in the queue. Source: fix 902336e; `plan-proposals` spec "Work a bolt in flight needs to land goes into that bolt".

**[plan.6]** Rules out: `unit split` on a unit in code; construct on a merged unit; an amended unit held for the user's approval. Source: `bolt-plan` spec; unit-amendments design; ADR 0014 (D5); units-build-at-once-and-are-reviewed-in-batches; `plan.py` `place_stage`, `run_check`, `unmark`; `tests/py/test_stages.py`, `tests/py/test_stage_rules.py`, `tests/py/test_amend.py`.

**[plan.7]** Rules out: a unit named after an archived change. Source: `plan.py` 808–817.

**[plan.8]** Rules out: a bolt cut from a stale clone; a landing onto a main behind GitHub; `git reset` or `git branch -f` on a bolt's branch by an agent; a fix that replays main's commits over the bolt; the carrying fix judged by `git cherry`, which compares patches and so never sees a resolved commit as the bolt's. Not ruled out: main-level ops moving a bolt's branch onto a carrying fix that the conductor and ops both read as faithful, on the user's yes given on a card, when crew's own judgement is the defect the bolt fixes (crw-2, 2026-10-11: main's crew paired the bolt's two identical empty approval commits out of order; the user, on a card asking for their hand: "Ask the designer why the fuck we're doing this. The whole point is that you do the work not me"); the user gives a yes, never a git command. A fix carries the bolt when it sits on a commit main holds, holds as many commits beyond their common base as the bolt does, and in order each is the same commit replayed, by message and author, its patch equal or changed; `git range-diff` is printed as the reading and judges nothing, since its creation factor fails to pair a commit whose context main rewrote (crw-1's fix agent, 2026-10-10, signal 2026-10-10-crw-1-conductor-69720a11/01). Source: fix 04daa5d; `plan.py` 846–879, 976–981; ADR 0015 as restated 2026-10-09 (signal 2026-10-09-crw-1-conductor-47d11d45/01; crw-2's construct's reading). Built by `plan.py` `carry_judgment`, which judges by each commit's message and author and counts the changed patches by patch id, and `carry`, which moves the bolt and runs its post-merge hooks; proved by `tests/py/test_carry.py`, `tests/py/test_fix.py`, `tests/contract/test_git.py`, `tests/contract/test_wt.py` and `tests/t-journey-land.sh`.

**[plan.9]** A chore's place is `<kit>/places/chore-<name>` on `chore/<name>` (`plan.11`). Rules out: tidying `main`; removing a dirty worktree; removing anything when a plan is unreadable; `git worktree remove` on a kit whose `.config/wt.toml` has a `[pre-remove]` or `[post-remove]` hook (swb-3-ops, 2026-10-09: switchboard-kit's hook tears down the worktree's ministack and its Frontegg Development objects, and three fix worktrees' stood after crew removed them, signal 2026-10-09-swb-3-ops-401c8aa3/01 on wldn/main). Read the same day: `wt remove` runs pre-remove hooks with the worktree's files still there, post-remove after, and deletes the branch only when merged, with `--no-delete-branch` to leave it to `plan.10`'s judgment; crew's and swancloud's kits have merge hooks only. Source: worktrees-go-with-their-work; `plan.py` `tidy`, `tidy_over`, `kept_why`, `wt_refused`; `tests/py/test_tidy.py`, `tests/contract/test_wt.py`.

**[plan.10]** Rules out: `git branch -D` on a branch with unmerged patches; judging by ancestry across a rebase. Source: ADR 0003. The code deletes outright and judges by ancestry until `a-drop-keeps-unmerged-work` lands: `_open.md`.

**[plan.11]** Rules out: a construct stage for a chore; a chore that writes a spec; a chore in a review batch; a chore's stage kept by hand; a third record set, whose records recutils keeps together after their descriptor, so the file's order could not be the build order of units and chores together; a dependent of a chore waiting on the chore's merge, which `plan.13` rules out for any work: a dependent of a chore starts once the chore's code has delivered, from the chore's head, as its start's `Took` records (the user, 2026-10-12: a chore should not differ from any other unit). Source: ADR 0001 as amended 2026-10-12, on the user's ruling: a Unit record marked `Kind: chore`, in build order, since recutils keeps a record set's records together after their descriptor; `chores-beside-units-and-fixes`. Built by `plan.py` `is_chore`, `Plan.work`, the unit ops with the kind from the command (`kind_refusal`), `Stages` (`chore_stage`, `after_met`, `built_on`), `took_from` and `TAKE`, `chore_check` (`chore_refusal`, `untrailed`, `CHORE_LOG`), `rebase_dependents`, `Owed` and `delivered`, `slot_stage`, `tidy_over`, and `gather.py` `chores`, `chore_place` and `own_head`; proved by `tests/py/test_chores.py`, `tests/contract/test_gather.py`, `tests/contract/test_recfix.py` and `tests/t-journey-chores.sh`.

**[plan.12]** Rules out: a second `gather` in one command; a stage fact that disagrees with openspec. The direct reading knows openspec's own spec-driven schema; a change of any other schema, of a spec-driven its kit or user redefines, or with metadata crew does not read, is read through `openspec`. Source: `openspec/explorations/command-cost/reading.md`; ADR 0008; a-command-reads-the-kits-once; `plan.py` `Reading`, `fetch`, `land`, `survey`; `gather.py` `tasks_of`, `planned`; `tests/t-stage-facts.sh`; `tests/contract/test_gather.py`; `tests/t-journey-units.sh` and `tests/t-journey-slots.sh`, whose status and unit run each fetch and gather once, and `tests/t-journey-board.sh`, whose rail tab's refresh does.

**[plan.13]** Rules out: `After` set by hand between units that only touch the same files; a dependent's construct before its dependency's change is committed; a dependent's construct held for its dependency's merge; a dependent merged before its dependency; `After` as sequencing; a dependent forecast to conflict with its dependency on the dependency's own work its place took, once the dependency's rebase or settle rewrote it: the dependent is forecast against it from the head its place took (`teams.12`); a dependent's rebase at its dependency's merge that replays the dependency's commits as its place took them, and so conflicts on the dependency's own files once its settle rewrote them: the rebase leaves out each merged After unit's head the dependent took and still holds, from an upstream with no ref whose parents are the bolt and those heads, since `git rebase --onto` the bolt from the taken head alone replays the bolt's commits made between the two places and conflicts where the bolt changed them again (both read 2026-10-12 in `tests/contract/test_git.py`); a dependent whose rebase conflicts told to rebase onto the bolt alone, which replays the work crew's rebase left out: it is told the command that makes that upstream again, from the bolt as it then stands and the heads its place holds (`rebase_words`, the heads on the forecast's `Took`), since the upstream has no ref and nothing keeps it; crew writes no ref for it, so there is nothing to remove after and nothing for `read.4` or `plan.9` to allow. What these leave, an After unit's work taken by hand after the place took its head and the other After units' work in one forecast: `_open.md`. Not ruled out: the `After` a conductor sets on a forecast conflict between two unmerged units (`teams.12`). A chore holds to this rule as a unit does, its code being what a dependent builds on (`plan.11`). Source: ADR 0011; ADR 0014 (D1 to D3); `bolt-plan` spec "The file's order and dependencies are the plan"; units-build-at-once-and-are-reviewed-in-batches; `plan.py` `Stages`, `run_check`, `take`, `rebase_dependents`, `rebase_leaves_out`, `ONTO`, `rebase_words`, `amended_afters`, `took_heads`, `forecasts_due`; `tests/py/test_stage_rules.py`, `tests/py/test_forecast.py`, `tests/contract/test_git.py`, `tests/t-journey-slots.sh`, `tests/t-journey-merge.sh`.

**[plan.14]** A landing's record is `crew bolt land`'s `bolt.land` entry, naming the kit (`Repo`) and the commit its main holds afterwards (`Head`), read on the team's host as the landing's guard reads how far main is from GitHub's (built 2026-10-12). What the deploys and operations look like is read from those entries alone (`ops.environments`, `state.4`): the board's Operation lane shows each environment's deploys and the operations waiting, and the page's deploys view each environment's deploys as a timeline, a deploy carrying the landings on its kit between the one that left main at its from and the one that left it at its to, and naming the commit instead when no landing in the record left main there (`read.1`; `the-page-shows-the-deploys`, record 0010, built 2026-10-12). Built 2026-10-11 as `crew ops` (`plugin/lib/ops.py`, `tests/py/test_ops.py`, `tests/t-journey-ops.sh`), a deploy being one kind of operation: a `manual` environment's deploy is offered by the kit's deployer as a row under *operations*, `deploy/<env>/<sha>`, whose card is main-level ops's (`briefs.11`); holding it is the user's word, recorded with `crew ops approve` and read back with `crew ops word` until that deploy's end; the deploy's acts and every other operation's states are `ops.*` entries on `env/<env>` in the run record of the host where the partition's main level runs, and an operation the user is to take that waits is a row of its own, `op/<env>/<n>`. A kit with no deployer has its main deployed by main-level ops only on the user's word for that deploy, a departure from "main-ops running a deploy" the user ruled on 2026-10-11 (`a-bolt-lands-by-one-procedure`). Rules out: a deploy implied by `crew bolt land`; a deploy whose contents are remembered rather than read; main-ops running a deploy; a `manual` deploy approved anywhere but its card; an after-deploy list of what a check could assert; a step for the user that lives only in a pane. Source: ADR 0012 as amended 2026-10-08 and 2026-10-09; `main-level` spec; swancloud ADR 0018, 0019; the versions statement on channels. Not built: `_open.md`.

**[plan.15]** Rules out: an amendment refused because the unit's coder was working, left for the conductor to force (crw-2, 2026-10-11, proposal 124); an amended unit idle at construct while its review card stays out (madswan, 2026-10-10: proposal 6 approved at 00:58:53Z, construct never run again, the conductor restarted at 01:40 and the pending run lost; signal 2026-10-10-madswan-design-3d7ef799/01); a re-run that lives only in a conductor's memory. Source: ADR 0014 D5 (construct run again with the user's words); `conductor.md` 77; `plan.py` `amended`, `op_unit_amend`, `run_check`, `amended_units`; `an-amendment-runs-construct-again-itself`; `tests/py/test_amend.py`, `tests/t-journey-plan.sh`, `tests/py/test_teams.py`, `tests/t-journey-teams.sh`.

**[plan.16]** Rules out: a landing on the planner's word or on a rail row appearing; main pushed on a second word after the landing, which left crew's main 103 commits ahead of GitHub's on 2026-10-11 while the box ran GitHub's; a deploy as a step of a landing; a brief that repeats the steps rather than pointing to main-ops's. Why: the briefs, the rules and the specs gave three procedures, and agents argued over which held (the user, 2026-10-11). Source: `roles.2`, `state.3`, `plan.8`, `plan.14`, `briefs.11`; `main-ops.md` *Landing a bolt*; `a-bolt-lands-by-one-procedure`.
