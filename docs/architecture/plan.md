# Plan rules

The rules for the plan, proposals, stages, worktrees and every write to a flywheel's branch. `core.md` binds here too; the how-to is README's The plan, Proposals and State sections. Why a drop keeps unmerged work is record 0003; why a change is archived at merge is 0006.

## Rules

- **[plan.1]** Every write runs `recfix --check` on each `.rec` file it changed and crew's own rules (a unit's bolt in the same repo, `After` within one bolt, no cycle) before committing, and its change function re-checks every precondition against the tip it is applied to, since it replays.
- **[plan.2]** Every commit on a flywheel's branch has a subject ending ` (<agent>)` and a `Crew-Entry:` trailer naming its run-record entry, and carries the host's uncarried run record; a carry-only commit names no entry.
- **[plan.3]** A proposal holds only the plan commands a proposal may hold, parsed by the command line's own grammar and applied by the same functions as a direct run; it is checked by applying each `Do` in order to a copy at the tip, one refusal refuses the whole, and approval applies every `Do` the user read and kept in order at the tip and closes the proposal in one commit, or changes nothing; a unit new to the bolt the user cleared on the card is left out with every command that only concerns it, a kept command that names it refuses the whole, and the approval records what was cleared.
- **[plan.4]** A proposal is numbered once, never removed, its `Do` lines never changed; it closes only as approved or dropped, and one that touches a held bolt is approved only after that bolt's conductor has agreed.
- **[plan.5]** Work a held bolt needs before it can be proven or land is placed in that bolt ahead of its first unmerged unit, marked `--unblocks`; a proposal that marks a unit so and places it elsewhere is refused.
- **[plan.6]** A unit that has merged or landed is never amended, split, moved or dropped; a unit marked `Amended` reads amended, then construct, and its code, verify and merge are refused until its construct has committed again, with no approval asked.
- **[plan.7]** A unit's name is its OpenSpec change's name, refused when the kit's main already holds a change by that name, open or archived.
- **[plan.8]** A bolt is cut from the kit's main as it stands at that moment, meets main at its landing, and before it only when a forecast on its conductor's waits says it would conflict with what main has landed, when the team takes main in as below (`teams.21`); its landing is main-level ops's submission of the bolt's branch to main through sluice, landed as a merge commit carrying sluice's verdict once main with the bolt passes main's checks, formed by sluice on GitHub's main and pushed with a lease, so no landing is refused for the host's local main lagging GitHub's; when the bolt and main conflict nothing lands, the conflict is the bolt's, and the team takes main into the bolt by a submission to the bolt and submits again; no unit starts on a bolt whose landing is queued; no agent, and nothing of crew's, moves a bolt's branch or main by git.
- **[plan.9]** crew removes only worktrees it made, directly under `<kit>/places/` on a `unit/`, `chore/` or `fix/` branch, and a bolt's worktree made before record 0026 under `<kit>/bolts/`, which crew's tidy detaches at the bolt's tip while the bolt lasts, once their work is finished, and removes each through the kit's own worktree tool so the kit's remove hooks run and what the kit stood up for that worktree goes with it, a hook that fails keeping the worktree, named; a worktree with modified or non-ignored untracked files, a locked one, the main checkout, a detached anchor crew never moves, and a hand-made one are never removed, and nothing is removed while a plan the kit's work goes in cannot be read.
- **[plan.10]** A branch holding commits whose patch the bolt or main lacks, judged by `git cherry`, is kept and named when its worktree goes; a branch holding nothing beyond its target is removed.
- **[plan.11]** A chore is planned maintenance built inside a bolt by code, verify and merge, with no construct and no review, and changes nothing a spec says must be true; it is a Unit record of the plan marked `Kind: chore`, its stage read from its trailer on main or the bolt and its place, and `After` holds for it as for any unit (`plan.13`), its code being what a dependent builds on.
- **[plan.12]** A command reads each kit once and fetches the state branch once, however many steps it has, and stage facts read without `openspec` agree with openspec's on the same worktree.
- **[plan.13]** `After` names a unit whose code the dependent builds on, a contour that exists only once that unit's code exists, or a unit a forecast conflict between the two put it after, an order crew writes once for a pair and only when the later unit's settle delivers a commit that takes the other's work, never when the settle finds nothing to change, the forecast's words reaching the unit either way; one crew wrote whose settle delivered no commit is lifted by crew itself, one the user lifted stays lifted, and no proposal or card asks the user to undo crew's own forecast; the dependent's construct starts only once each has finished construct, never waiting on a merge, and the dependent merges only after each has merged into the bolt; `After` is never set by hand for shared files or for product order, which is the file's.
- **[plan.14]** A landing records the sha main holds afterwards and deploys nothing; a deploy is one act by the kit's deployer under the environment's policy, to one environment, over every landing since that environment's last deployed state, recorded in the run record as it runs with its contents, the kit's after-deploy checks and their outcomes, and every after-deploy step of the landings it carries with its doer and state; a `manual` environment's deploy is a rail row with a card held to approve, a step that is the user's, or an agent's held for the user's word, is a rail row with a card until the user marks it done or skipped or says when the agent does it, and promotion to the next environment is a deploy to it.
- **[plan.15]** An amendment the user approves runs the unit's construct again by that approval's own act, on the team's host with the amendment's words, ending the unit's agent where it stands when it is past construct, and withdraws the unit's stale card through its owner's notice; a conductor brought back finds an amended unit with no construct running and starts it; nothing waits on anyone remembering; and the approval's command answers once its write is made and the construct's start is handed to the team's host, which reads the start and tells the conductor what started or why nothing did, so no plan write waits on an agent's session coming up or its prompt landing, and whoever needs the construct waits with `crew unit wait`.
- **[plan.16]** A bolt lands by one procedure, main-level ops's: the user's approval of the bolt's landing card, which crew raises in its conductor's name once the bolt's verification is green at its head (record 0025) and the conductor passes on with `crew tell`, or the user's words in ops's pane, is the word to land and to push; ops submits the bolt's branch to main through sluice, which lands it on GitHub's main as a merge commit by a leased push or refuses it with the conflict named for the team, and runs `crew bolt land`, which asks sluice to delete the bolt's branch and closes the landing card naming the fleet's timer, since sluice pushed main and the timer moves every host's anchor, nothing pushed or levelled by ops; a bolt no team holds, built outside a team, whose every unit's change and chore its kit's main already holds, lands by `crew bolt land` alone on the user's word, nothing merged or pushed, recording the commit main holds as any landing does; nothing else is a word to land, and a landing deploys nothing.
- **[plan.17]** crew makes a worktree ready only through its kit's declaration in `.config/sluice.toml`, by the declared toolchain and then the declared runner's setup, run in the worktree on the team's host with sluice's cleaned environment, whenever it makes the worktree or finds it made; a kit that declares nothing has nothing run; crew enforces no floor on the version of a kit's runner and refuses a moon only when it cannot read its version, sluice's moon runner keeping its own floor, moon 2.6, at its run; crew names no kit script, reads no kit's profile, and assumes neither moon nor devenv.
- **[plan.18]** No worktree of crew's checks out a kit's main or a bolt branch: a kit's main folder is a detached anchor at `origin/main` that the fleet's timer alone moves, a bolt's worktree from before record 0026 is detached at the bolt's tip, every read of main now in crew is `origin/main` after a fetch, crew never moves an anchor or levels a checkout, and a landing is submitted from a short-lived worktree on the bolt's branch that sluice warns of and lands anyway.
- **[plan.19]** A bolt's branch lives on GitHub: made at `crew bolt give` by sluice's `branch create` from `origin/main` and ended at `crew bolt land` by sluice's `branch delete`, under a ruleset whose one writer is sluice's app, so crew pushes nothing to a kit's remote and cuts every place from `origin/bolt/<bolt>`; a give is refused when the kit's policy names no remote for its bolts or the host's sluice lacks the command, naming the version; and crew's plugin reaches a host live, from a detached worktree the timer moves, or released, pinned by swancloud from crew's release tags, never from a checkout on the branch.

## Details

**[plan.1]** Rules out: a write that skips `recfix`; a precondition checked once before the replay loop. Source: `plan.py` 263–328, 390–406, 488–500. `land` checks every file a commit holds, the carried `runs/<host>/` files among them; a signal's or capture's markdown is checked by its frontmatter, read as one record.

**[plan.2]** Rules out: a commit with no trailer; two acts in one commit with one entry. Source: `flywheel-state` spec "A commit names its run-record entry"; `plan.py` 449–535.

**[plan.3]** Rules out: a proposal as prose; `bolt give` in a `Do`; a half-applied approval; a cleared unit's `--after` left standing. Not ruled out: the approval of a subset the user chose on the card, unit by unit (ADR 0018). Not built: `_open.md`. Source: `plan-proposals` spec; design "Each plan command becomes three parts"; `plan.py` 1122–1165, 1797–1845.

**[plan.4]** Rules out: editing `proposals.rec`; reusing a number; approving over a missing agreement. Source: `plan-proposals` spec; `plan.py` 1498–1510, 1710–1774.

**[plan.5]** Rules out: an `--unblocks` unit in the queue. Source: fix 902336e; `plan-proposals` spec "Work a bolt in flight needs to land goes into that bolt".

**[plan.6]** Rules out: `unit split` on a unit in code; construct on a merged unit; an amended unit held for the user's approval. Source: `bolt-plan` spec; unit-amendments design; ADR 0014 (D5); units-build-at-once-and-are-reviewed-in-batches; `plan.py` `place_stage`, `run_check`, `unmark`; `tests/py/test_stages.py`, `tests/py/test_stage_rules.py`, `tests/py/test_amend.py`.

**[plan.7]** Rules out: a unit named after an archived change. Source: `plan.py` 808–817.
