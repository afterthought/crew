# Test rules

The rules for how crew is tested and gated. `core.md` binds here too; the how-to is CLAUDE.md's Tests section. Why the suite gates every merge and runs as moon tasks is record 0008; why it is in three tiers, record 0022.

## Rules

- **[tests.1]** End-to-end tests run only through `tests/run`, which enters crew's devenv shell itself when started outside it, refuses to start unless stub herdr, ssh, hostname, claude, plannotator and pendingyou shadow the real ones, gives each test its own scratch directory and home per simulated host and bare remotes, and exits non-zero on any failure; only "0 failed" passes.
- **[tests.2]** Every `tests/t-*.sh` opens with a comment saying what it proves and, as its first command, sources `lib.sh` through `${TESTS:?…}`, so it stops when run outside the runner; a test reaches a real service only under `CREW_TEST_LIVE=1`.
- **[tests.3]** A test edits a fixture in place with `rewrite`, never `sed -i`, and runs crew only as a simulated host.
- **[tests.4]** A fix to `plugin/` lands with a test that reproduces the case it fixes, at the lowest tier that can hold it: a decision's in the logic tier, a local tool's behaviour in a contract test; and when the fix depends on how a tool crew stubs behaves, the stub is changed to behave the same way.
- **[tests.5]** Every merge into a bolt and onto main is gated by sluice on the checks the kit's policy requires of that branch, and sluice's verdict on the bolt's last landing is the bolt's verification, read by crew from the landing commit; crew's suite runs as moon tasks in parallel, one for the logic tier, one for the contract tier, one for crew's mod's own cases and one per end-to-end test file, each tagged `check-full`, which crew's policy requires, and replayed on an identical tree.
- **[tests.6]** Every rule a brief carries is pinned by a phrase `tests/t-briefs.sh` checks.
- **[tests.7]** No Claude session in a crew checkout is entered into crew's devenv shell at its start, by crew, its plugin or a hook the checkout carries; an agent runs crew's tools through the shell per command, `devenv shell -- <command>`, as CLAUDE.md says, or through `tests/suite` and `tests/run`, which enter it themselves, as sluice does through the toolchain `.config/sluice.toml` declares; and the host carries no application tool on an agent's path, so a command run outside the shell fails for want of the tool rather than running the host's copy.
- **[tests.8]** A test waits on a condition, never on the clock: no fixed sleep decides an outcome, every wait it makes has a limit that holds on a host under heavy load, and a verification that reddens only because the host was busy is a defect of the test, fixed before the next bolt lands.
- **[tests.9]** The suite's parallelism on a host is bounded by that host's cores, shared across every team's verification and merge gate running on it, so two suites side by side never load a host past its cores; a run that would exceed the bound waits its turn rather than thrashing the host.
- **[tests.10]** An end-to-end test's moon task takes as inputs crew's command core and each other path its outcome depends on, named on its `# Reads:` line, and a merge onto main replays no test.
- **[tests.11]** crew's tests are in three tiers: logic tests call crew's decisions in-process on plain facts and start no process; contract tests run git, recutils, worktrunk and moon for real in a scratch directory, each pinning a behaviour crew's code assumes; end-to-end tests run the `crew` command on the stubs and prove its wiring; nothing in the suite calls a real agent, posts a real card or reaches another host.
- **[tests.12]** A coder's edit runs the logic tier; every merge gate runs all three tiers; a decision is checked in the logic tier, and an end-to-end test checks no more than one case per command beyond its wiring.
