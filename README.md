# crew

Bolt teams of Claude agents, run in herdr, and each partition's main level above them.

- The teams and partitions are data in `~/.config/crew/teams.json` (version 2), written by the machine's configuration (in swancloud, `lib/crew-teams.nix`); each partition carries its batch setting, `review: {every, hours}`, and crew refuses one without it. Hosts, sessions, each session's partition and the repos of its space come from `~/.config/swancloud/herdr-hosts.json`.
- `plugin/` is the same for every team: the roles (`roles/`, each an agent definition naming its model and effort), the `crew` and `crew-role` commands (`bin/`), the builder that turns the teams file into briefs and settings (`lib/crew.py`), the plan (`lib/plan.py`, with `lib/gather.py`, which reads a host's kits, and `lib/transcript.py`, which checks a signal's excerpt against its agent's transcript), `crew sites` (`lib/sites.py`), and the skills. It installs as a Claude Code plugin; this repository is its marketplace.

## Teams

```
crew list
crew status   [team]
crew up|down|rebuild|close <team>
crew restart|resume <team> [conductor|ops]
crew clear    <team> conductor|ops
crew unit run <unit> construct|code|verify|settle|merge ["<words>"]
crew unit free <unit> [--team <team>]
crew chore run <chore> code|verify|merge ["<words>"]
crew chore free <chore> [--team <team>]
crew fix      <team> <name> "<what is wrong>"
crew fix      <team> <name> --merge
crew fix      <team> <name> --drop [--force]
crew fix      <team> <name> --wait [--timeout <ms>] [--stuck <ms>]
crew needs    "<what you tried and what you need>"
```

A team builds one **bolt** at a time: a body of work on the branch `bolt/<bolt>`, made from the kit's main with no worktree, which moves only through sluice and then lands on main. Its standing roles are the **conductor** and **ops**. A bolt is built from **units**, each one OpenSpec change on `unit/<unit>` in `<kit>/places/<unit>`, taken stage by stage: construct writes the change, code builds it as soon as it is committed, with no review between, verify checks it once, code run once more fixes what its report marks fix, and merge archives its change, then submits it to the bolt with `wt submit bolt/<bolt> --no-remove`: sluice tests the bolt with it merged on the checks the kit's policy requires of its bolt branches, `[branches."bolt/*"]` in the `.config/sluice.toml` on its main, and lands it as a merge commit only when they pass. `crew bolt give` makes the bolt's branch alone, and refuses a kit whose policy names no such checks, naming the file. Each stage is a fresh agent at that stage's effort, in one of the team's `units` slots; a team taken down with `crew down` starts no stage until it is brought up. crew sends the agent the stage's prompt only once it is ready for input, and the stage begins only once the agent's own transcript shows Claude received it; a prompt it does not show within a short time is cleared from the agent's input with one Ctrl+C and sent once more. When the second is not taken either, or the agent was never ready, nothing is left typed in its pane: the stage never started, its start is recorded refused with no end owed, its slot and idle agent stay, and `crew unit run` or `crew fix` fails saying so and how to run it again. crew sends nothing more, and presses nothing, while the agent is working, or when it cannot read whether the prompt was taken, and says what it could not read. Construct can be run again with the user's words at any stage before the unit merges: run on a unit that is planned, in code or in verify, it marks the unit amended in the plan, code, verify and merge are refused until the change written again is committed, and the write that records that construct's end clears the mark; the unit then goes on from its tasks, with nothing to approve, and its revised change is in the partition's next batch. A merged unit is not amended: a defect in it is a fix, and a new need a new unit.

Every worktree crew makes for work, the place of a unit, a chore or a fix, is made ready by its kit's own toolchain, as the kit declares it in sluice's words: the `[tests]` table of `.config/sluice.toml` in the worktree, with `toolchain`, a command whose output is shell code that sets the kit's tools up (`["devenv", "print-dev-env"]`), and `runner`, `"moon"` or `"command"` (with `command`). crew runs the toolchain in the worktree on the team's host, with only `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG`, `TERM`, `PROTO_HOME`, `MOON_HOME` and `LC_*` of the host's environment and stdin closed, keeps what it prints in the worktree's git directory, and then, for the moon runner, runs `moon --version`, refusing only a moon whose version it cannot read, since crew enforces no moon floor (sluice's moon runner refuses a moon below 2.6 at its own run, so a kit on sluice runs 2.6 or later), and `moon setup`, each with that output sourced by the `bash` on the PATH. It does this before any agent starts there, and again when it finds the worktree already made, so a command run again after a step failed sets it up; a step that fails refuses a unit's or a chore's stage in the tool's words, the worktree made, while a fix's agent starts all the same, told the step that failed, since a fix is how a bolt whose toolchain is broken is repaired. A kit that declares nothing has nothing run: crew assumes neither moon nor devenv, and runs no script a kit names for crew. crew reads only those keys of the file, through `plugin/lib/kit.py`; sluice reads the same table to run a kit's checks, and the file becomes `flywheel.toml` once flywheel uses sluice's SDK.

A bolt's units are built side by side, as slots allow, their changes written in waves: every unit with no `After` is constructed at once, and a unit that comes after others as soon as their changes are committed, never waiting on their merge. A dependent's new place takes the head of each of its unmerged `After` units as it stands; when one of them merges, crew rebases the dependent's place onto the bolt at the team's next read or the conductor's next wait, only while its agent is not working and its place is clean, the bolt's commits dropping out, and the merged unit's work as the place took it with them, since the bolt holds that work as it merged; a rebase that conflicts is undone and reaches the dependent as a forecast does, with the command that rebases it from the same upstream. A dependent merges only after each unit it comes after has merged. Construct ends the proposal with `## Touches` and a fenced block of paths or globs; code is refused without it, a unit whose Touches overlap those of an unmerged unit ahead of it in the bolt's merge order starts code with the overlap and that unit's change in its prompt, and verify's prompt names each path the unit changed against its bolt and did not declare. Overlap holds nothing. On every `crew unit wait`, crew dry-runs with `git merge-tree`, writing no ref, the merge of each unmerged unit with the bolt and with each unmerged unit ahead of it in the bolt's merge order, `After` first and the plan's order only between units neither comes after, so a unit's dependents are never ahead of it, a dependent's with a unit it comes after from the head of that unit its place took, so the unit's own work, rewritten since by its rebase or settle, is no conflict of the dependent's; a forecast conflict reaches only the later unit, once for a pair of heads (`forecast` in the run record): told to its stage's agent once that is not working, carried in its next stage's prompt when none of it runs (a forecast against the bolt only until a newer one against the bolt is made for the unit), or as a **settle** stage, a fresh coder in its slot, when it has delivered its verify and waits to merge; a settle ends at a commit on its branch, or its agent saying nothing needs to change, and the unit then merges with no verify again. A forecast between two unmerged units puts the later after the earlier. An `After` unit constructed again reaches each of its dependents the same way, and holds none of them. The later unit resolves every conflict, keeping both changes' intents; the earlier is never changed for it. A **fix** is built the same way on `fix/<bolt>/<name>` from the bolt, in `<kit>/places/fix-<bolt>--<name>`, with no change and no plan record; a fix name already in use on the bolt is refused. A fix merges into the bolt like a unit, by a submission; nothing of crew's moves a bolt's branch. A landing that conflicts with main is the bolt's: a fix merges main into its place, resolving the conflict, and is submitted to the bolt. Every worktree crew made goes, with its branch, once its work is over: a bolt's branch, which crew marks as its own in the kit's git config when it makes it (`branch.bolt/<bolt>.crew`), once no plan has it (landed or dropped) and no worktree is on it, and the worktree a bolt given before bolts were branches still has likewise, a unit's once it has merged into its bolt or landed or no plan has it, and a fix's once it has merged into its bolt, its conductor dropped it, or no plan has its bolt; when a removed branch held commits of its own, crew says the commit it was at. `crew fix <team> <name> --drop` ends a fix that is not wanted, one in flight or one whose branch and place stand with no slot: its slot is freed and its agent ended, a working one only with `--force`, its branch is marked `branch.<fix>.crew dropped` in the kit's git config, and the team's read that follows removes its place and branch as a dropped unit's, keeping the branch, named and unmarked, when `git cherry` finds commits of its own beyond the bolt. A fix that has merged into its bolt is not dropped: a new fix undoes it. Each time crew reads a team (`crew status <team>`, `crew unit run`, `crew fix`) it frees every slot whose unit or fix has merged or been dropped, or whose unit has left the team's bolt (queued again by `crew bolt drop --requeue`, or moved to another bolt), once the slot's agent is not working, then removes every such worktree in the team's kit checkout that no slot holds, whatever left it there. `crew bolt drop`, `crew unit drop` and `crew bolt land` do the same on the team's host right after they change the plan; when that host doesn't answer, the team's next read does it. A worktree with uncommitted changes (modified files, or untracked files git doesn't ignore) or a lock is kept with its branch, and every read names it until it is clean, when crew removes it, or gone; ignored files, such as installed dependencies, never keep one. Each removal goes through the kit's own `wt remove`, run from the kit's main checkout with the branch left to crew, so the kit's remove hooks run: those before removal with the worktree's files still there, those after once it is gone. A remove hook that fails, or that the user has not approved on that host (`wt config approvals add`, in the kit's main checkout), keeps the worktree with its branch, and every read names it, with what wt said failed but never its advice to skip the hooks, and tries it again; crew never approves or skips a kit's hooks. A host whose path has no `wt` keeps the worktree too, named. crew removes only worktrees directly under `<kit>/bolts/` or `<kit>/places/` on a `bolt/`, `unit/` or `fix/` branch it names, never the main checkout, a worktree made by hand or a detached one, and nothing while a plan the kit's work goes in can't be read. `crew rebuild` frees those slots too, its agents ended with the rest, and keeps only the slots of work still in flight on the bolt. `crew unit free <unit>` frees a slot still holding a dropped unit, or one no longer in the team's bolt, at once, and refuses a unit still in it.

A bolt may also hold **chores**: planned maintenance that changes nothing a spec says must be true and needs no decision, such as a tool or dependency bump, a pin or config aligned with another, the archive of a change whose every task is ticked, a rename, or a stale instruction or line of documentation. A chore has no OpenSpec change, no construct and no review: `crew chore run <chore> code|verify|merge` builds it in its bolt, on `chore/<chore>` in `<kit>/places/chore-<chore>` from the bolt, each stage a fresh agent in a slot of the team as a unit's is. Code is told `Chore <chore>: <its words>` and commits each change with a `Chore: <chore>` trailer; verify is told `Verify chore <chore>: <its words>` and checks every commit beyond the bolt against them, saving its report as a unit's verify does, each finding marked fix or leave; merge merges it into the bolt as a unit's merge does. `After` means for a chore what it means for a unit: a chore's code starts once each unit or chore it comes after has something committed to build on, a unit's change or a chore's code, never waiting on a merge, its new place taking their heads as they stand (`Took`), and it merges only after each has merged; a unit that comes after a chore is constructed once the chore's code has delivered, its place taking the chore's head. Verify waits for a commit of the chore's own beyond the bolt, what its place took of others never counting as its own; merge waits for the chore's verify to have delivered, once, and is refused, naming the commits, while one of its own lacks the trailer. When what a chore comes after merges, the team's next read rebases the chore's place onto the bolt, as a unit's. `crew unit run` on a chore, or `crew chore run` on a unit, is refused naming its kind. A chore's stage is read from the kit like a unit's: `landed` once main's history holds its trailer, `merged` once the bolt's does, `verify` once its place holds a commit of its own beyond the bolt, `code` while it holds none, else `ready` or `waiting`. No batch ever holds a chore. Its slot is freed and its place removed as a unit's are, once it has merged or landed, been dropped, or left the team's bolt; `crew chore free <chore>` frees its slot at once, as `crew unit free` does a unit's.

A stage ends at what it delivers, read in the kit or on the team's host, never when its agent goes quiet: construct's change committed since the stage began, its planning complete; code's commit since it began, with every task ticked at the branch's head; settle's commit since it began; verify's report for the unit saved since it began in the team's reports folder, `~/.local/state/<team>-team/reports`; merge's bolt holding the unit's change archived, the chore's trailer or the fix's commits; a fix's commit, and a chore's code's, on its branch since it began; and a chore's verify's report. When a stage began is the time at the front of its start's entry id. `crew unit wait <unit>`, `crew chore wait <chore>` and `crew fix <team> <name> --wait` run on the team's host and return with one line: the stage delivered, once its agent has stopped working, with what it delivered, and its end recorded; it stopped short, with what its agent needs in the agent's words; it is stuck, its agent quiet past `--stuck` (15 minutes) with nothing delivered, nothing said and no background work of its own still running, which crew reads from the agent's Claude transcript (when it can't, the clock runs and the line says what could not be read); its agent is gone; or it is still running when `--timeout` (an hour) passes, its agent working or waiting on work of its own. Only a delivered end is recorded by a wait. `crew needs "<what it needs>"`, run by a stage's agent, ends the stage short: crew records the end without the words and gives them to the conductor, as the answer of a wait running on the stage, else in a tell marked as from the agent; anyone with no stage owed is refused. The answer comes back as the stage run again with it as its words.

A team is two herdr workspaces in its session: `<team>`, with a `conductor` tab (the conductor and ops, started in the kit's main checkout, or in the worktree a bolt given before bolts were branches still has) and, when the team's host is a Mac, a `git` tab (gitgui in the kit and the blueprints repo; gitgui is unusable over ssh), and `<team> units`, one tiled pane per slot in flight, which exists only while a unit or fix is. A team sits whole on one host, and its panes and state live there: a command about a team run anywhere else is run on the team's host, over ssh, by the crew checkout that host's sessions keep.

## The plan

```
crew bolts [<bolt>] [--label L] [--json]
crew bolt  new <bolt> "<goal>" --repo <kit> [--source S]... [--before <bolt>]
crew bolt  give <team> [<bolt>]
crew bolt  order <bolt> --before <bolt>|--first|--last
crew bolt  drop <bolt> "<reason>" [--requeue]
crew bolt  land <bolt>
crew unit  add <unit> "<intent>" --bolt <bolt>|--repo <kit> [--source S]... [--after U]... [--before U] [--signal ID] [--unblocks <bolt>]
crew unit  split <unit> "<narrowed intent>" --into <unit> "<intent>"
crew unit  amend <unit> "<new intent>"
crew unit  order <unit> --before <unit>|--first|--last
crew unit  after <unit> <unit>...|--none
crew unit  move <unit> <bolt>|queue [--unblocks <bolt>]
crew unit  drop <unit> "<reason>"
crew chore add <chore> "<what is done>" --bolt <bolt>|--repo <kit> [--source S]... [--after U]... [--before U] [--signal ID] [--unblocks <bolt>]
crew chore order <chore> --before <unit or chore>|--first|--last
crew chore after <chore> <unit or chore>...|--none
crew chore move <chore> <bolt>|queue [--unblocks <bolt>]
crew chore drop <chore> "<reason>"
```

Each partition keeps one recutils `plan.rec`, for all its kits, on its flywheel's branch of its state repository (see State). It holds only intent: Bolt and Unit records, in build order, a Unit record marked `Kind: chore` being a chore, its `Intent` its words. A name is taken once in a kit, by a unit or a chore: `crew unit add` and `crew chore add` refuse one the plan holds, one the kit's main has a change by, and one main's history holds a chore trailer for. The `crew chore` commands take a unit's flags and make its refusals; there is no `chore split` or `chore amend`, a chore's words changing by a drop and an add, and a unit command on a chore, or a chore command on a unit, is refused naming its kind. A Source is a path in the partition's first blueprints repo, or `<owner>/<name>:<path>` in another. Every stage is read from the kits, one call per host. A command fetches the branch and reads each kit once on each host it runs on, however many steps it has, and a step that makes or removes a worktree leaves the next to read that kit again; a wait, the rail tab and `crew events --follow` read afresh each time they look. A unit's tasks and planning mean what OpenSpec means by them, read from the change's files when it uses OpenSpec's spec-driven workflow and through `openspec` otherwise. A write fetches the branch over https into crew's bare cache of the repo (`~/.cache/crew/git/<owner>/<name>.git`), applies itself to the tip, checks each file it changed with `recfix --check` and the plan with crew's rules, commits through a temporary index, and pushes without force; a push refused because someone wrote first is applied again to the new tip, up to five times. Nothing is ever merged. A write that touches a bolt a team holds sends that team's conductor the commit's subject.

A unit's stage, as `crew bolts` shows it and `--json` gives it in `stage`, is the first that holds of `landed` (main has its change), `merged` (its bolt holds its change archived, as its own merge leaves it), `verify` (every task ticked), `code` (some ticked), `planned` (its planning complete), `construct` (its worktree exists), and `ready` or `waiting` by whether each of its `After` units has finished construct; a unit with no bolt is `queued`. A unit whose change its bolt holds open, carried there inside another unit's merge, has not merged: it reads at its own stage, from its place or, once that is gone, from the change on the bolt, keeps its place and slot, and `crew status` names it carried by another's merge, its own merge owed; that merge makes its place again from the bolt when it is gone. A unit's or chore's merge is refused while its branch holds another unit's change open that the bolt does not hold archived, naming it. A unit the plan marks `Amended` reads, after `landed` and `merged`, `amended` until construct is run again, then `construct` until that commits, whatever its tasks say; then the mark stops counting, the unit reads from its tasks again, and the write that records that construct's end clears it.

A unit in flight is amended in one of two ways, and both put its revised change in the partition's next batch. How it builds what it builds changes when its conductor runs construct again with the user's words (see Teams). What it builds changes with `crew unit amend <unit> "<new intent>"`, which the user runs at a shell and the planner only inside a proposal: it replaces the unit's intent, and a unit that has a worktree is marked amended (`intent`, or `proposal/<n>` from an approval). Once the plan's write has landed, the amendment itself runs `crew unit run <unit> construct` on the team's host, in the name of whoever applied it, the user or the proposal's approver, and its fresh agent is told the intent was amended and by whom, and given the planner's case as the user approved it for a proposal. The conductor is told that construct runs again and to wait for it, with the card of the verify the amendment ended named once construct starts; or why it did not start (the host does not answer, the team is down, or the slot's agent is still working, which crew never ends for it), with that card, and to run it once it can. A unit whose construct did not start reads `amended`, and anyone may start its construct, the user having approved the amendment. A conductor crew brings back finds such units: the greeting of `crew up`, `rebuild`, `restart` and `revive` opens with the units of its bolt that read `amended`, and `crew resume`, which greets nobody, sends it the same line as crew's notice. A unit that has merged is refused: a defect in it is a fix, and new work is a new unit.

`crew bolt drop` removes a bolt and its units and chores from the plan, or with `--requeue` queues them, which it refuses while one of them has a worktree, since a queued unit has none. `crew bolt land` removes a bolt whose units and chores have all landed on main, which main-level ops runs once the bolt's submission to main has landed through sluice: `crew bolt submit <bolt>`, refused while the kit's main is behind GitHub's, makes a short-lived worktree on the bolt's branch at `<kit>/places/land-<bolt>` on the team's host, runs `wt submit main` there in the asker's name and waits for sluice's outcome, then removes the worktree and brings the kit's main checkout level with what landed, since sluice moves main's branch and not that checkout's files; a bolt no team holds, built outside a team, lands the same way on the user's word once main holds each of its units' changes and chores, read on the host of a team of the partition building that kit, with nothing to merge; its entry in the run record names the kit and the commit its main holds afterwards (`Repo` and `Head`), from which a deploy's view tells the bolts it carried. A landing that conflicts with main, or fails main's checks, lands nothing and moves nothing: main-level ops passes sluice's words to the bolt's conductor, and the team takes main into the bolt by a fix submitted to it (see Teams). Either way the bolt's branch and worktrees then go from its team's host (see Teams), and a landing whose worktree is kept, for uncommitted changes or a remove hook, still lands.

## Proposals

```
crew plan propose <file> [--replaces <n>]
crew plan proposed [<n>] [--label L] [--json] [--open]
crew plan agree <n> [--team <team>]
crew plan card <n> [--label L]
crew plan approve <n> [--clear <unit>...]
crew plan answer <n> <question> <answer>... [--note "<text>"]
crew plan drop <n> "<reason>"
```

The planner changes the plan only by a **proposal** the user approves: where new work goes (a new bolt, a unit in a bolt, the queue), and every move, split, amendment, reorder or drop. A proposal is a record in `proposals.rec` on the flywheel's branch: the planner's `Case`, and the plan commands it would run, in order, one `Do` each, as typed without the leading `crew` (`bolt new|order|drop`, `unit add|amend|move|split|order|after|drop`, `chore add|move|order|after|drop`). Proposals are numbered, and never removed or changed.

- `crew plan propose <file>` takes a file of one record, a `Case` and its `Do` lines. Each command is checked in order against the plan as the ones before it leave it, with every refusal it has run directly; a refused command refuses the proposal and nothing is written. The conductor of each bolt in flight the proposal touches is told. `--replaces <n>` drops proposal n and writes its successor in one commit.
- `crew plan proposed` lists the open proposals and what each waits on; `crew plan proposed <n>` prints one as markdown: the case, then each change in plain words, a unit's intent beside what it rests on (a signal's assertion and excerpt) and the goal and team of the bolt it would join, and an amended unit's bolt, team and stage, its intent as it stands and as proposed, and what approval sets in motion; under each change, the command approval runs; and, for an open proposal, who it waits on, in words. It reads only the branch, so any host can answer. With `--open`, it writes that page to `~/.local/state/crew/proposals/<label>-<n>.md` on the host it runs on and opens it in plannotator, for the user to read and annotate: beside the caller in herdr, inline in the terminal otherwise.
- `crew plan agree <n>` is a conductor's recorded agreement to a proposal that touches the bolt its team holds; the user may agree for any team it touches.
- `crew plan card <n>` prints the proposal's Pending You card as JSON, drawn by crew from the branch alone, reading no kit: its title with the counts (dropped, amended, new, moved, split), a summary of what the proposal is, its unit count before and after and the bolt's goal, its case and each change as background, the change as text in lines of at most forty characters (a block per change, then the order once approved), and its questions: an approval, and, for each five units or chores the proposal makes new to a bolt (added, to a bolt or the queue, or moved into a bolt), a question listing them, a chore's words beginning "Chore:", every one ticked, each cleared to leave it out; a lone one is a choice of keeping it or leaving it out, and a proposal with no new unit, or more than fifteen, is a plain approval. No question asks for words: to keep a dropped unit or change an amendment, the user does not approve and says why in the card's note, for the planner to write the proposal again, since a note beside an approval changes nothing applied. It also draws the card's picture, a PNG 780 pixels wide of each bolt the proposal touches once approved, a dropped unit struck where it stood with its reason, an amended one's old intent struck above the new, a new one outlined, in Python's standard library with a bitmap font crew carries, and writes it to `~/.local/state/crew/cards/<label>/proposal/<n>/` on the host it runs on, printing where. It writes nothing to the branch or the run record, and refuses a closed proposal or one that no longer applies.
- `crew plan approve <n>` applies the proposal's commands, as read, to the plan at the tip and closes the proposal, in one commit, or changes nothing when one no longer applies or a touched bolt's conductor has not agreed. A unit or chore with a worktree that moves is rebased before the push and put back if the approval is refused. With `--clear <unit>...` it leaves out the new units and chores the user cleared and every command that concerns only one of them, so a cleared unit is never made and one moved in from the queue or another bolt stays where it was; it refuses, changing nothing, a cleared unit the proposal does not make new to a bolt, and a command left in that names a cleared unit, for the planner to write the proposal again; and it records each as `Cleared` on the proposal. The user runs it, or an agent on the user's word.
- `crew plan answer <n> <question> <answer>...` records one answer of the proposal's card, from the card or a card the user split off it, as the planner reads it: `plan approve` or `plan decline`, or `units-<k>` and the units left ticked (for a lone unit, the unit or `leave-out`), with `--note` for the user's note. It checks the answer against the card `crew plan card <n>` would print, refuses an answer that differs from one it holds, and keeps the answers in `~/.local/state/crew/cards/<label>/proposal/<n>/answers.json` on the host it runs on, the planner's, never on the branch. Once it holds the approval and every unit question's answer, it applies the approval with each unticked unit cleared, as `crew plan approve --clear` does, and prints the note as the user's word for the planner's next proposal; a decline applies nothing. Either way the answers go.
- `crew plan drop <n> "<reason>"` closes a proposal unapplied, with the reason.

Work a bolt in flight needs before it can be proven or land goes into that bolt: a `unit add` or `unit move` marked `--unblocks <bolt>` must place the unit in that held bolt, where it goes ahead of the first unit not yet merged, and the mark is shown on the proposal.

Who writes the plan directly, when the command runs as an agent crew started (`CREW_AGENT`):

| Agent | Writes directly | Otherwise |
|---|---|---|
| the user at a shell | everything | |
| `<label>-planner` | proposals | refused, naming `crew plan propose` |
| `<team>-conductor` | `unit split`, `unit order`, `unit after`, `chore order`, `chore after` on units and chores of the bolt its team holds, and the amended mark `crew unit run <unit> construct` sets on one that is planned, in code or in verify; `plan agree`. The mark's move on a unit whose intent was amended is made by whoever starts that construct | refused, naming the planner |
| `<label>-design` | `unit add … --repo <kit>` and `chore add … --repo <kit>`, the queue | refused, naming the planner |
| `<label>-dispatch-<host>` | `bolt give` | refused, naming the planner |
| `<label>-ops` | `bolt land` | refused, naming the planner |
| any other agent | nothing | refused, naming the planner |

Every refusal is a run-record entry. Writing, agreeing, approving and dropping a proposal are entries naming `proposal/<n>`, and each change an approval applies is an entry of its own, from the proposal, with the approval's commit; `crew trace` follows them.

## State

```
crew state init <label>
```

A partition's **flywheel** is its loop, named by its label. Its state is the files on one branch, `<label>/main`, of the state repository the teams file names for it (`state`, one per organisation, such as `WilldanGroup/crew-state`), apart from the design:

- `plan.rec`, the plan;
- `moves.rec`, every signal's one move;
- `proposals.rec`, the planner's proposals;
- `signals/<capture>/`, the captures and signals recorded through crew (see Signals);
- `runs/<host>/<YYYY-MM-DD>.rec`, the run record each host has carried.

Flywheels sharing a repository never meet: each command fetches and pushes only its own flywheel's branch, and no branch shares history with another. A write that changes several files is one commit, and its message ends with a `Crew-Entry:` trailer naming the run-record entry that describes it. `crew state init <label>` creates the branch: it adopts the first blueprints repo's `plan/<label>` with its history where there is one, joins another blueprints repo's `plan/<label>` in one commit naming where it came from, and copies the first blueprints repo's `signals/moves.rec`; run again, it finishes what a stopped run left, or says the branch exists. A clone of the branch reads with `recsel` and nothing else.

## Signals

```
crew signal <slug> "<what it asserts>" --excerpt "<the words, verbatim>"|--excerpt-file <path> [--kind K] [--subject a,b]
crew signal show <id>
crew signal move <id> attach|challenge|new-territory|answered|drop [--target T] [--reason R]
crew signal land <capture-dir> [--label L]
```

A **signal** is one thing noticed, with the words that show it, in the shape the blueprints' `signals/README.md` gives: a directory per capture, holding `capture.md` and one file per signal. Signals have two homes. What the agents and the user record with `crew signal` is under `signals/` on the flywheel's branch of its state repository; what the daily pass reads from meetings and channels stays under `signals/` in the partition's first blueprints repo. An id is unique across both, and every command looks it up on the flywheel's branch first.

An agent crew started gives an **excerpt**: the words that show the finding, copied as its session received them, from the user or from a tool's output (`--excerpt-file` for words the shell would mangle). crew looks for them, whitespace aside, in the agent's own Claude transcript, `~/.claude*/projects/*/<session>.jsonl` for the session herdr names for the agent, and records a grade on the capture:

- `verified`: the words are in a record the session received, and the capture says who asserted them: `user`; `tool`, for a command's output; `agent:<name>`, for what another agent sent with `crew tell`; or `crew`, for crew's own notice;
- `found`: they are in the transcript, in a record crew cannot classify;
- `unverified`: crew could not read the transcript, and the capture says why: herdr names no session, there is no file, its lines are not JSON, or it has not been written for 15 minutes, so crew may be reading another session's.

A signal is refused only when the transcript is the live session's, its last record written within 15 minutes, and the words are nowhere in it but in what the agent wrote itself: a paraphrase. A change in Claude Code's format lowers a grade and never stops a capture, and no command refuses anything for its grade; the grade is shown wherever the excerpt is.

A capture is the one record the excerpt came from. Its `capture.md` names the host, the Claude session, the record and its time, who asserted it, and where the agent was working: its team, the bolt the team holds and the unit its slot holds, or the main level. The record itself is copied to `~/.local/state/crew/<label>/raw/<capture>.jsonl` on the host, and the capture points at it as `<host>:<path>`; of the source, only the excerpt enters git. A second signal from the same record joins its capture as its next signal, and the same signal again writes nothing. The capture and its signal are one commit on the flywheel's branch. The user's own note, `crew signal` at a shell, is its own excerpt (`excerpt: own`), of kind `ask` unless another is given.

A program records its own captures, a kit's deployer one per failed deploy, an adapter watching the tools the fleet pins one per newer upstream version, and hands each to crew with `crew signal land <capture-dir> --label L`, run as the program (`CREW_AGENT`) on the host that ran it. The folder holds `capture.md` and its signals, `NN-<slug>.md`, and nothing else; the capture names itself, the program as its `source`, who captured it, its event's date and its raw record, `<host>:<path>`, which must be on that host, since only the excerpt enters git; it is read, and counts its signals, at least one, made by the program with no model between: the capture is its own excerpt. Each signal names itself, its kind and who asserted it, says what it asserts, quotes its excerpt, and is no larger than 8 KiB, the program cutting its excerpt to fit and keeping the whole in the raw record. A capture whose name is not crew's kind of name, lowercase words, digits and dashes, is refused. crew lands the folder whole on the flywheel's branch in one commit, as a `capture` entry naming each signal; files the branch holds already are passed over, the same capture again prints that it is already landed and writes nothing, and a capture or signal there that differs is refused, since neither is ever changed. A program never writes a blueprints repo, and `crew signal land --help`'s first line is its usage, which a program reads to know this crew takes captures.

`crew signal show <id>` prints a signal, its capture's fields (the grade, who captured it, where and when, the session and the raw record) and its move, from any host. Curation's moves, `crew signal move`, are appended to `moves.rec` on the flywheel's branch, and a signal becomes work only through its `route` move, which `crew unit add --signal` writes in the same commit as the unit, and `crew chore add --signal` with the chore. Each signal has one move, and nothing is ever merged.

What crew sends an agent is marked as crew's: `crew tell` sends `[crew tell from <sender>] <text>`, the sender being the agent or `<user>@<host>`, and crew's greetings and notices send `[crew] <text>`, so neither is taken for the user's typing.

## Operations

```
crew ops offer|approve <env> --label L --to <sha> [--from <sha|none>]
crew ops word|quiet <env> --label L
crew ops record <env> --label L --to <sha> --act start|step|end [--from F] [--step S] [--outcome O] [--log P] [--rows F]
crew ops step <env> --label L --key K --state waiting|handed|done|failed|declined [--to <sha>] [--doer D] [--agent A] [--when W] [--text F] [--changes C] [--note N]
crew ops steps <env> --label L --json
```

The operations on a partition's environments, a deploy being one kind. A landing deploys nothing; a kit's deployer, or a hosted CI/CD in its place, deploys main under each environment's policy (ADR 0012, `plan.14`), and these are what it asks of crew, each run where the partition's main level runs, as the one asking, on that host's run record (`ops.*` entries on `env/<env>`). `offer` makes a `manual` environment's deploy of a commit a row under *operations* on the rail, keyed `deploy/<env>/<sha>`, whose card main-level ops posts; the same offer again writes nothing, and a newer one replaces it. The user's word is holding that card, recorded with `approve` for the commit the row shows, and refused for any other; `word` prints the commit a word was given for, or exits 1 when there is none, and a word is for one deploy: once its end is recorded, there is none until the next approval. `record` puts a deploy's start, each of its steps (the machine, the guests, the suite and its rows) and its end in the run record as it runs. Every other operation, a command after a deploy, a restart, a check, is a `step`, recorded with its state, its doer, the agent it was handed to and its text, after the deploy it names with `--to` or on its own; one whose doer is the user waits as a rail row, `op/<env>/<n>`, until its card is answered done or declined, and `steps` gives each step's latest state as JSON. `quiet` exits 0 when no stage agent of a team on the environment's host is working and no test of crew's runs there, and 1 saying what does.

Each partition has a main level in the session the teams file names: the **design agent** (elaboration on main and curation of signals), the **planner** (the only writer of bolts and placements, and the poster of the partition's review batches), the **reviewer** (started fresh for each batch, in a `review` tab, and ended once its summary is written) and the main-level **ops** (lands a bolt whose verification is green by one procedure, its submission to main through sluice, on the user's approval of the landing card, pushes main, and deploys a kit with no deployer only on the user's word for that deploy), as tabs of the `<label>` workspace; and a **dispatcher** on each host the partition's teams run on, in `<label> dispatch`, which gives that host's teams their bolts. The **operator agent** stands in each operator session (the session named `<label>`), started there with `crew operator up <label>`, and works for the user. Each agent `crew main up` or `crew operator up` starts is greeted once it is up, as a conductor is, marked `[crew]`: told to read where the partition stands and carry on with what is its role's; one that was already up is neither started nor greeted. `crew tell` prompts any of these agents by name, wherever it runs, marked with who sent it. A tell to an agent waiting on a question in its pane fails with nothing typed, and says to send it again once the question is answered, whether herdr sees the question or crew's PreToolUse hook marked it when the agent opened a question or a plan for the user; the mark counts until the agent's transcript holds the answer. crew's greetings and notices go the same way. A greeting is also read back as a stage's prompt is: sent once the agent is ready, cleared and sent once more when its transcript does not show it, and when the second is not taken either, nothing is left typed, no greeting is recorded, and crew says the agent was not greeted, with the `crew tell` that would greet it.

`crew rail` lists everything that waits on the user, from any host, in four groups, always in this order: open proposals, review batches whose card is still open, bolts whose every unit has merged, waiting to land, and operations: an environment's deploy offered and not yet approved, and an operation that is the user's to take (see Operations). Each row says what waits, when it began to wait and how long ago that was, and carries the commands that answer it, written to be pasted; within a group, the oldest comes first. A proposal waits from its entry in the run record (or the day it was opened), a batch from its review's end, and a bolt from its last merge. Every row and every time is read from the plan, the proposals, the kits and the run record, and nothing is kept by hand: a row leaves the list as soon as its answer is recorded. A host that doesn't answer is named. A bolt whose every unit has merged is offered for landing only once every unit's latest change has been in a batch: until then its row names the units that have not, and carries no command. Nor is it offered until its verification is green, which is the bolt's proof: sluice's verdict on its last landing, the `Sluice-Result` trailer sluice writes on the commit it lands, read at the bolt's head; until then its row says what the verification is. `crew operator up` also opens a `rail` tab in the `operator` workspace, beside `flow`: the list above, printed again every 30 seconds and as soon as the run record gains an entry, and a shell below with crew on its path, to paste a row's command into. It opens a `board` tab after `rail`, drawing the board `crew board` prints from the rail tab's own read: each refresh reads the plans, the kits and the run record once, prints the rail, ending card sessions as `crew rail` does, and hands the board to the board tab, which draws it at its own width. A board read more than 90 seconds ago is headed with how long ago, so a rail tab whose loop has stopped is never taken for a live one; a board tab with no board yet says so, and a rail tab opened before the board existed is closed and opened afresh, with the board tab, by `crew operator up <label>`.

`crew board` shows a partition's whole flow at once, as four lanes stacked one above the other, one object to a line, with a header naming the partition, when it was read and the hosts that answered: **Inception**, the signals no move has taken in either of their homes, grouped by who captured them, each group with how many it holds and when its oldest was captured, each signal with its kind and its first words, then each exploration on main of each kit the partition's teams build, with the first line of its first file; **Bolt plan**, each open proposal with its number, who proposed it and its case, each bolt no team holds with its repository, goal and units and their stages, and the queue, each unit with its sources; **Construction**, each bolt a team holds as a ledger, its head naming its repository, team and host, then each unit in plan order with its stage, its tasks done and total in code and verify, the slot holding it and the URL of the dev server running in its worktree, each fix with whether it has merged, and the bolt's own server at the foot; and **Operation**, each bolt landed in the last seven days, newest first, with when, who landed it, its team and its units, then each environment's deploys that moved in those seven days or are still open, newest first, each with the commit it deploys and the one it comes from, where it stands (waiting on the user's word, replaced by a newer offer unanswered, deploying, approved and not yet deployed, or its outcome and when it ended, at the step that failed), whose word it went on and the bolts it carried, and the operations waiting on that environment, each with who has it: a deploy carried the landings on its kit after the one that left main at the commit it came from, up to the one that left main at its own, and when no landing in the record left main at either, the line names that commit rather than a bolt. A lane with nothing in it says none. Every rail row but a batch's is a marker on its object's line, never a line of its own: ✓ on a proposal waiting on the user, on the head of a bolt waiting to land, on a deploy waiting on the user's word and on an operation waiting on the user, each saying at the line's end whether its card is open and who asked it. The board prints no command and answers nothing: the rail and its shell are where things are answered. At its foot, attention names with ! each host that did not answer, each plan or signals home that could not be read, and each bolt whose every unit has landed but which is still in the plan, whose head carries ! too. It reads the plan, the proposals, the moves, the signals, the kits and the run record, and writes nothing. `crew board --json` prints the same lanes as data, each partition's environments with the teams on their host, each object with its markers, each marker with its rail group, its card key, when its row began to wait and its card, for the page that draws the board.

Each refresh of the rail tab also writes every agent's view of that board beside the board tab's, in `~/.cache/crew/board/<label>.agents.json`, and crew's plugin draws it in the band above that agent's prompt, as a Claude Code mod (`plugin/hooks/status.js`). A conductor sees the bolt its team holds as a ledger, a pip to each unit for its stage (○ not begun, ◔ construct, ◑ code, ◕ verify, ● merged, ? unread), each rail marker on its line, the open proposals that name its team, saying which waits on its agreement, what is planned and queued next for its kit, and what needs attention there; the planner sees the plan in brief, each team's bolt as its pips, the open proposals and whom each waits on, and what comes next and is queued; the design agent sees the signals no move has taken, by who captured them, and the first explorations; main-level ops sees the partition's operations, environment by environment: each deploy waiting on the user's word with its card, each approved and not yet deployed, each running, and each operation step waiting, handed or failed, with the deploy it comes after and its doer; and an operator sees the partition's board in brief, a line to each lane, each team's bolt, each environment with a deploy or an operation waiting, its latest deploy and how many operations wait, and how many rows wait on the user, its deploys' and operations' among them. Every bolt's line is led by its product, the repository it builds, and, in the planner's and the operator's, by the team holding it, dim, product by product. Any other agent, and a session that is no crew agent, draws nothing. The mod finds its agent from `CREW_AGENT` and `CREW_LABEL`, or from the session's record for one herdr resumed, looks at the file's time every five seconds and reads it only when it has changed: it starts no process and adds nothing Claude reads. Views read more than 90 seconds ago end with when they were read; while no rail tab on the host has written any, a crew agent's band says so in one line, naming `crew operator up <label>`.

Each row of the rail is also answered through one **Pending You** card, posted by the agent that owns its decision: the planner's for each proposal it opens and each review batch's one card, and a team conductor's for its bolt once proven. The design agent posts one card for each decision record it proposes, and for each amendment to one, under `record/<kit>/<number>/<commit>`, for a kit its partition builds, the commit the one that proposed the record or the amendment, so each new version is a new card; the record is accepted only on the user's yes on that card. A team's ops and stage agents post no card, and crew's hook refuses, before it reaches Pending You, a card a crew agent posts under any key but a rail row's of its own, or the design agent's record key, and an area under any key but its kit's `create-area:<owner>/<kit>`, naming the key to use. The landing card is marked high stakes, so it is approved only by holding the button in the Pending You app, never with a key in Herdr's popup. Each row's card has its row's form: a proposal's is the card `crew plan card <n>` prints, drawn by crew, an approval with a question per five units the proposal makes new to a bolt, each to be cleared to leave it out, and its answers recorded with `crew plan answer`; a landing's is an approval, high stakes, whose yes has the conductor tell main-level ops to land; a batch's is one notice, kind `fyi`, that says first what it is, names every unit with its team and the reviewer's opening paragraph as prose, asks nothing and links the batch's one reading session, sent back with one tap, its notes the annotations the user sends from that session and the card's own note; a decision record's is an approval of low risk, reversible, with no options or steps; no card asks a question in words, which Pending You makes required; and crew's PreToolUse hook refuses a row's or a record's card in another form, or a change that takes it out of its form, before Pending You sees it, naming the form to use. Answering a card wakes its owner, which acts on the user's word and closes the card with what it did; when crew records a change that ends a row, it names the row's card to its owner, in the command's output when the owner made the change and by a tell otherwise. Under each row's commands, `crew rail` prints the row's card key (`proposal/<n>`, `batch/<n>` or `land/<bolt>/<head>`) and whether a card with that key is open, who asked it and the card's id, by which its owner asks Pending You for it; a newer card its owner posts under a row's key is the row's card, and the older is taken as lost; after the groups, it lists the decision records waiting on the user, each open card under a record key with when it was asked and by whom, and then each open card whose row is gone, oldest first, with a `crew tell` asking its owner to close it, a record card never among those; then each card session it ended on that read, with its card key (and unit, for an old batch card's), its partition, its host and why, its card closed or its row gone, and each host whose sessions it could not check, with why. When it ended none and checked every host, it says nothing about sessions. A landing's key carries the head of the bolt it asks about, so a bolt proven again on a new head after a fix is a new card, and its owner closes the card under the old key with what changed. A card that reads "not found" to its owner, after the host signs in to Pending You again, is lost to it: while its row still waits, its owner, which checks its open cards by their ids at its start and whenever Pending You has it sign in again, posts the card again under its row's key, its summary saying after the link and the bolt that an older copy is dead and this one is the one to answer; the dead copy is the user's to dismiss in the app, and a lost card whose row is gone is posted again by nobody. crew learns of the cards from its agents' own sessions: its PostToolUse hook records each card a crew agent posts, updates, withdraws or closes in the run record, with the card's id and key and nothing written on the card.

A card can also be posted, changed, closed and read through crew itself, as the asking assistant, with no Pending You tools in the agent's session (`briefs.16`, ADR 0005 as amended 2026-10-12): `crew card post <key>` takes the card's own fields as one JSON object on standard input, refuses it as crew's card hook refuses a card under that key, and posts it through the fleet's `pendingyou mcp --app claude-code` under the host's sign-in, in the asker's crew name, under the key, with this host and the folder it runs in as its session, filed in the area Pending You matches to the folder's git remote or, when none does, the kit's area made under `create-area:<owner>/<kit>`; it prints the card's id and link and records `card.post` from Pending You's reply, and posted again under the key it gives the same card back. `crew card change <key>` changes the card the asker holds under the key, at the version Pending You reports; `crew card close <key> --outcome "<line>"` closes it once the asker has acted on the answer, and `--reason "<line>"` withdraws it, each ending the card's session as a close through Pending You's tools does; `crew card read <key>` prints the card's status, whose turn it is, and the user's answer and words. The card a key names is the asker's newest posted under it on this host that no close has closed. What Pending You refuses is refused in its words and recorded; a host with no sign-in is refused saying the user signs it in with `pendingyou-signin`. Until `every-crew-card-goes-through-crew` lands, the briefs still have agents post through Pending You's tools.

A proposal's card holds the proposal whole, crew's picture of the change, its text and the case, and links no session, but for a proposal of more than fifteen new units, which the card can't hold and whose card links the session on its page. A card that asks the user to read something else, a batch's changes, carries the link to a plannotator session on it rather than a file or a path, so the user reads and annotates it from wherever the card is answered, the phone included. The link is the first thing in the card's words, its summary and its background, but on a batch card, whose summary says first what it is and whose background opens with the link, and is among its links; the card's words say what the user decides from in the document's own words, a change's Why and the lead sentence of each of its changes, a proposal's case and changes, a report's findings, and no card carries a path. Its owner starts the session by the card's key: `crew card session <key>` finds the rail row with that key, starts plannotator on the row's document (the proposal's page as `crew plan proposed <n>` prints it, or the report) on the host it runs on, with an Approve button and no browser opened there, and prints the link, the host's tailnet name and a port. Run again while that session runs, it prints the same link and starts nothing. It refuses a landing's key, which has nothing to read, a key with no row, a document on another host, and a link that would open only on the host itself. `crew card wait <key>`, run by the owner in the background, returns once the user decides in the session and prints the decision, approved or annotated with the user's words as they wrote them, or closed in plannotator with no decision; a session that ended without one is said so, and a decision made while nobody waited is returned by the next wait. The owner acts on that decision as the card's answer and withdraws the card. When a crew agent closes or withdraws a keyed card, crew's hook ends the session started for its key; `crew card end <key>` ends one by hand. And every rail read, `crew rail` and each refresh of the rail tab, ends each session crew started whose card is closed or whose row is gone, on every host of the partition, whoever closed the card, and says which it ended; it runs `crew card sweep` on each host with what it judged, which is the rail's and not for hand use. It leaves alone every session crew did not start and every one it can't judge: none on a host that does not answer, which it names, none of a closed card and no batch card's while a host of the run record did not answer, and none started under two minutes before, which a later read judges. `crew board` ends nothing. crew ends only a process plannotator lists as serving the document it started for that key, and keeps each key's session in `~/.local/state/crew/cards/<label>/<key>/` on the owner's host; when plannotator's list of sessions can't be read there, it ends nothing, keeps the session and says so, and a later rail read ends it. The session's link is plain http on the tailnet, from swancloud's `PLANNOTATOR_URL_HOST` and `PLANNOTATOR_PORT`. A batch card has one session, on the whole batch: `crew card session batch/<n>`, run on the partition's main level's host and refused elsewhere, writes the batch's folder beside its summary, `batch-<label>-<n>/`, holding the summary and then every unit's Markdown files as the batch read them at their commits, each named for its unit, and starts plannotator on those files as one review, so each opens whole. It refuses a unit with that key, and a batch it can't read whole, naming the unit and its host, with nothing written or started. `crew card wait batch/<n>` and `crew card end batch/<n>` act on that session, and the card's close ends it; its decision holds the batch's notes and never answers the card. A batch posted under `batch/<n>-<k>`, before a batch was one card, keeps a session for each unit it holds: `crew card session batch/<n>-<k> <unit>` starts one on that unit's change, given its Markdown files, proposal first, rather than its folder, on the host the teams file names for the unit's team; `crew card wait` and `crew card end` take the unit the same way, `crew card end <key>` with no unit ends each of them, and so does the card's close.

The user reads a partition's constructed and amended changes in **batches** that span its teams. A unit's change is due each time a construct of it delivers, and stops being due once a batch has held it at the commit that construct left. On each wait of one of the partition's conductors, crew counts the changes due from the run record and makes a batch due at the partition's setting in the teams file (`review`: `every` N changes, or `hours` T since its last batch with at least one due), or at once when a bolt has every unit merged and some unit's latest change outside a batch; it then tells the planner once (`batch.due`). The planner runs `crew review <label>`, which starts the reviewer, a main-level role taking no slot and greeted by nobody, fresh in a `review` tab of the `<label>` workspace on the main level's host, sent the changes due and how to read each at its commit (`review.start`). The reviewer writes its summary to `~/.local/state/crew/<label>-main/reports/batch-<label>-<n>.md`, as prose with no code block, each unit's section opening with a paragraph of what it does and what the user would most care about, and nothing else; `crew review <label> --wait` returns its path once it is written, records the batch with each unit at its commit (`review.batch`), ends the reviewer and closes its tab. The planner posts the batch as one card, keyed `batch/<n>`, however many units it holds: a notice that says first what it is, names every unit with its team and its opening paragraph, asks nothing and links the batch's one reading session. The batch's notes are the annotations the user sends from that session and the card's own note: the planner sends them, word for word, to the conductor of each unit they speak of, or to every unit's when they name none, saying so, and the conductor runs construct again with them. An unanswered card holds nothing, and `crew bolt land` is refused while a unit's latest change has been in no batch.

A partition or host without Pending You keeps the rail as it is, and its conductors tell the operator agents of every wait instead.

A herdr server that restarts resumes each agent in its saved pane folder, which is the folder crew moved the pane to before starting the agent, since Claude finds a conversation only from the folder it began in. crew's SessionStart hook gives a resumed agent its name and identity back. An agent that never had a message has no conversation to resume, so its pane comes back as a shell: `crew revive`, run on a host after a restart, brings back each standing agent of that host whose pane came back empty, from its last conversation or fresh, greets each conductor and each agent outside a team it brought back, and leaves a team or main level taken down with `crew down` as it is. `crew sites` lists each host's bolts, units and fixes with the URL of each running dev server, named by swancloud's `devurl` and found among the host's portless routes.

## Seeing what happened

```
crew events [--label L] [--about <object>] [--since <time>] [--follow] [--json]
crew events --push [--label L]
crew trace  <object>
crew page   <label> [--out <file>] [--since <time>]
crew unit wait <unit> [--timeout <ms>] [--stuck <ms>]
crew chore wait <chore> [--timeout <ms>] [--stuck <ms>]
```

Every crew command that moves work appends one entry per act, after the act, to the **run record** of the partition it acts for, on the host where it ran: `~/.local/state/crew/<label>/runs/<host>/<YYYY-MM-DD>.rec`, one recutils file per UTC day, each entry one write, never rewritten. An entry holds:

- `Id`, `At` (UTC) and `Host`, where crew ran;
- `By`, the agent crew started that asked (`CREW_AGENT`), or `<user>@<host>`, and `Session`, that agent's Claude session as `<host>:<id>`, carried with a command crew runs again on another host;
- `Act`, such as `unit.add`, `bolt.give`, `stage.start`, `stage.end`, `tell`, `team.up` or `agent.restart`; `forecast`, `amendment` and `unit.rebase`, what reached a unit from another; `batch.due`, `review.start` and `review.batch`, a partition's review batches; and the card acts crew's hook writes, `card.post`, `card.update` and `card.close`;
- `On`, each object acted on, and `From`, each object it came from, as typed names: `unit/<unit>`, `chore/<chore>`, `bolt/<bolt>`, `queue/<kit>`, `signals/<id>`, `team/<team>`, `agent/<name>`, `stage/<unit or chore>/<stage>`, `stage/<bolt>/proof`, `fix/<bolt>/<name>`, `batch/<n>`;
- `Commit`, `<owner>/<name>@<sha>`, when the act wrote one, and `Why`, the subject crew composed from the names of things;
- `Refused`, crew's reason, when a command that would have moved work was refused;
- a stage's end's `Result` (the stage the unit reached), `Tasks`, `Head` (the unit's or fix's branch head), `Ended` (`delivered`; `short`, when its agent said what it needs through crew; or `stopped`, when crew ended its agent first), `Delivered`, what it delivered as an object (`unit/<unit>@<head>`, `chore/<chore>@<head>`, `fix/<bolt>/<name>@<head>`, `bolt/<bolt>@<head>` or `report/<file>`, and `proof/<file>` in an entry from before a bolt's proof was its verification), and `Observed: late` when nobody waited for it, a tell's `Chars`, `Amended: yes` on the start of a construct that marked its unit amended, whose `Commit` is the plan's, and `Took`, the heads of the units it comes after that a construct's new place took; a forecast's `Heads` (`<unit>@<sha> <other>@<sha>`), its conflicting `Paths` and how it `Reached` the later unit (`told`, `prompt` or `settle`), and a stage start's `Forecast`, the forecasts its prompt carried; a review batch's `Batch` and `Units` (each `<unit>:<team>@<commit>`), and a batch due's `Count`; and a card act's `Card` (the Pending You card's id) and `Key` (its rail row's card key, or its record key), on the row's object, on `record/<kit>/<number>` for a decision record's card, or on `agent/<name>` for a card with neither key.

No entry holds text anyone typed: not a tell's text, what a stage's agent said it needs, an intent, a goal, a reason or an excerpt. A read writes nothing, and a record that can't be written is said on standard error and changes nothing about the command. `recsel -t Entry` reads the files with no crew involved.

Every write to the flywheel's branch also carries the host's uncarried entries there, to `runs/<host>/`: each day's file on the branch becomes the union by `Id` of what it had and what the host has, so a host only ever adds to its own files, and one that is asleep or rebuilt loses nothing it had carried. `crew events --push` carries in a commit of its own, and makes none when nothing is left. `crew events` reads the branch, then gathers what every host the partition runs on (its teams', its main level's and its operator sessions') has not yet carried, one call per host, and prints them in time order, naming a host that does not answer, whose entries are shown as far as it had carried them; `--follow` prints them as they are written, and the operator workspace's `flow` tab runs it. `crew trace <object>` prints one bolt's, unit's, chore's or signal's history from the entries alone: what was done, by whom, with which commit, what it came from and what came from it, each line with the `zoe <session>` to open on its host. A bare name is tried as a unit, then a chore, then a bolt, then a signal; `report/<file>` and `proof/<file>` find the end that delivered them. `crew unit wait <unit>` waits on the team's host for the unit's stage to end at its deliverable and records that end. An end nobody waited for is recorded, once and marked late, the next time crew reads the team, but only once its deliverable is there: a stage whose agent has only gone quiet has no end. A stage whose agent crew ends first, to run it again or to free its slot, is recorded `delivered` when its deliverable is there, else `stopped`; one stopped short is recorded by `crew needs` itself.

`crew page <label>` writes the partition's page, one HTML file that opens on its board: the four lanes `crew board` reads, Inception, Bolt plan, Construction and Operation, made by the same read at the same commit of `<label>/main` as the rest of the page, and drawn as the flywheel mockup's phases view draws them: a signal as a quote under who captured it, a proposal as a sheet, a queued unit as a slip, a bolt as a ledger with its units as a chain, a landed bolt as a record, and every rail row a ✓ marker on its object. The lanes sit side by side on a desktop and stack under 760 px, as on a phone, and the page follows the viewer's light or dark preference. A strip under the header shows each host the board asked, one that did not answer marked, and what needs attention. The header's team control narrows every lane but that strip to one of the partition's teams; the choice is kept in the page's address (`#team=<name>`) and in the browser for that partition, so it survives a reload and a page written over this one. The header names every partition in the teams file, and each other one is a link to its page beside this one, `../<label>/page.html`: that holds while the pages keep crew's layout, `~/.local/state/crew/<label>/page.html` or the same under another folder, and not for a page written with `--out` anywhere else. The board answers nothing, and making it asks every host of the partition for its kits, as `crew board` does.

The page's flow view, one switch away, draws the partition's lineage: its signals, agenda items, proposals, units and bolts as columns in that order, a line from each to what it led to, a timeline of the entries per day beneath, and each object opening to its history, the entries `crew trace` prints for it, each with who did it, on which host, with which commit, and the `zoe <session>` to open. Selecting an object marks everything it came from and everything that came from it; a filter hides closed and landed work, and a box narrows by name. Which objects there are, how they are linked and in what order things happened are read from the run record alone, by the walk `crew trace` makes, so the page and the trace cannot disagree; labels and present status (a signal's assertion and move, an item's subject, a proposal's case, a unit's intent and stage, a bolt's goal and team) are read from the flywheel's branch at the commit the entries were read at, and an object the branch no longer holds, such as a landed bolt's units, is labelled from its newest entry. The file holds its data, style and script and loads nothing, so it opens from disk with the network off. It is written whole to `~/.local/state/crew/<label>/page.html` on the host where the command runs, or to `--out`, and never committed; the command prints its path, then as of when and which commit of `<label>/main` it was drawn from, then each host that did not answer, whose uncarried entries the page does not show. `--since` draws only the entries from then on. When the branch can't be read, no page is written and an earlier one is left as it was. The page's deploys view, a third switch, draws each environment's deploys as a timeline over the same window, oldest at the top, so the sequence of what was approved, replaced or left waiting reads down it: each deploy with the commit it moved from and to, the user's word on it as its card's answer recorded it, its steps, the suite's checks and its outcome, the bolts it carried, each with the proposals the lineage joins to it, which say what the deploy brought, and the after-deploy steps of its commit with their doers and states, then the operations waiting on the environment; it is read from the ops entries of the main level's host and the landings, as the board's Operation lane is. Nothing reads the page and making it appends no entry: it is a view, made again to refresh it. The operator agent makes it and opens it beside its pane when asked to show how work flowed.

## Needs

`herdr`, `jq`, `python3`, `git`, and `recutils` for the plan; in each kit `wt`, `sluice` with its `wt-submit`, which worktrunk runs as `wt submit`, `moon` and `openspec`; `devurl` and `portless` for `crew sites`. crew's own toolchain is devenv's system tools, `jq`, `recutils` and `proto`, and the application tools `.prototools` pins, which entering the shell installs when one is missing, and activates: `moon`, and Python at the minor every host runs crew on, with `uv`; the tiers' `venv` task syncs pytest from `tests/uv.lock` into `tests/.venv` before every run of them, with the uv moon's toolchain gives, since moon's own install is skipped under `--force`, as sluice runs.

`tests/run [name...]` runs crew's tests one after another on stub `herdr`, `ssh`, `claude` and `wt submit`, each simulated host with its own scratch home, so no test reaches a real session, host or agent. `tests/suite` runs them as moon tasks, one per test file, each running its test through `tests/run`, side by side; a test whose inputs are identical to a run that passed on the host, in any worktree of crew, is replayed rather than run again. `tests/suite --affected` runs only the tests a change affects, against the merge-base with `main` and counting uncommitted edits, `tests/suite <name>...` the ones named, and `tests/suite --force` runs without replaying. An agent runs the tests that prove what it changes by name while it works and `--affected` once before its merge, never the whole suite by hand: sluice runs every `check-full` task afresh on each submission to a bolt and to main, as crew's `.config/sluice.toml` requires. Every test waits for one of the host's test slots (`tests/slot`), its cores less two unless `CREW_TEST_SLOTS` says otherwise, shared by every worktree on the host. The tasks are `tests/moon.yml`, written by `tests/moon-tasks` from the test files with each task's inputs: crew's command core (`plugin/bin/` and the modules `plan.py` and `crew.py` import) and the common files, and whatever else the test's outcome depends on, named on a `# Reads:` line of its opening comment; after adding or removing a test, or changing what one reads, run `tests/moon-tasks` and commit `tests/moon.yml`, since `tests/suite` refuses to run while they are out of step. Both run in crew's devenv shell, and enter it themselves when started outside it; crew's other tools run through it per command, `devenv shell -- <command>`, and a terminal enters it with `devenv shell`, or direnv with the checkout's `.envrc`. crew's mod has its own cases, `plugin/tests/*.test.ts`, run as the task `mod` by `tests/mod`, which runs them with `claude plugin test plugin`: Claude Code's test kit, with no session, model, sign-in or network. `claude plugin test` takes no option before `plugin`, so where `claude` is a wrapper that adds its own, `tests/mod` runs the program the wrapper's last `exec` names, once it answers `--version` as Claude Code; `CREW_TEST_CLAUDE` names another. The live `crew sites` check on mac-studio is no task: `CREW_TEST_LIVE=1 tests/run sites-live` runs it.
