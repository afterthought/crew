# crew

Bolt teams of Claude agents, run in herdr, and each partition's main level above them.

- The teams and partitions are data in `~/.config/crew/teams.json` (version 2), written by the machine's configuration (in swancloud, `lib/crew-teams.nix`); each partition carries its batch setting, `review: {every, hours}`, and crew refuses one without it. Hosts, sessions, each session's partition and the repos of its space come from `~/.config/swancloud/herdr-hosts.json`.
- `plugin/` is the same for every team: the roles (`roles/`, each an agent definition naming its model and effort), the `crew` and `crew-role` commands (`bin/`), the builder that turns the teams file into briefs and settings (`lib/crew.py`), the plan (`lib/plan.py`, with `lib/gather.py`, which reads a host's kits, and `lib/transcript.py`, which checks a signal's excerpt against its agent's transcript), `crew sites` (`lib/sites.py`), and the skills. It installs as a Claude Code plugin; this repository is its marketplace.

## Teams

```
crew list
crew status   [team]
crew up|down|rebuild|close <team>
crew restart|resume <team> [conductor|ops]
crew clear    <team> conductor|ops
crew unit run <unit> construct|code|verify|settle|merge ["<words>"]
crew unit free <unit> [--team <team>]
crew fix      <team> <name> "<what is wrong>"
crew fix      <team> <name> --merge
crew fix      <team> <name> --wait [--timeout <ms>] [--stuck <ms>]
crew prove    <team> ["<words>"]
crew prove    <team> --wait [--timeout <ms>] [--stuck <ms>]
crew needs    "<what you tried and what you need>"
```

A team builds one **bolt** at a time: a body of work on `bolt/<bolt>`, in `<kit>/bolts/<bolt>`, deployed and tested from that branch and then landed on main. Its standing roles are the **conductor** and **ops**. A bolt is built from **units**, each one OpenSpec change on `unit/<unit>` in `<kit>/places/<unit>`, taken stage by stage: construct writes the change, code builds it as soon as it is committed, with no review between, verify checks it, and merge merges it into the bolt with `wt merge bolt/<bolt> --no-squash --no-remove`, one merge at a time, or with `wt submit bolt/<bolt>` where the kit opts into sluice by `sluice = true` in its main checkout's `.config/crew.toml`, whose verdict replaces the merge hooks' suite gate. Each stage is a fresh agent at that stage's effort, in one of the team's `units` slots; a team taken down with `crew down` starts no stage until it is brought up. crew sends the agent the stage's prompt only once it is ready for input, and the stage begins only once the agent's own transcript shows Claude received it; a prompt it does not show within a short time is cleared from the agent's input with one Ctrl+C and sent once more. When the second is not taken either, or the agent was never ready, nothing is left typed in its pane: the stage never started, its start is recorded refused with no end owed, its slot and idle agent stay, and `crew unit run` or `crew fix` fails saying so and how to run it again. crew sends nothing more, and presses nothing, while the agent is working, or when it cannot read whether the prompt was taken, and says what it could not read. ops's request for a proof (`crew prove`) goes the same way, and a proof whose request is not taken never started. Construct can be run again with the user's words at any stage before the unit merges: run on a unit that is planned, in code or in verify, it marks the unit amended in the plan, code, verify and merge are refused until the change written again is committed, and the write that records that construct's end clears the mark; the unit then goes on from its tasks, with nothing to approve, and its revised change is in the partition's next batch. A merged unit is not amended: a defect in it is a fix, and a new need a new unit.

A bolt's units are built side by side, as slots allow, their changes written in waves: every unit with no `After` is constructed at once, and a unit that comes after others as soon as their changes are committed, never waiting on their merge. A dependent's new place takes the head of each of its unmerged `After` units as it stands; when one of them merges, crew rebases the dependent's place onto the bolt at the team's next read or the conductor's next wait, only while its agent is not working and its place is clean, the bolt's commits dropping out. A dependent merges only after each unit it comes after has merged. Construct ends the proposal with `## Touches` and a fenced block of paths or globs; code is refused without it, a unit whose Touches overlap those of an unmerged unit ahead of it starts code with the overlap and that unit's change in its prompt, and verify's prompt names each path the unit changed against its bolt and did not declare. Overlap holds nothing. On every `crew unit wait` and `crew prove --wait`, crew dry-runs with `git merge-tree`, writing no ref, the merge of each unmerged unit with the bolt and with each unmerged unit ahead of it, and a forecast conflict reaches only the later unit, once for a pair of heads (`forecast` in the run record): told to its stage's agent once that is not working, carried in its next stage's prompt when none of it runs, or as a **settle** stage, a fresh coder in its slot, when it has delivered its verify and waits to merge; a settle ends at a commit on its branch, or its agent saying nothing needs to change, and the unit then merges with no verify again. A forecast between two unmerged units puts the later after the earlier. An `After` unit constructed again reaches each of its dependents the same way, and holds none of them. The later unit resolves every conflict, keeping both changes' intents; the earlier is never changed for it. A **fix** is built the same way on `fix/<bolt>/<name>` from the bolt, in `<kit>/places/fix-<bolt>--<name>`, with no change and no plan record; a fix name already in use on the bolt is refused. A fix whose branch is the bolt's own commits replayed onto the kit's main, a conflict resolved and nothing added, carries the bolt onto main. crew judges that by the commits themselves: the fix holds as many commits beyond main as the bolt, and in order each is the bolt's commit replayed, with the same message and author, its patch the same or changed by the resolution. Beside its judgment crew prints `git range-diff` of the two as the reading, which judges nothing. `crew fix <team> <name> --merge` then makes its head the bolt's head rather than merging it, ending the fix's agent and moving `bolt/<bolt>` in the bolt's worktree, runs the kit's post-merge hooks there on the new head as a merge into the bolt would, and records `fix.carry`; the bolt is proven again before it lands. Any other fix merges into the bolt like a unit, and crew says why it did not carry the bolt, naming the bolt's commits that are not in it and the fix's that are none of the bolt's. Every worktree crew made goes, with its branch, once its work is over: a bolt's once no plan has it (landed or dropped), a unit's once it has merged into its bolt or landed or no plan has it, and a fix's once it has merged into its bolt or no plan has its bolt; when a removed branch held commits of its own, crew says the commit it was at. Each time crew reads a team (`crew status <team>`, `crew unit run`, `crew fix`) it frees every slot whose unit or fix has merged or been dropped, or whose unit has left the team's bolt (queued again by `crew bolt drop --requeue`, or moved to another bolt), once the slot's agent is not working, then removes every such worktree in the team's kit checkout that no slot holds, whatever left it there. `crew bolt drop`, `crew unit drop` and `crew bolt land` do the same on the team's host right after they change the plan; when that host doesn't answer, the team's next read does it. A worktree with uncommitted changes (modified files, or untracked files git doesn't ignore) or a lock is kept with its branch, and every read names it until it is clean, when crew removes it, or gone; ignored files, such as installed dependencies, never keep one. Each removal goes through the kit's own `wt remove`, run from the kit's main checkout with the branch left to crew, so the kit's remove hooks run: those before removal with the worktree's files still there, those after once it is gone. A remove hook that fails, or that the user has not approved on that host (`wt config approvals add`, in the kit's main checkout), keeps the worktree with its branch, and every read names it, with what wt said failed but never its advice to skip the hooks, and tries it again; crew never approves or skips a kit's hooks. A host whose path has no `wt` keeps the worktree too, named. crew removes only worktrees directly under `<kit>/bolts/` or `<kit>/places/` on a `bolt/`, `unit/` or `fix/` branch it names, never the main checkout, a worktree made by hand or a detached one, and nothing while a plan the kit's work goes in can't be read. `crew rebuild` frees those slots too, its agents ended with the rest, and keeps only the slots of work still in flight on the bolt. `crew unit free <unit>` frees a slot still holding a dropped unit, or one no longer in the team's bolt, at once, and refuses a unit still in it.

A stage ends at what it delivers, read in the kit or on the team's host, never when its agent goes quiet: construct's change committed since the stage began, its planning complete; code's commit since it began, with every task ticked at the branch's head; settle's commit since it began; verify's report for the unit saved since it began in the team's reports folder, `~/.local/state/<team>-team/reports`; merge's bolt holding the unit's change or the fix's commits; a fix's commit on its branch since it began; and ops's proof file. When a stage began is the time at the front of its start's entry id. `crew unit wait <unit>`, `crew fix <team> <name> --wait` and `crew prove <team> --wait` run on the team's host and return with one line: the stage delivered, once its agent has stopped working, with what it delivered, and its end recorded; it stopped short, with what its agent needs in the agent's words; it is stuck, its agent quiet past `--stuck` (15 minutes) with nothing delivered, nothing said and no background work of its own still running, which crew reads from the agent's Claude transcript (when it can't, the clock runs and the line says what could not be read); its agent is gone; or it is still running when `--timeout` (an hour) passes, its agent working or waiting on work of its own. Only a delivered end is recorded by a wait. `crew needs "<what it needs>"`, run by a stage's agent, or by ops during a proof, ends the stage short: crew records the end without the words and gives them to the conductor, as the answer of a wait running on the stage, else in a tell marked as from the agent; anyone with no stage owed is refused. The answer comes back as the stage run again with it as its words. `crew prove <team>` asks the team's ops, in a tell marked as from the caller, to deploy the bolt and work each unit's *Proof in dev* list, and owes the proof's end like a stage's; ops writes its results once, whole, to `proof-<bolt>-<YYYYMMDD-HHMM>.md` in the team's reports folder. It is refused while the team holds no bolt or its ops is not up; a proof still owed ends as stopped when another is asked for, or when ops is restarted or taken down.

A team is two herdr workspaces in its session: `<team>`, with a `conductor` tab (the conductor and ops, started in the worktree of the bolt the team holds) and, when the team's host is a Mac, a `git` tab (gitgui in the kit and the blueprints repo; gitgui is unusable over ssh), and `<team> units`, one tiled pane per slot in flight, which exists only while a unit or fix is. A team sits whole on one host, and its panes and state live there: a command about a team run anywhere else is run on the team's host, over ssh, by the crew checkout that host's sessions keep.

## The plan

```
crew bolts [<bolt>] [--label L] [--json]
crew bolt  new <bolt> "<goal>" --repo <kit> [--source S]... [--before <bolt>]
crew bolt  give <team> [<bolt>]
crew bolt  order <bolt> --before <bolt>|--first|--last
crew bolt  drop <bolt> "<reason>" [--requeue]
crew bolt  land <bolt>
crew unit  add <unit> "<intent>" --bolt <bolt>|--repo <kit> [--source S]... [--after U]... [--before U] [--signal ID] [--unblocks <bolt>]
crew unit  split <unit> "<narrowed intent>" --into <unit> "<intent>"
crew unit  amend <unit> "<new intent>"
crew unit  order <unit> --before <unit>|--first|--last
crew unit  after <unit> <unit>...|--none
crew unit  move <unit> <bolt>|queue [--unblocks <bolt>]
crew unit  drop <unit> "<reason>"
```

Each partition keeps one recutils `plan.rec`, for all its kits, on its flywheel's branch of its state repository (see State). It holds only intent: Bolt and Unit records, in build order. A Source is a path in the partition's first blueprints repo, or `<owner>/<name>:<path>` in another. Every stage is read from the kits, one call per host. A command fetches the branch and reads each kit once on each host it runs on, however many steps it has, and a step that makes or removes a worktree leaves the next to read that kit again; a wait, the rail tab and `crew events --follow` read afresh each time they look. A unit's tasks and planning mean what OpenSpec means by them, read from the change's files when it uses OpenSpec's spec-driven workflow and through `openspec` otherwise. A write fetches the branch over https into crew's bare cache of the repo (`~/.cache/crew/git/<owner>/<name>.git`), applies itself to the tip, checks each file it changed with `recfix --check` and the plan with crew's rules, commits through a temporary index, and pushes without force; a push refused because someone wrote first is applied again to the new tip, up to five times. Nothing is ever merged. A write that touches a bolt a team holds sends that team's conductor the commit's subject.

A unit's stage, as `crew bolts` shows it and `--json` gives it in `stage`, is the first that holds of `landed` (main has its change), `merged` (its bolt has it), `verify` (every task ticked), `code` (some ticked), `planned` (its planning complete), `construct` (its worktree exists), and `ready` or `waiting` by whether each of its `After` units has finished construct; a unit with no bolt is `queued`. A unit the plan marks `Amended` reads, after `landed` and `merged`, `amended` until construct is run again, then `construct` until that commits, whatever its tasks say; then the mark stops counting, the unit reads from its tasks again, and the write that records that construct's end clears it.

A unit in flight is amended in one of two ways, and both put its revised change in the partition's next batch. How it builds what it builds changes when its conductor runs construct again with the user's words (see Teams). What it builds changes with `crew unit amend <unit> "<new intent>"`, which the user runs at a shell and the planner only inside a proposal: it replaces the unit's intent, and a unit that has a worktree is marked amended (`intent`, or `proposal/<n>` from an approval). Once the plan's write has landed, the amendment itself runs `crew unit run <unit> construct` on the team's host, in the name of whoever applied it, the user or the proposal's approver, and its fresh agent is told the intent was amended and by whom, and given the planner's case as the user approved it for a proposal. The conductor is told that construct runs again and to wait for it, with the card of the verify the amendment ended named once construct starts; or why it did not start (the host does not answer, the team is down, or the slot's agent is still working, which crew never ends for it), with that card, and to run it once it can. A unit whose construct did not start reads `amended`, and anyone may start its construct, the user having approved the amendment. A conductor crew brings back finds such units: the greeting of `crew up`, `rebuild`, `restart` and `revive` opens with the units of its bolt that read `amended`, and `crew resume`, which greets nobody, sends it the same line as crew's notice. A unit that has merged is refused: a defect in it is a fix, and new work is a new unit.

`crew bolt drop` removes a bolt and its units from the plan, or with `--requeue` queues its units, which it refuses while one of them has a worktree, since a queued unit has none. `crew bolt land` removes a bolt whose units have all landed on main, which main-level ops runs once the bolt's merge onto main has landed through the kit's hooks. A landing whose rebase conflicts lands nothing: main-level ops aborts it and names the commit and files to the bolt's conductor, and the team carries the bolt onto main with a fix (see Teams). Either way the bolt's worktrees then go from its team's host (see Teams), and a landing whose worktree is kept, for uncommitted changes or a remove hook, still lands.

## Proposals

```
crew plan propose <file> [--replaces <n>]
crew plan proposed [<n>] [--label L] [--json] [--open]
crew plan agree <n> [--team <team>]
crew plan approve <n>
crew plan drop <n> "<reason>"
```

The planner changes the plan only by a **proposal** the user approves: where new work goes (a new bolt, a unit in a bolt, the queue), and every move, split, amendment, reorder or drop. A proposal is a record in `proposals.rec` on the flywheel's branch: the planner's `Case`, and the plan commands it would run, in order, one `Do` each, as typed without the leading `crew` (`bolt new|order|drop`, `unit add|amend|move|split|order|after|drop`). Proposals are numbered, and never removed or changed.

- `crew plan propose <file>` takes a file of one record, a `Case` and its `Do` lines. Each command is checked in order against the plan as the ones before it leave it, with every refusal it has run directly; a refused command refuses the proposal and nothing is written. The conductor of each bolt in flight the proposal touches is told. `--replaces <n>` drops proposal n and writes its successor in one commit.
- `crew plan proposed` lists the open proposals and what each waits on; `crew plan proposed <n>` prints one as markdown: the case, then each change in plain words, a unit's intent beside what it rests on (a signal's assertion and excerpt) and the goal and team of the bolt it would join, and an amended unit's bolt, team and stage, its intent as it stands and as proposed, and what approval sets in motion; under each change, the command approval runs; and, for an open proposal, who it waits on, in words. It reads only the branch, so any host can answer. With `--open`, it writes that page to `~/.local/state/crew/proposals/<label>-<n>.md` on the host it runs on and opens it in plannotator, for the user to read and annotate: beside the caller in herdr, inline in the terminal otherwise.
- `crew plan agree <n>` is a conductor's recorded agreement to a proposal that touches the bolt its team holds; the user may agree for any team it touches.
- `crew plan approve <n>` applies the proposal's commands, exactly as read, to the plan at the tip and closes the proposal, in one commit, or changes nothing when one no longer applies or a touched bolt's conductor has not agreed. A unit with a worktree that moves is rebased before the push and put back if the approval is refused. The user runs it, or an agent on the user's word.
- `crew plan drop <n> "<reason>"` closes a proposal unapplied, with the reason.

Work a bolt in flight needs before it can be proven or land goes into that bolt: a `unit add` or `unit move` marked `--unblocks <bolt>` must place the unit in that held bolt, where it goes ahead of the first unit not yet merged, and the mark is shown on the proposal.

Who writes the plan directly, when the command runs as an agent crew started (`CREW_AGENT`):

| Agent | Writes directly | Otherwise |
|---|---|---|
| the user at a shell | everything | |
| `<label>-planner` | proposals | refused, naming `crew plan propose` |
| `<team>-conductor` | `unit split`, `unit order`, `unit after` on units of the bolt its team holds, and the amended mark `crew unit run <unit> construct` sets on one that is planned, in code or in verify; `plan agree`. The mark's move on a unit whose intent was amended is made by whoever starts that construct | refused, naming the planner |
| `<label>-design` | `unit add … --repo <kit>`, the queue | refused, naming the planner |
| `<label>-dispatch-<host>` | `bolt give` | refused, naming the planner |
| `<label>-ops` | `bolt land` | refused, naming the planner |
| any other agent | nothing | refused, naming the planner |

Every refusal is a run-record entry. Writing, agreeing, approving and dropping a proposal are entries naming `proposal/<n>`, and each change an approval applies is an entry of its own, from the proposal, with the approval's commit; `crew trace` follows them.

## State

```
crew state init <label>
```

A partition's **flywheel** is its loop, named by its label. Its state is the files on one branch, `<label>/main`, of the state repository the teams file names for it (`state`, one per organisation, such as `WilldanGroup/crew-state`), apart from the design:

- `plan.rec`, the plan;
- `moves.rec`, every signal's one move;
- `proposals.rec`, the planner's proposals;
- `signals/<capture>/`, the captures and signals recorded through crew (see Signals);
- `runs/<host>/<YYYY-MM-DD>.rec`, the run record each host has carried.

Flywheels sharing a repository never meet: each command fetches and pushes only its own flywheel's branch, and no branch shares history with another. A write that changes several files is one commit, and its message ends with a `Crew-Entry:` trailer naming the run-record entry that describes it. `crew state init <label>` creates the branch: it adopts the first blueprints repo's `plan/<label>` with its history where there is one, joins another blueprints repo's `plan/<label>` in one commit naming where it came from, and copies the first blueprints repo's `signals/moves.rec`; run again, it finishes what a stopped run left, or says the branch exists. A clone of the branch reads with `recsel` and nothing else.

## Signals

```
crew signal <slug> "<what it asserts>" --excerpt "<the words, verbatim>"|--excerpt-file <path> [--kind K] [--subject a,b]
crew signal show <id>
crew signal move <id> attach|challenge|new-territory|answered|drop [--target T] [--reason R]
```

A **signal** is one thing noticed, with the words that show it, in the shape the blueprints' `signals/README.md` gives: a directory per capture, holding `capture.md` and one file per signal. Signals have two homes. What the agents and the user record with `crew signal` is under `signals/` on the flywheel's branch of its state repository; what the daily pass reads from meetings and channels stays under `signals/` in the partition's first blueprints repo. An id is unique across both, and every command looks it up on the flywheel's branch first.

An agent crew started gives an **excerpt**: the words that show the finding, copied as its session received them, from the user or from a tool's output (`--excerpt-file` for words the shell would mangle). crew looks for them, whitespace aside, in the agent's own Claude transcript, `~/.claude*/projects/*/<session>.jsonl` for the session herdr names for the agent, and records a grade on the capture:

- `verified`: the words are in a record the session received, and the capture says who asserted them: `user`; `tool`, for a command's output; `agent:<name>`, for what another agent sent with `crew tell`; or `crew`, for crew's own notice;
- `found`: they are in the transcript, in a record crew cannot classify;
- `unverified`: crew could not read the transcript, and the capture says why: herdr names no session, there is no file, its lines are not JSON, or it has not been written for 15 minutes, so crew may be reading another session's.

A signal is refused only when the transcript is the live session's, its last record written within 15 minutes, and the words are nowhere in it but in what the agent wrote itself: a paraphrase. A change in Claude Code's format lowers a grade and never stops a capture, and no command refuses anything for its grade; the grade is shown wherever the excerpt is.

A capture is the one record the excerpt came from. Its `capture.md` names the host, the Claude session, the record and its time, who asserted it, and where the agent was working: its team, the bolt the team holds and the unit its slot holds, or the main level. The record itself is copied to `~/.local/state/crew/<label>/raw/<capture>.jsonl` on the host, and the capture points at it as `<host>:<path>`; of the source, only the excerpt enters git. A second signal from the same record joins its capture as its next signal, and the same signal again writes nothing. The capture and its signal are one commit on the flywheel's branch. The user's own note, `crew signal` at a shell, is its own excerpt (`excerpt: own`), of kind `ask` unless another is given.

`crew signal show <id>` prints a signal, its capture's fields (the grade, who captured it, where and when, the session and the raw record) and its move, from any host. Curation's moves, `crew signal move`, are appended to `moves.rec` on the flywheel's branch, and a signal becomes work only through its `route` move, which `crew unit add --signal` writes in the same commit as the unit. Each signal has one move, and nothing is ever merged.

What crew sends an agent is marked as crew's: `crew tell` sends `[crew tell from <sender>] <text>`, the sender being the agent or `<user>@<host>`, and crew's greetings and notices send `[crew] <text>`, so neither is taken for the user's typing.

## The main level and the operator agent

```
crew main     up|down|status <label>
crew operator up <label>
crew rail     [--label L]
crew board    [--label L] [--json]
crew card     session|wait|end <key> [<unit>] [--label L]
crew review   <label> [--wait [--timeout <ms>]]
crew revive
crew tell     <agent> "<text>"
crew sites    [<label>] [--json]
```

Each partition has a main level in the session the teams file names: the **design agent** (elaboration on main and curation of signals), the **planner** (the only writer of bolts and placements, and the poster of the partition's review batches), the **reviewer** (started fresh for each batch, in a `review` tab, and ended once its summary is written) and the main-level **ops** (lands proven bolts by one procedure on the user's approval of the landing card, pushes main, and deploys a kit with no deployer only on the user's word for that deploy), as tabs of the `<label>` workspace; and a **dispatcher** on each host the partition's teams run on, in `<label> dispatch`, which gives that host's teams their bolts. The **operator agent** stands in each operator session (the session named `<label>`), started there with `crew operator up <label>`, and works for the user. Each agent `crew main up` or `crew operator up` starts is greeted once it is up, as a conductor is, marked `[crew]`: told to read where the partition stands and carry on with what is its role's; one that was already up is neither started nor greeted. `crew tell` prompts any of these agents by name, wherever it runs, marked with who sent it. A tell to an agent waiting on a question in its pane fails with nothing typed, and says to send it again once the question is answered, whether herdr sees the question or crew's PreToolUse hook marked it when the agent opened a question or a plan for the user; the mark counts until the agent's transcript holds the answer. crew's greetings and notices go the same way. A greeting is also read back as a stage's prompt is: sent once the agent is ready, cleared and sent once more when its transcript does not show it, and when the second is not taken either, nothing is left typed, no greeting is recorded, and crew says the agent was not greeted, with the `crew tell` that would greet it.

`crew rail` lists everything that waits on the user, from any host, in four groups, always in this order: open proposals, review batches whose card is still open, verify reports the user hasn't answered, and bolts whose every unit has merged, waiting to land. Each row says what waits, when it began to wait and how long ago that was, and carries the commands that answer it, written to be pasted; within a group, the oldest comes first. A proposal waits from its entry in the run record (or the day it was opened), a batch from its review's end, a verify report from when it was written, once it is newer than that commit, and a bolt from its last merge. Every row and every time is read from the plan, the proposals, the kits and the run record, and nothing is kept by hand: a row leaves the list as soon as its answer is recorded. A host that doesn't answer is named. A bolt whose every unit has merged is offered for landing only once every unit's latest change has been in a batch: until then its row names the units that have not, and carries no command. `crew operator up` also opens a `rail` tab in the `operator` workspace, beside `flow`: the list above, printed again every 30 seconds and as soon as the run record gains an entry, and a shell below with crew on its path, to paste a row's command into. It opens a `board` tab after `rail`, drawing the board `crew board` prints from the rail tab's own read: each refresh reads the plans, the kits and the run record once, prints the rail and hands the board to the board tab, which draws it at its own width. A board read more than 90 seconds ago is headed with how long ago, so a rail tab whose loop has stopped is never taken for a live one; a board tab with no board yet says so, and a rail tab opened before the board existed is closed and opened afresh, with the board tab, by `crew operator up <label>`.

`crew board` shows a partition's whole flow at once, as four lanes stacked one above the other, one object to a line, with a header naming the partition, when it was read and the hosts that answered: **Inception**, the signals no move has taken in either of their homes, grouped by who captured them, each group with how many it holds and when its oldest was captured, each signal with its kind and its first words, then each exploration on main of each kit the partition's teams build, with the first line of its first file; **Bolt plan**, each open proposal with its number, who proposed it and its case, each bolt no team holds with its repository, goal and units and their stages, and the queue, each unit with its sources; **Construction**, each bolt a team holds as a ledger, its head naming its repository, team and host, then each unit in plan order with its stage, its tasks done and total in code and verify, the slot holding it and the URL of the dev server running in its worktree, each fix with whether it has merged, and the bolt's own server at the foot; and **Operation**, each bolt landed in the last seven days, newest first, with when, who landed it, its team and its units. A lane with nothing in it says none. Every rail row but a batch's is a marker on its object's line, never a line of its own: ✓ on a proposal waiting on the user and on the head of a bolt waiting to land, ✎ on a unit whose verify report the user hasn't answered, each saying at the line's end whether its card is open and who asked it. The board prints no command and answers nothing: the rail and its shell are where things are answered. At its foot, attention names with ! each host that did not answer, each plan or signals home that could not be read, and each bolt whose every unit has landed but which is still in the plan, whose head carries ! too. It reads the plan, the proposals, the moves, the signals, the kits and the run record, and writes nothing. `crew board --json` prints the same lanes as data, each object with its markers, each marker with its rail group, its card key, when its row began to wait and its card, for the page that draws the board.

Each row of the rail is also answered through one **Pending You** card, posted by the agent that owns its decision: the planner's for each proposal it opens and each card of a review batch, and a team conductor's for each verify report the user decides on, and its bolt once proven. A team's ops and stage agents post no card, and crew's hook refuses, before it reaches Pending You, a card a crew agent posts under any key but a rail row's of its own and an area under any key but its kit's `create-area:<owner>/<kit>`, naming the key to use. The landing card is marked high stakes, so it is approved only by holding the button in the Pending You app, never with a key in Herdr's popup. Each row's card has its row's form: a proposal's and a landing's are approvals, the landing's high stakes, whose yes has the conductor tell main-level ops to land; a verify report's is a choice of the conductor's options; and crew's PreToolUse hook refuses a row's card in another form, or a change that takes it out of its form, before Pending You sees it, naming the form to use. A batch's card is checked for its key alone, not yet for its form. Answering a card wakes its owner, which acts on the user's word and closes the card with what it did; when crew records a change that ends a row, it names the row's card to its owner, in the command's output when the owner made the change and by a tell otherwise. Under each row's commands, `crew rail` prints the row's card key (`proposal/<n>`, `batch/<n>-<k>`, `verify/<unit>/<stamp>` or `land/<bolt>/<head>`) and whether a card with that key is open, and who asked it; after the groups, it lists each open card whose row is gone, oldest first, with a `crew tell` asking its owner to close it. A verify report's key carries its stamp and a landing's the head of the bolt it asks about, so a report written again, or a bolt proven again on a new head after a fix, is a new card, and its owner closes the card under the old key with what changed. crew learns of the cards from its agents' own sessions: its PostToolUse hook records each card a crew agent posts, updates, withdraws or closes in the run record, with the card's id and key and nothing written on the card.

A card that asks the user to read something, a proposal, a batch's changes or a verify report, carries the link to a plannotator session on it rather than a file or a path, so the user reads and annotates it from wherever the card is answered, the phone included. The link is the first thing in the card's words, its summary and its background, and is among its links; the card's words say what the user decides from in the document's own words, a change's Why and the lead sentence of each of its changes, a proposal's case and changes, a report's findings, and no card carries a path. Its owner starts the session by the card's key: `crew card session <key>` finds the rail row with that key, starts plannotator on the row's document (the proposal's page as `crew plan proposed <n>` prints it, or the report) on the host it runs on, with an Approve button and no browser opened there, and prints the link, the host's tailnet name and a port. Run again while that session runs, it prints the same link and starts nothing. It refuses a landing's key, which has nothing to read, a key with no row, a document on another host, and a link that would open only on the host itself. `crew card wait <key>`, run by the owner in the background, returns once the user decides in the session and prints the decision, approved or annotated with the user's words as they wrote them, or closed in plannotator with no decision; a session that ended without one is said so, and a decision made while nobody waited is returned by the next wait. The owner acts on that decision as the card's answer and withdraws the card. When a crew agent closes or withdraws a keyed card, crew's hook ends the session started for its key; `crew card end <key>` ends one by hand. crew ends only a process plannotator lists as serving the document it started for that key, and keeps each key's session in `~/.local/state/crew/cards/<label>/<key>/` on the owner's host. The session's link is plain http on the tailnet, from swancloud's `PLANNOTATOR_URL_HOST` and `PLANNOTATOR_PORT`. A batch card has a session for each unit it holds: `crew card session batch/<n>-<k> <unit>` starts one on that unit's whole change, its proposal, design, specs and tasks, on the host the teams file names for the unit's team, and refuses a unit the card does not hold; `crew card wait` and `crew card end` take the unit the same way, `crew card end <key>` with no unit ends each of them, and so does the card's close.

The user reads a partition's constructed and amended changes in **batches** that span its teams. A unit's change is due each time a construct of it delivers, and stops being due once a batch has held it at the commit that construct left. On each wait of one of the partition's conductors, crew counts the changes due from the run record and makes a batch due at the partition's setting in the teams file (`review`: `every` N changes, or `hours` T since its last batch with at least one due), or at once when a bolt has every unit merged and some unit's latest change outside a batch; it then tells the planner once (`batch.due`). The planner runs `crew review <label>`, which starts the reviewer, a main-level role taking no slot and greeted by nobody, fresh in a `review` tab of the `<label>` workspace on the main level's host, sent the changes due and how to read each at its commit (`review.start`). The reviewer writes its summary to `~/.local/state/crew/<label>-main/reports/batch-<label>-<n>.md` and nothing else; `crew review <label> --wait` returns its path once it is written, records the batch with each unit at its commit (`review.batch`), ends the reviewer and closes its tab. The planner posts the batch as cards of at most five units, keyed `batch/<n>-<k>`, each with each unit's summary and its session's link, asking which need notes and for the notes, and sends each picked unit's notes, verbatim, to its team's conductor, which runs construct again with them. An unanswered card holds nothing, and `crew bolt land` is refused while a unit's latest change has been in no batch.

A partition or host without Pending You keeps the rail as it is, and its conductors tell the operator agents of every wait instead.

A herdr server that restarts resumes each agent in its saved pane folder, which is the folder crew moved the pane to before starting the agent, since Claude finds a conversation only from the folder it began in. crew's SessionStart hook gives a resumed agent its name and identity back. An agent that never had a message has no conversation to resume, so its pane comes back as a shell: `crew revive`, run on a host after a restart, brings back each standing agent of that host whose pane came back empty, from its last conversation or fresh, greets each conductor and each agent outside a team it brought back, and leaves a team or main level taken down with `crew down` as it is. `crew sites` lists each host's bolts, units and fixes with the URL of each running dev server, named by swancloud's `devurl` and found among the host's portless routes.

## Seeing what happened

```
crew events [--label L] [--about <object>] [--since <time>] [--follow] [--json]
crew events --push [--label L]
crew trace  <object>
crew page   <label> [--out <file>] [--since <time>]
crew unit wait <unit> [--timeout <ms>] [--stuck <ms>]
```

Every crew command that moves work appends one entry per act, after the act, to the **run record** of the partition it acts for, on the host where it ran: `~/.local/state/crew/<label>/runs/<host>/<YYYY-MM-DD>.rec`, one recutils file per UTC day, each entry one write, never rewritten. An entry holds:

- `Id`, `At` (UTC) and `Host`, where crew ran;
- `By`, the agent crew started that asked (`CREW_AGENT`), or `<user>@<host>`, and `Session`, that agent's Claude session as `<host>:<id>`, carried with a command crew runs again on another host;
- `Act`, such as `unit.add`, `bolt.give`, `stage.start`, `stage.end`, `tell`, `team.up` or `agent.restart`; `forecast`, `amendment` and `unit.rebase`, what reached a unit from another; `batch.due`, `review.start` and `review.batch`, a partition's review batches; and the card acts crew's hook writes, `card.post`, `card.update` and `card.close`;
- `On`, each object acted on, and `From`, each object it came from, as typed names: `unit/<unit>`, `bolt/<bolt>`, `queue/<kit>`, `signals/<id>`, `team/<team>`, `agent/<name>`, `stage/<unit>/<stage>`, `stage/<bolt>/proof`, `fix/<bolt>/<name>`, `batch/<n>`;
- `Commit`, `<owner>/<name>@<sha>`, when the act wrote one, and `Why`, the subject crew composed from the names of things;
- `Refused`, crew's reason, when a command that would have moved work was refused;
- a stage's end's `Result` (the stage the unit reached), `Tasks`, `Head` (the unit's, fix's or proven bolt's branch head), `Ended` (`delivered`; `short`, when its agent said what it needs through crew; or `stopped`, when crew ended its agent first), `Delivered`, what it delivered as an object (`unit/<unit>@<head>`, `fix/<bolt>/<name>@<head>`, `bolt/<bolt>@<head>`, `report/<file>` or `proof/<file>`), and `Observed: late` when nobody waited for it, a tell's `Chars`, `Amended: yes` on the start of a construct that marked its unit amended, whose `Commit` is the plan's, and `Took`, the heads of the units it comes after that a construct's new place took; a forecast's `Heads` (`<unit>@<sha> <other>@<sha>`), its conflicting `Paths` and how it `Reached` the later unit (`told`, `prompt` or `settle`), and a stage start's `Forecast`, the forecasts its prompt carried; a review batch's `Batch` and `Units` (each `<unit>:<team>@<commit>`), and a batch due's `Count`; and a card act's `Card` (the Pending You card's id) and `Key` (its rail row's card key), on the row's object, or on `agent/<name>` for a card with no row key.

No entry holds text anyone typed: not a tell's text, what a stage's agent said it needs, an intent, a goal, a reason or an excerpt. A read writes nothing, and a record that can't be written is said on standard error and changes nothing about the command. `recsel -t Entry` reads the files with no crew involved.

Every write to the flywheel's branch also carries the host's uncarried entries there, to `runs/<host>/`: each day's file on the branch becomes the union by `Id` of what it had and what the host has, so a host only ever adds to its own files, and one that is asleep or rebuilt loses nothing it had carried. `crew events --push` carries in a commit of its own, and makes none when nothing is left. `crew events` reads the branch, then gathers what every host the partition runs on (its teams', its main level's and its operator sessions') has not yet carried, one call per host, and prints them in time order, naming a host that does not answer, whose entries are shown as far as it had carried them; `--follow` prints them as they are written, and the operator workspace's `flow` tab runs it. `crew trace <object>` prints one bolt's, unit's or signal's history from the entries alone: what was done, by whom, with which commit, what it came from and what came from it, each line with the `zoe <session>` to open on its host. A bare name is tried as a unit, then a bolt, then a signal; `report/<file>` and `proof/<file>` find the end that delivered them. `crew unit wait <unit>` waits on the team's host for the unit's stage to end at its deliverable and records that end. An end nobody waited for is recorded, once and marked late, the next time crew reads the team, but only once its deliverable is there: a stage whose agent has only gone quiet has no end. A stage whose agent crew ends first, to run it again or to free its slot, is recorded `delivered` when its deliverable is there, else `stopped`; one stopped short is recorded by `crew needs` itself.

`crew page <label>` writes the partition's page, one HTML file that opens on its board: the four lanes `crew board` reads, Inception, Bolt plan, Construction and Operation, made by the same read at the same commit of `<label>/main` as the rest of the page, and drawn as the flywheel mockup's phases view draws them: a signal as a quote under who captured it, a proposal as a sheet, a queued unit as a slip, a bolt as a ledger with its units as a chain, a landed bolt as a record, and every rail row a ✓ or ✎ marker on its object. The lanes sit side by side on a desktop and stack under 760 px, as on a phone, and the page follows the viewer's light or dark preference. A strip under the header shows each host the board asked, one that did not answer marked, and what needs attention. The header's team control narrows every lane but that strip to one of the partition's teams; the choice is kept in the page's address (`#team=<name>`) and in the browser for that partition, so it survives a reload and a page written over this one. The header names every partition in the teams file, and each other one is a link to its page beside this one, `../<label>/page.html`: that holds while the pages keep crew's layout, `~/.local/state/crew/<label>/page.html` or the same under another folder, and not for a page written with `--out` anywhere else. The board answers nothing, and making it asks every host of the partition for its kits, as `crew board` does.

The page's flow view, one switch away, draws the partition's lineage: its signals, agenda items, proposals, units and bolts as columns in that order, a line from each to what it led to, a timeline of the entries per day beneath, and each object opening to its history, the entries `crew trace` prints for it, each with who did it, on which host, with which commit, and the `zoe <session>` to open. Selecting an object marks everything it came from and everything that came from it; a filter hides closed and landed work, and a box narrows by name. Which objects there are, how they are linked and in what order things happened are read from the run record alone, by the walk `crew trace` makes, so the page and the trace cannot disagree; labels and present status (a signal's assertion and move, an item's subject, a proposal's case, a unit's intent and stage, a bolt's goal and team) are read from the flywheel's branch at the commit the entries were read at, and an object the branch no longer holds, such as a landed bolt's units, is labelled from its newest entry. The file holds its data, style and script and loads nothing, so it opens from disk with the network off. It is written whole to `~/.local/state/crew/<label>/page.html` on the host where the command runs, or to `--out`, and never committed; the command prints its path, then as of when and which commit of `<label>/main` it was drawn from, then each host that did not answer, whose uncarried entries the page does not show. `--since` draws only the entries from then on. When the branch can't be read, no page is written and an earlier one is left as it was. Nothing reads the page and making it appends no entry: it is a view, made again to refresh it. The operator agent makes it and opens it beside its pane when asked to show how work flowed.

## Needs

`herdr`, `jq`, `python3`, `git`, and `recutils` for the plan; in each kit `wt`, `moon` and `openspec`; `devurl` and `portless` for `crew sites`. `devenv.nix` declares `jq`, `moon`, `python3` and `recutils`.

`tests/run [name...]` runs crew's tests one after another on stub `herdr`, `ssh` and `claude`, each simulated host with its own scratch home, so no test reaches a real session, host or agent. `tests/suite` runs them as moon tasks, one per test file, each running its test through `tests/run`, side by side; a test whose inputs are identical to a run that passed on the host, in any worktree of crew, is replayed rather than run again. `tests/suite --affected` runs only the tests a change affects, against the merge-base with `main` and counting uncommitted edits, `tests/suite <name>...` the ones named, `tests/suite --force` runs without replaying, and `tests/suite --gate <branch>`, the merge gate's run, replays nothing onto main. An agent runs the tests that prove what it changes by name while it works and `--affected` once before its merge, never the whole suite by hand: every merge's gate runs it, and the bolt's verification after it. Every test waits for one of the host's test slots (`tests/slot`), two fewer than its cores unless `CREW_TEST_SLOTS` says otherwise, shared by every worktree on the host. The tasks are `tests/moon.yml`, written by `tests/moon-tasks` from the test files with each task's inputs: crew's command core (`plugin/bin/` and the modules `plan.py` and `crew.py` import) and the common files, and whatever else the test's outcome depends on, named on a `# Reads:` line of its opening comment; after adding or removing a test, or changing what one reads, run `tests/moon-tasks` and commit `tests/moon.yml`, since `tests/suite` refuses to run while they are out of step. Run both in crew's devenv shell, which a Claude session in a crew checkout is in from its start; a terminal enters it with `devenv shell`, or direnv with the checkout's `.envrc`. The live `crew sites` check on mac-studio is no task: `CREW_TEST_LIVE=1 tests/run sites-live` runs it.
