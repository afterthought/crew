# crew

Bolt teams of Claude agents, run in herdr, and each partition's main level above them.

- The teams and partitions are data in `~/.config/crew/teams.json` (version 2, 3 or 4, version 3 naming each team's `flume`, see Teams, and version 4 each partition's too, which names the main-level roles that run as their Flume kinds: see The main level and the console), written by the machine's configuration (in swancloud, `lib/crew-teams.nix`); each partition carries its batch setting, `review: {every, hours}`, and crew refuses one without it. Hosts, sessions, each session's partition and the repos of its space come from `~/.config/swancloud/herdr-hosts.json`.
- `plugin/` is the same for every team: the roles (`roles/`, each an agent definition naming its model and effort), the `crew` and `crew-role` commands (`bin/`), the builder that turns the teams file into briefs and settings (`lib/crew.py`), the plan (`lib/plan.py`, with `lib/gather.py`, which reads a host's kits, and `lib/transcript.py`, which checks a signal's excerpt against its agent's transcript), `crew sites` (`lib/sites.py`), and the skills. It installs as a Claude Code plugin; this repository is its marketplace.

## Teams

```
crew list
crew status   [team]
crew up|down|rebuild|close <team>
crew restart|resume <team> [conductor|ops]
crew clear    <team> conductor|ops
crew fix      <bolt> <name> "<what is wrong>" [--label L]
crew fix      <bolt> <name> --drop [--label L]
crew answer   <work> "<words>" [--label L]
```

A **bolt** is a body of work on the branch `bolt/<bolt>` on GitHub, which `crew bolt start` has sluice make from the kit's main, with no worktree, which moves only through sluice and then lands on main. `crew bolt start <bolt>` is the user's, or a proposal's the user approves: the planner proposes which bolts run, and no other agent starts one. Once a bolt is proven, every unit and chore merged and its verification green, it waits to land on the user's yes, a row of its kit's landings card, and a fix when its landing conflicts with main. Its standing roles are the **conductor** and **ops**. A bolt is built from **units**, each one OpenSpec change, built in a Flume place of the change kind on its kit's host, which constructs, codes and verifies it and submits it to the bolt through sluice: sluice tests the bolt with it merged on the checks the kit's policy requires of its bolt branches, `[branches."bolt/*"]` in the `.config/sluice.toml` on its main, read from `origin/main`, and lands it as a merge commit only when they pass. `crew bolt start` has sluice make the bolt's branch on GitHub, `sluice branch create bolt/<bolt> --from main` in the kit's main checkout on the kit's host, the host of the team that builds the kit in a stream, before it writes the plan, and makes nothing else; it refuses, with the plan unchanged and no branch made, a kit whose policy at `origin/main` names no such checks or no `remote` for its bolt branches, naming the file and the key, a host whose sluice is older than 0.20.0, which has no `branch create`, or whose version it can't read, naming the version it needs and what the host's said, and a create sluice refuses, in sluice's words, but for a branch already on GitHub at main's tip with no commit of its own, as a start that failed after sluice made it leaves it, which the start takes and goes on with, saying so; a branch with commits of its own is refused by name. A plan write refused after the create, or after the start took the branch, has sluice delete the branch again. Every unit's, chore's and fix's place is cut from `origin/bolt/<bolt>` after a fetch and tracks it, so it holds every merge sluice landed there from any host. crew reads a bolt on GitHub where it lives, at `origin/bolt/<bolt>`, when the policy there names a remote for it: its head, its verification, the changes and chores it holds and every stage read from it, never the host's own `bolt/<bolt>`, which is sluice's copy and may lag GitHub's. `crew bolts` and a start's making of the branch fetch the kit's origin first, a fetch that fails named in git's words and nothing read from the host's copy in its place; every other read, `crew status`, the rail and the board among them, takes the bolt as the host last fetched it. A bolt whose branch crew made on its host before sluice made bolts' branches stays local until it lands: no create is run for it, its places are cut from the local branch, and each read of its team says so once. crew starts no stage and waits on none: a stage's start and end are Flume's, read from the runner's records (see below).

A unit's, chore's and fix's places are Flume's, readied by its kind and the kit's own files, its `CLAUDE.md`, its `openspec/config.yaml` and its `.config/flume.toml`; crew readies no worktree. crew reads of a kit's `.config/sluice.toml` only what gates its bolt branches, where they live and whether it declares a preview, through `plugin/lib/kit.py`; sluice reads the same file, which becomes `flywheel.toml` once flywheel uses sluice's SDK.

A **fix** is a Flume place of the fix kind on a started bolt, `crew fix <bolt> <name> "<what is wrong>"`, the planner's or main-level ops's, cut from `bolt/<bolt>`, with no change and no plan record; a fix name already in use on the bolt is refused, and `crew fix <bolt> <name> --drop` drops it, a merged one refused, since a new fix undoes it. Flume submits a fix to the bolt as it submits a unit, through sluice; nothing of crew's moves a bolt's branch. A landing that conflicts with main is the bolt's: a fix merges main into its place, resolving the conflict, and is submitted to the bolt. crew removes only what it made. A bolt's branch, which crew marks as its own in the kit's git config when it makes it (`branch.bolt/<bolt>.crew`), and marks landed once sluice has landed it on main, goes once no plan has it and no worktree is on it: a dropped bolt's only by sluice's delete, which keeps it on GitHub and the team's host, marked dropped, named as the drop's unmerged work in sluice's words and recorded once, while main lacks its tip, the team's reads asking sluice again once main holds it; and a landed bolt's only when `git cherry` finds no commit on it whose patch main lacks, one holding such a commit, or one git cannot compare, kept, named in the command's output with the commit it is at and how many commits it holds of its own, the user's to keep or delete, and recorded once in the run record (`branch.kept`), so a landing leaves in the kit only what main lacks. A landing's place, `<kit>/places/land-<bolt>` on `bolt/<bolt>`, goes once no plan has the bolt and never while its submission is with sluice. Every place of Flume's, a unit's, chore's or fix's place an older crew made, a bolt's worktree from before bolts were branches, the main checkout and every other worktree crew leaves alone, and it removes nothing while a plan the kit's work goes in can't be read. Each time crew reads a team (`crew status <team>`) it reads each landing of the team's bolts nothing recorded and sweeps what it made; `crew bolt drop`, `crew unit drop`, `crew chore drop` and `crew bolt land` do the same on the team's host right after they change the plan, and when that host doesn't answer, the team's next read does it. A landing's place with uncommitted changes (modified files, or untracked files git doesn't ignore) or a lock is kept with its branch, and every read names it until it is clean, when crew removes it, or gone; ignored files, such as installed dependencies, never keep one. Each removal first has sluice let the worktree go, asked from the kit's main checkout: sluice runs the teardown command the kit's sluice policy gives, ends what the worktree's runs left running and frees its ports, so what sluice stood up for it goes too; a let-go that fails, its teardown command among them, keeps the worktree with its branch, and every read names it, in sluice's words, and tries it again. It then goes through the kit's own `wt remove`, run from the kit's main checkout with the branch left to crew, so the kit's remove hooks run: those before removal with the worktree's files still there, those after once it is gone. A remove hook that fails, or that the user has not approved on that host (`wt config approvals add`, in the kit's main checkout), keeps the worktree with its branch, and every read names it, with what wt said failed but never its advice to skip the hooks, and tries it again; crew never approves or skips a kit's hooks. A host whose path has no `wt` keeps the worktree too, named.

A bolt may also hold **chores**: planned maintenance that changes nothing a spec says must be true and needs no decision, such as a tool or dependency bump, a pin or config aligned with another, the archive of a change whose every task is ticked, a rename, or a stale instruction or line of documentation. A chore has no OpenSpec change, no construct and no review: it is built in its bolt as a Flume place of the chore kind, each of its commits carrying a `Chore: <chore>` trailer, and submitted to the bolt through sluice as a unit is. `After` means for a chore what it means for a unit: it is launched only once what it comes after has landed on the bolt. A chore's stage is read from the runner's records as a unit's is, or, for one an older crew built, from the kit: `landed` once main's history holds its trailer, `merged` once the bolt's does. No batch ever holds a chore.

A wait of crew's, `crew review <label> --wait` and the `sluice wait` a landing keeps running while sluice has its submission, ends with the Claude session that started it, read by the process id Claude Code gives each command it runs (`CLAUDE_PID`): once that session is gone the wait ends at its next look, saying so and recording nothing; a wait run from a shell, or forwarded from another host, has no session to end with.

A team is two herdr workspaces in its session: `<team>`, with a `conductor` tab (the conductor and ops, started in the kit's main checkout, or in the worktree a bolt from before bolts were branches still has) and no git tab, on a Mac as on a box (a git tab an earlier crew opened there is the user's to close), and `<team> units`, one tiled pane per slot in flight, which exists only while a unit or fix is. Neither folder names the branch the conductor and ops work for, so while their team holds a bolt each carries the branch of the bolt it builds for sluice's sidebar and board, as `SLUICE_BRANCH` and as its pane's `sluice_branch` token, set again when herdr resumes it and cleared once the bolt lands or is dropped, when the conductor and ops are restarted at their next stop without it; a unit slot carries neither, its place being on its own branch. A team sits whole on one host, and its panes and state live there: a command about a team run anywhere else is run on the team's host, over ssh, by the crew checkout that host's sessions keep.

Every team's work runs through **Flume**. Version 3 of the teams file, and version 4 after it, names `flume` on every team, the name of the Flume stream its work runs in on its host, or `false` where it names none, and crew refuses a version-3 or 4 file in which a team names none, `true`, an empty string or a name crew does not accept, naming the team and the file; a version-2 file names no stream for any team. A team runs no conductor, ops or slot: `crew up`, `rebuild`, `restart`, `resume`, `clear`, `down` and `revive` of it are refused at once, touching no pane, naming that its work runs in Flume places on its host and that `crew bolts` shows them; `crew close` still closes what an older crew left standing. A start has sluice make the bolt's branch, and is refused for a bolt started already, while its host is held, while no team of the partition builds its kit in a stream, or while no runner answers there, the state repository holding no `<label>/runner/<host>`, naming it; its one plan write marks the bolt `Path: flume`, writing no team, and appends to `requests.rec` (see State) a launch for each unit and chore, in the plan's order, cut from `bolt/<bolt>`, in the team's stream, with its bolt's priority, the plan's first bolt the highest, the intent `<label>/<bolt>`, the partition's planner as its recipient and the work's own words as its brief, and starts no agent. The host's **runner** (agentplot/flywheel-runner) launches each through Flume, which runs its kind's stages, construct, code and verify for a unit and code for a chore or a fix, and submits it to the bolt through sluice itself; a unit or chore that comes after other work is launched only once that work has landed on the bolt, the runner holding it meanwhile. Plan writes reach the places, each the write's own act in its own commit: a unit or chore added to or moved into a started bolt is launched; an approved amendment is a retry of the unit's construct with its words, or a drop and a new launch carrying them while its first has not run; a drop drops its place, and a dependent waiting on it is launched again without it; a reorder of bolts appends a priority for each place whose priority changed; a move out of the bolt, a split or an `After` change of launched work is refused, naming its place and drop then add as the way on. `crew answer <work> "<words>"`, the planner's, the design agent's or main-level ops's, appends a retry of the stage the work's place stopped short on or waits on its caller for, carrying the words, `<work>` the unit's or chore's name or a fix's place (`<bolt>--<name>`, `main--<name>`), and is refused, naming the place's stage, when it neither stopped short nor waits on its caller. `crew fix <bolt> <name> "<words>"`, the planner's or main-level ops's, appends a launch of a Flume fix place on the bolt, `<bolt>--<name>`, with nothing held, on the host of the team holding it; `--drop` drops it, one merged refused; crew fix has no `--merge` or `--wait`, since Flume submits the fix to the bolt itself and `crew bolts` shows its stage; a fix in flight holds the bolt's landing. A started bolt that sluice refuses at its landing for a conflict with main launches its take-main fix by the act that reads the refusal, `<bolt>--take-main-<main's revision>`, with sluice's words, once however often the refusal is read, and its row says it takes main first; once that fix has merged and the bolt reads proven again, the user's send that ticked it still lands it.

## The plan

```
crew bolts [<bolt>] [--label L] [--json]
crew bolt  new <bolt> "<goal>" --repo <kit> [--source S]... [--before <bolt>]
crew bolt  start <bolt> [--label L]
crew bolt  order <bolt> --before <bolt>|--first|--last
crew bolt  drop <bolt> "<reason>" [--requeue]
crew bolt  land <bolt>
crew bolt  leave <bolt>... --excerpt "<the user's words>"
crew unit  add <unit> "<intent>" --bolt <bolt>|--repo <kit> [--source S]... [--after U]... [--before U] [--signal ID] [--unblocks <bolt>]
crew unit  split <unit> "<narrowed intent>" --into <unit> "<intent>"
crew unit  amend <unit> "<new intent>"
crew unit  order <unit> --before <unit>|--first|--last
crew unit  after <unit> <unit>...|--none
crew unit  move <unit> <bolt>|queue [--unblocks <bolt>]
crew unit  drop <unit> "<reason>"
crew chore add <chore> "<what is done>" --bolt <bolt>|--repo <kit> [--source S]... [--after U]... [--before U] [--signal ID] [--unblocks <bolt>]
crew chore order <chore> --before <unit or chore>|--first|--last
crew chore after <chore> <unit or chore>...|--none
crew chore move <chore> <bolt>|queue [--unblocks <bolt>]
crew chore drop <chore> "<reason>"
```

Each partition keeps one recutils `plan.rec`, for all its kits, on its flywheel's branch of its state repository (see State). It holds only intent: Bolt and Unit records, in build order, a Unit record marked `Kind: chore` being a chore, its `Intent` its words, and a started Bolt marked `Path: flume`; a bolt names no team, and a `Team` an older crew wrote is read by nothing. A name is taken once in a kit, by a unit or a chore: `crew unit add` and `crew chore add` refuse one the plan holds, one the kit's main has a change by, and one main's history holds a chore trailer for. The `crew chore` commands take a unit's flags and make its refusals; there is no `chore split` or `chore amend`, a chore's words changing by a drop and an add, and a unit command on a chore, or a chore command on a unit, is refused naming its kind. A Source is a path in the partition's first blueprints repo, or `<owner>/<name>:<path>` in another. Every stage is read from the kits, one call per host. A command fetches the branch and reads each kit once on each host it runs on, however many steps it has, and a step that makes or removes a worktree leaves the next to read that kit again; a wait reads afresh each time it looks, and the host's follower and `crew events --follow` read again, at each look, only what has moved since they last read. A unit's tasks and planning mean what OpenSpec means by them, read from the change's files when it uses OpenSpec's spec-driven workflow and through `openspec` otherwise. A write fetches the branch over https into crew's bare cache of the repo (`~/.cache/crew/git/<owner>/<name>.git`), applies itself to the tip, checks each file it changed with `recfix --check` and the plan with crew's rules, commits through a temporary index, and pushes without force; a push refused because someone wrote first is applied again to the new tip, up to five times. Nothing is ever merged. A write that touches a bolt a team holds sends that team's conductor the commit's subject.

A unit's stage, as `crew bolts` shows it and `--json` gives it in `stage`, is the first that holds of `landed` (main has its change), `merged` (its bolt holds its change archived, as its own merge leaves it), `verify` (every task ticked), `code` (some ticked), `planned` (its planning complete), `construct` (its worktree exists), and `ready` or `waiting` by whether each of its `After` units has finished construct; a unit with no bolt is `queued`. A unit whose change its bolt holds open, carried there inside another unit's merge, has not merged: it reads at its own stage, from its place or, once that is gone, from the change on the bolt, keeps its place and slot, and `crew status` names it carried by another's merge, its own merge owed; that merge makes its place again from the bolt when it is gone. A unit's or chore's merge is refused while its branch holds another unit's change open that the bolt does not hold archived, naming it. A unit the plan marks `Amended` reads, after `landed` and `merged`, `amended` until construct is run again, then `construct` until that commits, whatever its tasks say; then the mark stops counting, the unit reads from its tasks again, and the write that records that construct's end clears it.

A unit, chore or fix of a bolt marked `Path: flume` reads its stage from its host's runner's records (see State), never from the kit: `launching` until the runner answers its launch, `waiting` while the runner holds it for its `After` work, `refused` with the runner's words; then from Flume's status of its place, as the runner carried it: `queued` for room at a stage; `construct`, `code` with its ticked tasks of all, or `verify`, while that stage runs; `needs` with the agent's question when it stopped short; its stage with sluice's words when sluice sent it back; `submitted` with sluice's number; `waits` with Flume's words when it waits on its caller, `stalled` past its bound; `merged` once its place has landed on the bolt, `landed` once main holds that commit; and `dropped`. A host whose runner branch is missing or can't be read is named, and its pieces read `unknown`. `crew bolts` says each team's stream on its bolt's head line, `crw-4 @ deneb, in Flume stream madswan`, and gives a piece's line its place's folder and what goes with its stage; `--json` gives each bolt its team's `stream` and each piece of a started bolt its `flume` stage, and names each runner it could not read in `runners_unread`.

While a submission stands in sluice's queue, `crew bolts` shows its number and state on its bolt's row from the first read after the submit, whoever made it: a unit's, chore's or fix's merge into `bolt/<bolt>` on that line, `#41 under test`, and the bolt's landing on its kit's main, from `bolt/<bolt>` or a pull request opened from it, on the bolt's head line, `landing #355 queued`; `--json` gives each line a `submission` and the bolt a `landing`, each with its `id` and sluice's `state`. crew reads them from sluice's own record of the queue, `sluice overview --json` once in the kit's main checkout on the team's host, so a session that comes back after a restart finds on the row each submission it had in sluice. A queue that can't be read there is said once on the bolt's head line, and no line shows a number or says it has none.

A unit in flight is amended with `crew unit amend <unit> "<new intent>"`, which the user runs at a shell and the planner only inside a proposal, and its revised change is in the partition's next batch: it replaces the unit's intent, and a unit that has a worktree is marked amended (`intent`, or `proposal/<n>` from an approval). In a started bolt the write reaches the unit's place itself: a launched place gets a retry of its construct carrying the amendment's words, the planner's case among them for a proposal, and a launch the runner holds or has not answered is dropped and the unit launched anew carrying them. A unit that has merged is refused: a defect in it is a fix, and new work is a new unit.

`crew bolt drop` removes a bolt and its units and chores from the plan, or with `--requeue` queues them, which it refuses while one of them has a worktree, since a queued unit has none; for a started bolt, it then has sluice delete the bolt's branch, `sluice branch delete bolt/<bolt> --into main` on the team's host once its worktrees are gone, wherever the policy at its tip keeps it, crew deleting none with git: sluice deletes a branch whose tip main holds, and keeps one while main lacks its tip, on GitHub and the host, which the drop names as its unmerged work in sluice's words, the user's to keep or delete, and records once, the team's next read after main comes to hold its tip having sluice delete it; a drop whose host does not answer names the command, which the team's next read asks. `crew bolt land` removes a bolt whose units and chores have all landed on main, which `crew bolt submit` runs for each bolt as it lands and main-level ops runs itself for one the submission landed and could not close, has sluice delete the bolt's branch after its plan write, `sluice branch delete bolt/<bolt> --into main` on the team's host once the landing's place is gone, wherever the policy at its tip keeps it, on GitHub for a bolt started through sluice or a bolt made before whose landing's pull request put it there, naming a delete sluice refuses in its words with the bolt out of the plan all the same, ends the bolt's reading and lets go its preview on its team's host, and raises its kit's landings card on the partition's main machine, which closes once every bolt the user ticked has landed or been held, "Landed on GitHub's main: <bolt> at `<sha>`; every host's folder follows by swancloud's timer within minutes". The word to land is the user's send on that card, or their own words in main-level ops's pane, which ops passes with `crew bolt submit <bolt>... --excerpt "<the user's words>"`: before anything is submitted, crew reads the words in ops's own session transcript on its host and goes on only when it reads them as the user's, typed in the pane or told from the user's shell, refusing ops's own words, another agent's, crew's, a tool's and a word from the board, naming who said them; each landed bolt's `bolt.submit` entry names the transcript record and the words' length and none of the words, ops's host keeps the words until `crew bolt land`, and the kit's landings card then says first that the bolt landed on the user's word in ops's pane, with their words, changed in place while other rows can land and closed as answered there once none can, or, run on another host than the submission, naming the pane and the time without them. `crew bolt submit <bolt>...` lands one kit's bolts in the order given, refused before anything is submitted when they are of two kits, one is named twice or one is held by no team; a landing of a bolt already standing in sluice on its kit's main at the head it would submit, as when the session that submitted it ended, read from sluice's queue on the team's host, is waited on again rather than submitted anew, saying its number, nothing submitted and its pull request left as it is, and its end read and recorded as any landing's, while one standing at another head is said, naming its number and head, and the bolt submitted as below, as it is when the queue can't be read; for each other it first fetches the bolt's branch from the kit's origin on its team's host and submits the bolt where it lives: a bolt on GitHub, whose copy there has a policy naming a remote for it, at GitHub's head, never the host's own `bolt/<bolt>`, sluice's copy, which may lag and which crew first sets to that head with `git update-ref` guarded by the value it read, the one write sluice's guard lets through, saying so with both commits, or makes there when the host has none; a legacy bolt whose host tip holds merges GitHub's copy lacks, and GitHub's nothing beyond it, at that tip, its push moving GitHub's branch forward; and a bolt that lives on its host at its host's branch; a bolt whose two copies have diverged, each holding merges the other lacks, is submitted nothing and nothing is written, naming both commits and what each lacks, since either submission would drop merges, and the way on: the bolt is its branch on GitHub, so its team's conductor starts a fix, cut from GitHub's head, that takes the host copy's merges in with `git merge bolt/<bolt>` and merges into the bolt through sluice, the one merge into a split bolt crew lets through, since its head holds the host's tip and sluice drops none of it, and the landing then submits GitHub's head, levelling the host's copy to it; so is one whose copy on GitHub can't be read, in git's words, each before its pull request is readied; then it makes a short-lived worktree on the bolt's branch at `<kit>/places/land-<bolt>` on its team's host, or brings one a stopped landing left there to that head without writing a ref, and runs `wt submit main --no-wait --json` there in the asker's name, the next as soon as sluice has queued it when both are on one host, so sluice tests them as one chain and lands them in that order, and only once it has ended when the next is on another; then it waits on each in order with `sluice wait`, removes its worktree, naming it with git's words when git cannot, for `crew bolt land` to remove with the bolt's branch or name with why it stays, closes each that landed with `crew bolt land`'s own code, naming one it could not close with that command, and records one that did not land at the head it submitted, the rest going on, the command exiting non-zero naming each that did not land: refused, holding its row on the kit's landings card for its team's fix, only when sluice's own record of the submission has it in conflict or blamed for a check that ran and failed or that its time limit cut off, the bolt's own content; and stopped, with what stopped it and no refusal, for anything else, sluice itself failing, checks the host could not run, a refusal or an answer with no conflict or failed check in sluice's record, a withdrawal or an outcome crew can't tell, which keeps its row's box and the user's word, its row and its rail line saying what stopped it at that head and that main-level ops submits it again once that is cleared, which ops does with the same `crew bolt submit` on that word, with no new word of the user's, an answered landings card left as it is while it is stopped, a card that follows naming it as still landing with what stopped it, and `crew card read land/<kit>` printing the stop beside the command that lands it; sluice forms the landing on GitHub's main and pushes it with a lease, so nothing is refused for the host's own main lagging GitHub's, and whatever sluice warns of stops nothing. A landing pushes nothing and levels no host's checkout, its one write on the host the level of its copy of the bolt's branch above: every kit's main checkout is an anchor at GitHub's main that the fleet's timer moves within minutes, which crew never moves, and one still on branch `main` is brought level only until the timer reaches it, crew saying nothing of a detached one. A bolt no team holds, built outside a team, lands the same way on the user's word once main holds each of its units' changes and chores, read on the host of a team of the partition building that kit, with nothing to merge; its entry in the run record names the kit and the commit GitHub's main holds afterwards, read after a fetch (`Repo` and `Head`), from which a deploy's view tells the bolts it carried, and, for a bolt a team held, its age in whole minutes from its newest give to sluice's landing of it (`Age`) and those minutes by holder, as its head line on the board splits them (`Split`, `team 200, kit 12, team-or-kit 13, user 125, hold 0, nobody 20`, team-or-kit a submission's stay crew can't split between queued and under test), read once from sluice's record on the team's host, or neither when that or the give can't be read, the landing going on. A landing that conflicts with main, or fails main's checks, lands nothing and moves nothing: main-level ops passes sluice's words to the bolt's conductor, and the team takes main into the bolt by a fix submitted to it (see Teams). In a kit whose sluice policy at main takes pull requests into main, as crew's does, a landing's pull request from `bolt/<bolt>` is live only on the user's word, since sluice takes an open pull request out of draft back into main's queue whenever its branch moves: `crew bolt submit` readies each bolt's draft pull request before it submits it, submitting nothing of that bolt when it can't, and a landing that does not land leaves it a draft, said with its link, which a fix's start and every unit's, chore's or fix's merge into the bolt keep, each drafting it first, a merge that can't not starting, so only the next `crew bolt submit`, on the user's word, makes it live again; crew reads and marks it with `gh` on the team's host, and asks nothing of GitHub in a kit whose main takes no pull requests. Either way the bolt's branch and worktrees then go from its team's host (see Teams), and a landing whose worktree is kept, for uncommitted changes or a remove hook, still lands.

A kit's main that fails its checks after a landing is fixed by a fix on main, not a reopened bolt. Where a team builds the kit in a Flume stream, `crew main fix <kit> <name> "<the failure's words>"`, main-level ops's or the user's on reading main red, appends a launch of a Flume fix place on main, `main--<name>` (`fix/main/<kit>/<name>` in the run record), its brief the failure's words, its submission held for the user's word, main-level ops its recipient, ahead of every bolt, on the kit's host: the one host the teams that build it in a stream run on, or the partition's main-level host among several, and refused, naming them, where none is. Once its code has delivered and its submission waits held, the kit's landings row on the rail carries it, `fix main--<name>` with the failure's first line, beside the bolts that wait, and the user's send of that row is ops's word for it as for a landing: `crew main fix <kit> <name> --send`, with `--excerpt "<the user's words>"` for words in ops's pane, read in ops's own transcript as `crew bolt submit` reads them, appends the retry of its submission, once; the runner submits it, sluice lands it on main and the row leaves. `--drop` drops it, one landed refused. Where no team builds the kit in a stream, or no runner answers on its host, it is refused, naming the way until then: a bolt of one chore, proposed first among the planned.

## Proposals

```
crew plan propose <file> [--replaces <n>]
crew plan proposed [<n>] [--label L] [--json] [--open]
crew plan approve <n> [--clear <unit>...]
crew plan answer <n> <question> <answer>... [--note "<text>"]
crew plan drop <n> "<reason>"
```

The planner changes the plan only by a **proposal** the user approves: where new work goes (a new bolt, a unit in a bolt, the queue), and every move, split, amendment, reorder or drop. A proposal is a record in `proposals.rec` on the flywheel's branch: the planner's `Case`, and the plan commands it would run, in order, one `Do` each, as typed without the leading `crew` (`bolt new|order|drop`, `unit add|amend|move|split|order|after|drop`, `chore add|move|order|after|drop`). Proposals are numbered, and never removed or changed.

- `crew plan propose <file>` takes a file of one record, a `Case` and its `Do` lines. Each command is checked in order against the plan as the ones before it leave it, with every refusal it has run directly; a refused command refuses the proposal and nothing is written. A proposal is also refused, with nothing written and no card raised, when a bolt it creates, or a unit or chore it adds or moves into a bolt, names as a source a decision record (`docs/adr/<number>`, of its kit, or of the repository written before it as `<owner>/<name>:`) that its main on GitHub does not hold accepted, naming each record and what main holds: proposed, rejected, accepted with an amendment still marked proposed, no status, or no such record. It waits on the user alone, and no agent is told of it. `--replaces <n>` drops proposal n and writes its successor in one commit. Once the proposal is written, crew raises its Pending You card itself, in the planner's name, keyed `proposal/<n>` of the first proposal of its chain (the one each `--replaces` follows back to), and prints the line the planner adopts it with; a rewrite changes the chain's one card, "Rewritten as proposal <n> after your note", in place while it waits on the user, and once the user's note answered it, by acking it with that note and posting the new version following it; a card whose rows fill more than one list asks them as questions, which Pending You never changes in place, so a rewrite withdraws it with the note while it waits and posts the new version following it, as does a rewrite that moves the card to another form, a hold-to-approve, a choice, one list or lists; the rail's row for the successor carries the chain's key. A proposal the user writes has no card. The card asks only the units and chores the proposal makes new to a bolt or the queue, in one checkbox list, each a box ticked as proposed, which the user clears to leave it out; what else it changes, a drop, an amendment, a move, an order or a new bolt, is drawn on its face and applies with it, as its summary says. A lone new unit is the choice of its two sides, and a proposal with none a hold-to-approve, which the user declines with a note to keep what it drops or amends. A card Pending You refuses refuses nothing of the proposal.
- `crew plan proposed` lists the open proposals and what each waits on; `crew plan proposed <n>` prints one as markdown: the case, then each change in plain words, a unit's intent beside what it rests on (a signal's assertion and excerpt) and the goal and team of the bolt it would join, and an amended unit's bolt, team and stage, its intent as it stands and as proposed, and what approval sets in motion; under each change, the command approval runs; and, for an open proposal, who it waits on, in words. It reads only the branch, so any host can answer. With `--open`, it writes that page to `~/.local/state/crew/proposals/<label>-<n>.md` on the host it runs on and opens it in plannotator, for the user to read and annotate: beside the caller in herdr, inline in the terminal otherwise.
- `crew plan approve <n>` applies the proposal's commands, as read, to the plan at the tip and closes the proposal, in one commit, or changes nothing when one no longer applies. A unit or chore with a worktree that moves is rebased before the push and put back if the approval is refused. With `--clear <unit>...` it leaves out the new units and chores the user cleared and every command that concerns only one of them, so a cleared unit is never made and one moved in from the queue or another bolt stays where it was; it refuses, changing nothing, a cleared unit the proposal does not make new to a bolt, and a command left in that names a cleared unit, for the planner to write the proposal again; and it records each as `Cleared` on the proposal. The user runs it, or an agent on the user's word. crew then closes the proposal's card with what was applied and what was left out, and tells the planner the same when someone else approved it.
- `crew plan answer <n> <question> <answer>...` records one answer of open proposal n's card, as the planner reads it: `rows-<k>` and the ids of the boxes the user left ticked (`rows-1` for a card of one list, and for a lone new unit the side picked), or, for a hold-to-approve, `plan approve` or `plan decline`, with `--note` for the user's note. It checks the answer against the card crew builds for the proposal, refuses an answer that differs from one it holds, and keeps the answers in `~/.local/state/crew/cards/<label>/proposal/<n>/answers.json` on the host it runs on, the planner's, never on the branch. Once it holds every question's answer, it applies the change with the boxes as they stand, as `crew plan approve` does: a new unit unticked left out, as `--clear` leaves it, and recorded as `Cleared`; and it prints the note as the user's word for the planner's next proposal. A decline applies nothing. Either way the answers go.
- `crew plan drop <n> "<reason>"` closes a proposal unapplied, with the reason, and crew withdraws its card with it, or, once the user answered the card, closes it as dropped on their note, since their note may ask them something, which Pending You refuses as a close's outcome.

Work a bolt in flight needs before it can be proven or land goes into that bolt: a `unit add` or `unit move` marked `--unblocks <bolt>` must place the unit in that held bolt, where it goes ahead of the first unit not yet merged, and the mark is shown on the proposal.

Who writes the plan directly, when the command runs as an agent crew started (`CREW_AGENT`):

| Agent | Writes directly | Otherwise |
|---|---|---|
| the user at a shell | everything | |
| `<label>-planner` | proposals | refused, naming `crew plan propose` |
| `<label>-design` | `unit add … --repo <kit>` and `chore add … --repo <kit>`, the queue | refused, naming the planner |
| `<label>-ops` | `bolt land` | refused, naming the planner |
| any other agent | nothing | refused, naming the planner |

`crew bolt start` is the user's alone outside a proposal, which the planner proposes and the user approves; any agent running it is refused, naming the planner and the user. A proposal waits on the user alone.

The three commands that write a runner's requests rather than the plan, the user's at a shell, are refused from any agent but these: `crew answer`, the planner's, the design agent's and main-level ops's; `crew fix` on a started bolt, the planner's and main-level ops's; and `crew main fix`, main-level ops's. A request's `By` names who ran it.

Every refusal is a run-record entry. Writing, approving and dropping a proposal are entries naming `proposal/<n>`, and each change an approval applies is an entry of its own, from the proposal, with the approval's commit; `crew trace` follows them.

## State

```
crew state init <label>
```

A partition's **flywheel** is its loop, named by its label. Its state is the files on one branch, `<label>/main`, of the state repository the teams file names for it (`state`, one per organisation, such as `WilldanGroup/crew-state`), apart from the design:

- `plan.rec`, the plan;
- `moves.rec`, every signal's one move;
- `proposals.rec`, the planner's proposals;
- `signals/<capture>/`, the captures and signals recorded through crew (see Signals);
- `runs/<host>/<YYYY-MM-DD>.rec`, the run record, each entry pushed by the host that wrote it as it is written;
- `requests.rec`, crew's requests of each host's runner for a team's work (see Teams) and a role's run's work that lands (`crew role land`): a launch of a Flume place, a retry with words, a drop or a priority, numbered from 1, each appended in the commit of the plan write that occasions it, recfix-checked with crew's own rules, and never changed or removed;
- `asks.rec`, what waits on each main-level role that runs as its kind (see The main level and the console): an **Ask** for each thing that names the role, numbered from 1, with `Role`, `From`, `What` (`tell`, `send`, `capture`, `landed`, `card`, `open`, `batch` or `delivered`), the record it `Names`, the `Key` it is written once for, its `Words` and `At`; and a **Turn** for each start of a role's run that took something, numbered from 1, with the run, its place and host, a `Took` for each ask or waiting place it took, `Began`, and `Ended` with what the run `Said` it did, or `Superseded` by the turn that took its asks again;
- `roles.rec`, one **Role** record for each role a partition runs as its kind, written to match the teams file by `crew main up` and in the commit of any ask whose role's record is missing or differs: its `Address` (`<label>/<role>`), `Run`, `Host`, `Repository` (the partition's first blueprints repo), `Kinds`, `Kind` (`crew-<role>`), `Name`, `Stream`, `Priority`, `Intent`, `Model` and `Effort`, from which each host's runner launches the role's run.

Each host's runner answers on a branch of its own in the same repository, `<label>/runner/<host>`, which only that runner writes and crew never does: `runner.rec`, naming the host, the runner's version and since when it serves the partition, so a branch that exists says a runner answers there; `answers.rec`, its answer to each request it has read, `held` while a launch waits on its `After`, `launched`, `done` or `refused`, with the place's path and Flume's or its own words; and `places.rec`, Flume's status of each place it launched as `flume status --json` gives it, kept after Flume tidies the place until its work has left the plan, and a `Run` for each role's run, keyed by the role's address, `<label>/<role>`, with its place and status, or the runner's words where it could launch none, which `crew role open`, `crew main status` and the board read. crew fetches `<label>/runner/*` in the same fetch as `<label>/main`, into the same cache, and reads each host's three files at the tip it fetched; a host whose branch is missing, or whose files recfix refuses, hides only that host's work, which reads `unknown`, named.

Flywheels sharing a repository never meet: each command fetches and pushes only its own flywheel's branch, and no branch shares history with another. A write that changes several files is one commit, and its message ends with a `Crew-Entry:` trailer naming the run-record entry that describes it; that entry follows it as a commit of its own, changing its day's file under `runs/<host>/` alone and naming the entry it adds. `crew state init <label>` creates the branch: it adopts the first blueprints repo's `plan/<label>` with its history where there is one, joins another blueprints repo's `plan/<label>` in one commit naming where it came from, and copies the first blueprints repo's `signals/moves.rec`; run again, it finishes what a stopped run left, or says the branch exists. A clone of the branch reads with `recsel` and nothing else.

## Signals

```
crew signal <slug> "<what it asserts>" --excerpt "<the words, verbatim>"|--excerpt-file <path> [--kind K] [--subject a,b]
crew signal show <id>
crew signal move <id> attach|challenge|new-territory|answered|drop [--target T] [--reason R]
crew signal land <capture-dir> [--label L]
```

A **signal** is one thing noticed, with the words that show it, in the shape the blueprints' `signals/README.md` gives: a directory per capture, holding `capture.md` and one file per signal. Signals have two homes. What the agents and the user record with `crew signal` is under `signals/` on the flywheel's branch of its state repository; what the daily pass reads from meetings and channels stays under `signals/` in the partition's first blueprints repo. An id is unique across both, and every command looks it up on the flywheel's branch first.

An agent crew started gives an **excerpt**: the words that show the finding, copied as its session received them, from the user or from a tool's output (`--excerpt-file` for words the shell would mangle). crew looks for them, whitespace aside, in the agent's own Claude transcript, `~/.claude*/projects/*/<session>.jsonl` for the session herdr names for the agent, and records a grade on the capture:

- `verified`: the words are in a record the session received, and the capture says who asserted them: `user`; `tool`, for a command's output; `agent:<name>`, for what another agent sent with `crew tell`; or `crew`, for crew's own notice;
- `found`: they are in the transcript, in a record crew cannot classify;
- `unverified`: crew could not read the transcript, and the capture says why: herdr names no session, there is no file, its lines are not JSON, or it has not been written for 15 minutes, so crew may be reading another session's.

A signal is refused only when the transcript is the live session's, its last record written within 15 minutes, and the words are nowhere in it but in what the agent wrote itself: a paraphrase. The refusal says so, and names the other way words a tool printed can be missing: a background task's output reaches the transcript only once the agent has read the output file its task notification names, so the agent reads that file and records the signal again. A change in Claude Code's format lowers a grade and never stops a capture, and no command refuses anything for its grade; the grade is shown wherever the excerpt is.

A capture is the one record the excerpt came from. Its `capture.md` names the host, the Claude session, the record and its time, who asserted it, and where the agent was working: its team, the bolt the team holds and the unit its slot holds, or the main level. The record itself is copied to `~/.local/state/crew/<label>/raw/<capture>.jsonl` on the host, and the capture points at it as `<host>:<path>`; of the source, only the excerpt enters git. A second signal from the same record joins its capture as its next signal, and the same signal again writes nothing. The capture and its signal are one commit on the flywheel's branch. The user's own note, `crew signal` at a shell, is its own excerpt (`excerpt: own`), of kind `ask` unless another is given.

A program records its own captures, a kit's deployer one per failed deploy, an adapter watching the tools the fleet pins one per newer upstream version, and hands each to crew with `crew signal land <capture-dir> --label L`, run as the program (`CREW_AGENT`) on the host that ran it. The folder holds `capture.md` and its signals, `NN-<slug>.md`, and nothing else; the capture names itself, the program as its `source`, who captured it, its event's date and its raw record, `<host>:<path>`, which must be on that host, since only the excerpt enters git; it is read, and counts its signals, at least one, made by the program with no model between: the capture is its own excerpt. Each signal names itself, its kind and who asserted it, says what it asserts, quotes its excerpt, and is no larger than 8 KiB, the program cutting its excerpt to fit and keeping the whole in the raw record. A capture whose name is not crew's kind of name, lowercase words, digits and dashes, is refused. crew lands the folder whole on the flywheel's branch in one commit, as a `capture` entry naming each signal; files the branch holds already are passed over, the same capture again prints that it is already landed and writes nothing, and a capture or signal there that differs is refused, since neither is ever changed. A program never writes a blueprints repo, and `crew signal land --help`'s first line is its usage, which a program reads to know this crew takes captures.

`crew signal show <id>` prints a signal, its capture's fields (the grade, who captured it, where and when, the session and the raw record) and its move, from any host. Every command that takes a signal's id, `show`, `move`, `--signal` and `crew trace signals/<id>` among them, takes its full id, `<capture>/<NN>-<slug>`, or its short one, `<capture>/<NN>`, which names the one signal of that capture numbered NN. Curation's moves, `crew signal move`, are appended to `moves.rec` on the flywheel's branch, and a signal becomes work only through its `route` move, which `crew unit add --signal` writes in the same commit as the unit, and `crew chore add --signal` with the chore. Each signal has one move, and nothing is ever merged.

What crew sends an agent is marked as crew's: `crew tell` sends `[crew tell from <sender>] <text>`, the sender being the agent or `<user>@<host>`, and crew's greetings and notices send `[crew] <text>`, so neither is taken for the user's typing. A word the user sends from a dock of the board reaches its item's agent through `crew tell --board`, which reads the word as the board's listener posts it, `{"label", "key", "to", "text"}` on its standard input, refuses one that is not of that form, names no partition crew knows, is on a key of no dock's kind, is for an agent its item's kind does not go to in that partition, or is empty, over 1000 characters or more than one line, and sends `[crew tell from <user>@board] (on <kind> <name>) <text>`, `<user>` being whom the listener runs as, printing `sent to <agent>`; a tell it can't make types nothing and says why in the tell's own words. It is recorded as any tell, with its length and never its text. A tell from `<user>@board` is the user's word on the item it names, and a signal captured from it is the user's, but it answers nothing: crew never takes words that reached an agent only from the board as the user's word to land a bolt, answer a batch or settle a record in a pane, saying the words came from the board and where the user answers instead, and the same words typed in the pane, or told from the user's shell, still count. Every brief says so beside its roster.

## Operations

```
crew ops offer <env> --label L --to <sha> --from <sha|none> [--notes <file>] [--steps <file>]
crew ops approve <env> --label L --to <sha>
crew ops word|quiet <env> --label L
crew ops record <env> --label L --to <sha> --act start|step|end [--from F] [--step S] [--outcome O] [--log P] [--rows F]
crew ops step <env> --label L --key K --state waiting|handed|done|failed|declined [--to <sha>] [--doer D] [--agent A] [--when W] [--held] [--text F] [--changes C] [--note N]
crew ops steps <env> --label L --json
```

The operations on a partition's environments, a deploy being one kind. A landing deploys nothing; a kit's deployer, or a hosted CI/CD in its place, deploys main under each environment's policy (ADR 0012, `plan.14`), and these are what it asks of crew, each run where the partition's main level runs, as the one asking, on that host's run record (`ops.*` entries on `env/<env>`); an offer run on another host carries its files' text there. `offer` makes a `manual` environment's deploy of a commit a row under *operations* on the rail, keyed `deploy/<env>`, and crew raises its card in main-level ops's name, telling ops the line that adopts it: on its face the kit's notes for the range from the environment's last deployed commit, as the kit's changelog tool wrote them and the deployer hands them with `--notes <file>`, and the range's after-deploy steps with their doers, one a line as the deployer gathers them (`step <n> <doer> <when> <environments> <why> <text>`, tab-separated, `held` among the when words), with `--steps <file>`; handed no notes, the landings the range carries: the first-parent commits of the kit's main from the environment's last deployed commit to the offered one, read with git where the main level runs, a landing of sluice's by the subject of the branch it merged and one the run record holds by its bolt, or what git could not read. crew writes none of the notes, keeps the files beside the offer on its host and none of their text in the run record, and refuses a file it can't read, offering nothing. The card follows the environment's last deploy card when the user declined it, and otherwise no card: never a landings card, whose landings the deploy carries on its face. The same offer again writes nothing, and posts the deploy's card again when main-level ops holds none open, as when Pending You refused it; handed other notes or steps, it changes its card in place; a newer one replaces it and changes its one card in place. The user's word is holding that card, recorded with `approve` for the commit the row shows, and refused for any other; `word` prints the commit a word was given for, or exits 1 when there is none, and a word is for one deploy: once its end is recorded, there is none until the next approval. `record` puts a deploy's start, each of its steps (the machine, the guests, the suite and its rows) and its end in the run record as it runs; its end closes the deploy's card with each step's outcome, or the step that failed and its log. Every other operation, a command after a deploy, a restart, a check, is a `step`, recorded with its state, its doer, the agent it was handed to and its text, after the deploy it names with `--to` or on its own; one whose doer is the user, or an agent's marked `--held` for the user's word, waits as a rail row, `op/<env>/<n>`, until it is marked done or declined, and `steps` gives each step's latest state as JSON. crew raises such a step's card in main-level ops's name, one at a time on an environment, each following the one before: the user's a `do` with the step's words and, from its text's `- why:`, `- where:`, `- command:` and `- done:` lines, why, where, each command whole and what is seen when it worked; a held one a choice of now, when the host is quiet, or skip. Recorded again while its own card is open, the step changes that card in place when its words, its doer or its hold differ, a change of doer between the user and an agent withdrawing the card and posting the new one following it, since Pending You changes no card's kind, and the command prints the line that adopts the card either way; only another step's open card holds a step's card back. It closes the card when the step is marked done or declined, and raises the next. A step an agent runs on its own has no card. `quiet` exits 0 when no stage agent of a team on the environment's host is working and no test of crew's runs there, and 1 saying what does.

Each partition has a main level in the session the teams file names: the **design agent** (elaboration on main and curation of signals), the **planner** (the only writer of bolts and placements, and the poster of the partition's review batches), the **reviewer** (started fresh for each batch, in a `review` tab, and ended once its summary is written) and the main-level **ops** (lands the bolts whose verification is green by one procedure, their submission to main through sluice in order, on the user's send on their kit's landings card, and deploys a kit with no deployer only on the user's word for that deploy), as tabs of the `<label>` workspace; and a **dispatcher** on each host the partition's teams run on, in `<label> dispatch`, which gives that host's teams their bolts. The **operator**, `<label>-operator`, is the main level's fourth role and the partition's one door (record 0035): it works for the user, and every wait with no card is told to it. A main-level role runs in the main level's session unless its partition's `roles` names another of the machine's sessions for it, `roles.planner.session`, so a partition's design agent and planner, both Fable, can sit on two Claude accounts; `crew main up` opens a `<label>` workspace in each, and refuses while a role's agent still runs in a session it no longer stands in, which `crew main down` ends. The **console** is the `console` workspace of each host's operator session (the session named `<label>`), opened by `crew console up <label>` and closed by `crew console down <label>`, with no agent in it. It opens with a `shell` tab alone, a shell with crew on its path, and opens its `flow`, `rail` and `board` tabs only when they are named after the label, in any order, `crew console up <label> rail`; another word is refused, naming the three. The rail tab opens of itself too while no host job runs the host's follower, since its loop is then the follower. Every later `crew console up` keeps each tab already open, named or not, and a tab the user closed stays closed unless it is named again. `crew operator up <label>`, its name before record 0035, opens it too, with no tab named, and ends the operator agent a host's console held before, once it is not working, closing the panes crew recorded beside it. Each agent `crew main up` starts is greeted once it is up, as a conductor is, marked `[crew]`: told to read where the partition stands and carry on with what is its role's; one that was already up is neither started nor greeted. `crew tell` prompts any of these agents by name, wherever it runs, marked with who sent it. Anything for another team or partition goes with `crew send <team or partition> "<text>"`, to that partition's operator, its one door, wherever it runs: a team by the partition it belongs to, a partition by its label. The operator is told `[crew tell from <sender>] (sent to <team or partition>) <text>` and carries it on to the agent whose job it is, in the sender's words, and the send is one `send` entry in that partition's run record, with its length and never its text. A name that is no team or partition is refused, naming each, and so is the operator's own send to its partition, which it carries on with `crew tell`; every brief says beside its roster that this is the one way. A tell to an agent waiting on a question in its pane fails with nothing typed, and says to send it again once the question is answered, whether herdr sees the question or crew's PreToolUse hook marked it when the agent opened a question or a plan for the user; the mark counts until the agent's transcript holds the answer. When herdr names no Claude session for the agent's pane, as after herdr's own restore resumed it, crew reads the session it recorded of that agent starting in that pane, and with neither, herdr's reading of the pane alone guards the tell. crew's greetings and notices go the same way. A greeting is also read back as a stage's prompt is: sent once the agent is ready, cleared and sent once more when its transcript does not show it, and when the second is not taken either, nothing is left typed, no greeting is recorded, and crew says the agent was not greeted, with the `crew tell` that would greet it.

A main-level role may instead **run as its kind**, one role at a time, on the user's word, by its partition's `flume` in the teams file: version 4 names it on every partition, an object naming each of its five roles, `design`, `planner`, `reviewer`, `ops` and `operator`, `false` while the role stands as above or the Flume stream its runs run in on the main level's host, and crew refuses a version-4 file whose partition lacks it, leaves a role out, names another key or gives a role anything else, naming the partition, the role and swancloud's `lib/crew-teams.nix`; in a file at version 2 or 3 every role stands. ### Holding a host, and updates

`crew hold <host>|--all "<why>"` puts on the brakes before herdr is upgraded or a host rebooted. crew starts no agent on a held host until `crew go`, and refuses every command that would, saying who held it and why. Every standing agent up there is told to finish the step it is in and start nothing new, and a stage already running ends as it would. `crew hold status` says what still works on each host: an agent working, one waiting on a question to you, one running background work of its own, a stage not yet ended, crew's tests. `crew hold wait` waits until each host is quiet and then ends every crew agent there, keeping its panes, so herdr's restart brings back only shells; `--now` ends them at once. `crew go` lifts the hold, brings each standing agent back with its conversation through crew, greeted, tells one still up to carry on, and runs each console's tabs again.

crew's code is live on every call, but an agent takes its brief and crew's plugin (its hooks, skills and this band) once, at its start. Each start records the crew it loaded and what it was started with, and a landing or a teams file that changes either makes the standing agents it touches due a restart: crew restarts each at its next stop, once its turn has ended with no question open and nothing of its own running in the background but crew's waits. A conductor starts fresh; every other standing role resumes its conversation and is told what changed. crew's Stop hook catches an agent at the end of its turn, the host's follower catches one sitting idle when crew's checkout or the teams file moves, and `crew update` does it by hand. Nothing restarts on a held host. Each agent's band shows the crew it started on, and once it is due the version it takes at its next stop.

Every crew command that moves work appends one entry per act, after the act, to the **run record** of the partition it acts for, on the host where it ran: `~/.local/state/crew/<label>/runs/<host>/<YYYY-MM-DD>.rec`, one recutils file per UTC day, each entry one write, never rewritten. An entry holds:

- `Id`, `At` (UTC) and `Host`, where crew ran;
- `By`, the agent crew started that asked (`CREW_AGENT`), or `<user>@<host>`, and `Session`, that agent's Claude session as `<host>:<id>`, carried with a command crew runs again on another host;
- `Act`, such as `unit.add`, `bolt.give`, `stage.start`, `stage.end`, `tell`, `team.up` or `agent.restart`; `forecast`, `amendment` and `unit.rebase`, what reached a unit from another; `batch.due`, `review.start`, `review.batch` and `batch.close`, a partition's review batches and crew's close of one that waits on nothing; the card acts, `card.post`, `card.update` and `card.close`, which crew's hook writes for an agent's card and crew for its own, and `card.reading`, a try of a batch's, a long proposal's or a landing's reading after its card was raised, done or refused; `team.cross`, a team's crossing to Flume in an older crew, its `State` the stream its work ran in, which crew no longer writes, and `stage.answer`, `crew answer`'s retry of a Flume place; `ask`, an ask of a role that runs as its kind, on its run and the record it names, `turn.begin` and `turn.end`, a run's start and end, and `role.land`, a run's launch of work that lands, on `role/<role>/<name>` and the run;
- `On`, each object acted on, and `From`, each object it came from, as typed names: `unit/<unit>`, `chore/<chore>`, `bolt/<bolt>`, `queue/<kit>`, `signals/<id>`, `team/<team>`, `agent/<name>`, `stage/<unit or chore>/<stage>`, `stage/<bolt>/proof`, `fix/<bolt>/<name>`, `fix/main/<kit>/<name>`, `role/<role>/<name>`, `batch/<n>`;
- `Commit`, `<owner>/<name>@<sha>`, when the act wrote one, and `Why`, the subject crew composed from the names of things;
- `Refused`, crew's reason, when a command that would have moved work was refused;
- a stage's end's `Result` (the stage the unit reached), `Tasks`, `Head` (the unit's or fix's branch head), `Ended` (`delivered`; `short`, when its agent said what it needs through crew; or `stopped`, when crew ended its agent first), `Delivered`, what it delivered as an object (`unit/<unit>@<head>`, `chore/<chore>@<head>`, `fix/<bolt>/<name>@<head>`, `bolt/<bolt>@<head>` or `report/<file>`, and `proof/<file>` in an entry from before a bolt's proof was its verification), and `Observed: late` when nobody waited for it, a tell's and an ask's `Chars`, a `turn.begin`'s `Took`, how many asks and waiting places it took, `Amended: yes` on the start of a construct that marked its unit amended, whose `Commit` is the plan's, and `Took`, the heads of the units it comes after that a construct's new place took; a forecast's `Heads` (`<unit>@<sha> <other>@<sha>`), its conflicting `Paths` and how it `Reached` the later unit (`told`, `prompt` or `settle`), and a stage start's `Forecast`, the forecasts its prompt carried; on crew's own `unit.after` that orders two units a forecast found in conflict, `After`, the unit it now comes after, or `Lifted`, the one it no longer does, and `Settle`, the settle end that decided it; a review batch's `Batch` and `Units` (each `<unit>:<team>@<commit>`), and a batch due's `Count`; and a card act's `Card` (the Pending You card's id), `Key` (its rail row's card key, or its record key) and `Unread` (why its reading could not open, crew's own message, on the post or change of a card raised without it), on the row's object, on `record/<kit>/<number>` for a decision record's card, or on `agent/<name>` for a card with neither key.

No entry holds text anyone typed: not a tell's text, what a stage's agent said it needs, an intent, a goal, a reason or an excerpt. A read writes nothing, and a record that can't be written is said on standard error and changes nothing about the command. `recsel -t Entry` reads the files with no crew involved.

Every entry reaches the flywheel's branch as it is written: the command that appended it pushes it to `runs/<host>/<YYYY-MM-DD>.rec` there before it goes on, as a commit of its own from that host, by the one write every state write takes, its subject `runs(<host>): <act> <first object> (<agent>)` and its `Crew-Entry:` trailer naming it. Each day's file on the branch is the union by `Id` of what it had and what the host has, so a host only ever adds to its own files, and one that is asleep or rebuilt loses nothing it pushed. When the push can't be made, GitHub out of reach, the branch not started or a file of the host's failing `recfix --check`, the command says so once on standard error and does what it would have done; the entry waits in the host's file, and the host's next entry pushes it first, each still a commit of its own. `crew events --push` pushes by hand what a refused push left, or says nothing is left. `crew events` reads the run record from the partition's branch alone and prints it in time order, asking no host for it, so a host that is asleep hides nothing it pushed; it names the branch when that can't be read. `--follow` reads the branch as this host's cache holds it, again whenever its tip moves, reading only the files that changed, and prints each entry once it is there: a write on this host moves the cache at once, and the branch is fetched once a minute, by the host's follower, or by the follow itself for a partition no follower on the host follows, so another host's entry shows within the minute. The console's `flow` tab runs it. `crew trace <object>` prints one bolt's, unit's, chore's or signal's history from the entries alone, and `crew trace agent/<label>-<role>` a role's asks and turns: what was done, by whom, with which commit, what it came from and what came from it, each line with the `zoe <session>` to open on its host. A bare name is tried as a unit, then a chore, then a bolt, then a signal; `report/<file>` and `proof/<file>` find the end that delivered them. crew writes no stage's start or end and frees no slot: a stage's start and end are Flume's, read from the runner's records, and the `stage.start`, `stage.end` and `slot.free` entries an older crew wrote are read and printed as written.

`crew page <label>` writes the partition's page, one HTML file that opens on its board: the four lanes `crew board` reads, Inception, Bolt plan, Construction and Operation, made by the same read at the same commit of `<label>/main` as the rest of the page, and drawn as the flywheel mockup's phases view draws them: a signal as a quote under who captured it, a proposal as a sheet, a queued unit as a slip, a bolt as a ledger with its units as a chain, a landed bolt as a record, and every rail row a ✓ marker on its object, saying whether its card is open and who asked it, or that it has no card, its post refused, Pending You's words shown when the marker is pointed at. ## Needs

`herdr`, `jq`, `python3`, `git`, and `recutils` for the plan; in each kit `wt`, `sluice` with its `wt-submit`, which worktrunk runs as `wt submit`, and `openspec`; `devurl` and `portless` for `crew sites`. crew's own toolchain is devenv's system tools, `jq`, `recutils`, `proto` and `git-cliff`, with convco for the commit-msg hook entering the shell installs, and the application tools `.prototools` pins, which entering the shell installs when one is missing, and activates: `moon`, and Python at the minor every host runs crew on, with `uv`; the tiers' `venv` task syncs pytest from `tests/uv.lock` into `tests/.venv` before every run of them, with the uv moon's toolchain gives, since moon's own install is skipped under `--force`, as sluice runs.

`tests/run [name...]` runs crew's tests one after another on stub `herdr`, `ssh`, `claude` and `wt submit`, each simulated host with its own scratch home, so no test reaches a real session, host or agent. `tests/suite` runs them as moon tasks, one per test file, each running its test through `tests/run`, side by side; a test whose inputs are identical to a run that passed on the host, in any worktree of crew, is replayed rather than run again. `tests/suite --affected` runs only the tests a change affects, against the merge-base with `main` and counting uncommitted edits, `tests/suite <name>...` the ones named, and `tests/suite --force` runs without replaying. An agent runs the tests that prove what it changes by name while it works and `--affected` once before its merge, never the whole suite by hand: sluice runs every `check-full` task afresh on each submission to a bolt and to main, as crew's `.config/sluice.toml` requires. Every test waits for one of the host's test slots (`tests/slot`), its cores less two unless `CREW_TEST_SLOTS` says otherwise, shared by every worktree on the host. The tasks are `tests/moon.yml`, written by `tests/moon-tasks` from the test files with each task's inputs: crew's command core (`plugin/bin/` and the modules `plan.py` and `crew.py` import) and the common files, and whatever else the test's outcome depends on, named on a `# Reads:` line of its opening comment; after adding or removing a test, or changing what one reads, run `tests/moon-tasks` and commit `tests/moon.yml`, since `tests/suite` refuses to run while they are out of step. Both run in crew's devenv shell, and enter it themselves when started outside it; crew's other tools run through it per command, `devenv shell -- <command>`, and a terminal enters it with `devenv shell`, or direnv with the checkout's `.envrc`. crew's mod has its own cases, `plugin/tests/*.test.ts`, run as the task `mod` by `tests/mod`, which runs them with `claude plugin test plugin`: Claude Code's test kit, with no session, model, sign-in or network. `claude plugin test` takes no option before `plugin`, so where `claude` is a wrapper that adds its own, `tests/mod` runs the program the wrapper's last `exec` names, once it answers `--version` as Claude Code; `CREW_TEST_CLAUDE` names another. The live `crew sites` check on mac-studio is no task: `CREW_TEST_LIVE=1 tests/run sites-live` runs it.
