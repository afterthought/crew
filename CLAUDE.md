# crew

crew keeps each partition's plan of bolts, runs its main level of Claude agents in herdr, and reads its bolts' work as Flume runs it. `README.md` says how it works; `openspec/` holds its changes, and the partition's plan their order.

## Rules

The rules every change holds to are in `docs/architecture/`: `core.md`, imported below, binds all of crew, and an area's page beside it binds that area, loaded when a file under its paths is read. A design or commit that relies on a rule cites its id (`state.1`); one that departs from a rule says which and why. Where `docs/architecture/` and README or a spec disagree, `docs/architecture/` wins. The reasoning behind a rule is in `docs/adr/`.

## Crew

What an agent building crew needs to know. **The record**, in this order: `docs/architecture/` (the rules), `docs/adr/` (the reasoning), `openspec/specs/` (what each capability does), `README.md` and this file (the how-to), `openspec/explorations/` (readings and explorations, each saying so in its first line). **Where design is written**: a rule goes in `docs/architecture/core.md` if it binds all of crew, else on its area's page, with an id (`<area>.<n>`, the next free number in its area), one sentence, what it rules out and its source, amended in the same commit as the decision that changes it; a decision's reasoning is a record in `docs/adr/` (`adrs new`); how a capability behaves is its spec, changed only by a delta in the change that builds it. **What each agent sees**: crew's mod (`plugin/hooks/status.js`) draws the planner's, the design agent's, main-level ops's and each operator's slice of the board above its prompt, from `board.agent_views`; a change to what crew models (bolts, units, stages, proposals, explorations and elaborations, cards, rail rows) updates both in the same change, with their cases (`code.8`).

## How crew reaches a host

On every host, crew's `crew/main` is an anchor: detached at GitHub's main, moved only by swancloud's timer, and never worked in, committed in or put on a branch, by an agent, crew or the user (`plan.18`). mac-studio's is `~/Code/github_afterthought/crew/main`, the box's `/workspace/crew/main`. A host loads crew, the `crew` command and the plugin every Claude session loads, in one of two modes swancloud sets for it (`plan.19`, record 0032): **live**, from `crew/live/plugin`, where `crew/live` is a detached worktree beside `crew/main` at GitHub's main that the same timer moves, so a landing is live there minutes after it lands; or **released**, at the version swancloud pins from crew's release tags (`code.10`), so a landing reaches the host only once swancloud's bump to that tag is deployed. No host loads crew from a checkout on branch `main`. So work is built in a worktree of its own, cut from `origin/main`, and a bolt lands only on the user's word, through sluice. `main` moves only through sluice (`state.3`): a commit of anyone's, the user's own and the design agent's records among them, is made on a branch cut from `origin/main` in a worktree of its own, and submitted with `wt submit main` from there. Nothing levels a checkout after: the timer moves every anchor.

## Tests

- crew's shell is devenv (`devenv.nix`): its system tools, proto among them, and the application tools crew's `.prototools` pins (moon, Python 3.13, the hosts' minor, and uv), which entering the shell installs into crew's own proto home in the git common dir when one is missing, and activates (`code.1`). No session is entered into it at its start (`tests.7`, record 0024): run crew's application tools through it per command, `devenv shell -- <command>` from the checkout, such as `devenv shell -- moon run tests:logic`. Each run reads the shell as the checkout's files stand, so an edit to `devenv.nix` or `.prototools`, or a rebase that changes them, reaches the next command; a warm entry costs about a third of a second. `tests/suite` and `tests/run` enter the shell themselves when started outside it, and sluice enters it through the toolchain `.config/sluice.toml` declares, so run them as they are. The host carries no moon, bun, node or proto of its own on a session's path, so a tool run outside the shell fails for want of it rather than running the host's copy. A person at a terminal enters the shell with `devenv shell`, or direnv with the checkout's `.envrc`. Entering it installs the commit-msg hook, which refuses a message that is not a Conventional Commit (`code.6`), and `devenv shell -- release-preview` prints the version and notes the next push to main would release (`code.10`).
- crew's tests are in three tiers (`tests.11`, record 0022). **Logic** (`tests/py/`): crew's decisions called in-process on plain facts, by pytest, starting no process; a case reads as its spec's scenario and runs in milliseconds. **Contract** (`tests/contract/`): git, recutils, worktrunk and moon run for real in a scratch directory, each case naming what in crew assumes the behaviour it pins. **End to end** (`tests/t-*.sh`): the `crew` command on stub herdr, ssh, claude and plannotator, proving its wiring. A decision is a function of facts that calls no tool (`code.7`): test it in the logic tier, and when a decision you change still reaches a tool, pull it out first. A fix's reproducing case goes in the lowest tier that can hold it (`tests.4`). crew's mod (`plugin/hooks/status.js`) has its own cases in `plugin/tests/`, run as the suite's task `mod` by `tests/mod` under Claude Code's test kit, with no session or model (`tests.11`).
- While iterating, run the logic tier: `tests/suite logic`, or `devenv shell -- moon run tests:logic` for its output (the tests' pytest is in `tests/.venv`, which the tiers' `venv` task syncs from `tests/uv.lock` before every run of them, forced or not; the shell's `python3` has none). Run the contract tier, `tests/suite contract`, when you change how crew reads or writes git or the plan.
- While you work on the command itself, run the end-to-end tests that prove what you are changing, by name: `tests/suite <name>...`, or `tests/run <name>` for one on its own, with `CREW_TEST_SHOW=1` for its whole output. Run `tests/suite --affected` (against the merge-base with `main`, uncommitted edits counted) once, when the change is done, before its merge; an edit to crew's command core makes every test affected, so `--affected` while you iterate is the whole suite each time. Never run the whole suite by hand: sluice runs it afresh on every submission. `tests/suite` runs each test as a moon task, side by side, and replays a test whose inputs are identical to a run that passed on this host, in any worktree; `--force` runs without replaying. Every test on a host, whichever worktree or team runs it, waits for one of the host's test slots (`tests/slot`, its cores less two), so a busy host queues tests rather than thrashing (`tests.9`).
- After adding or removing a test, or changing what one reads, run `tests/moon-tasks` and commit `tests/moon.yml`: a task's inputs are what its test's outcome depends on (`tests.10`). Every task takes crew's command core (`plugin/bin/` and the modules `plan.py` and `crew.py` import), `tests/run`, `tests/slot`, `tests/lib.sh`, `tests/stubs/`, the toolchain files (`devenv.nix`, `devenv.yaml`, `devenv.lock`, `.prototools`, `.moon/toolchains.yml`, `tests/pyproject.toml`, `tests/uv.lock`) and itself; a test names anything else on a `# Reads:` line of its opening comment: `plugin/hooks/` when it starts an agent (the stub claude runs the session-start hook), `plugin/roles/` when it checks a brief's words, `plugin/lib/board.py`, `page.py`, `page.html` or `sites.py` when it runs them, and any other file of crew's it reads. `tests/suite` refuses to run while the tasks are out of step with the tests, or a test refers to a path its task leaves out.
- Run end-to-end tests only through `tests/suite` or `tests/run`, from the worktree's root. Never run a `tests/t-*.sh` file with bash: `tests/run` is what puts stub herdr, ssh, claude and hostname first on the path and gives each test a scratch HOME and bare remotes. A test run outside it reaches the real agents, the real plan on GitHub and the real repos. Every test stops on its first line when `TESTS` is unset; a new test keeps that line.
- `tests/suite` and `tests/run` exit non-zero when any test fails, and print a summary line; only "0 failed" passes.
- Inside devenv's shell `sed` is GNU sed. A test edits a fixture in place with `rewrite` from `tests/lib.sh`, never `sed -i ''`.
- Every merge in crew, a unit's, a chore's or a fix's into its bolt and a bolt's onto main, is a submission to sluice: sluice runs the `check-full` tasks the change affects, of those `.config/sluice.toml` requires of `bolt/*` and `main`, on the target with the work merged, open on the host and none replayed, in about two minutes, and lands it as a merge commit only when all pass, nothing landed otherwise; a change that affects none lands with nothing run (sluice ADR 0044; `tests.5`, `tests.10`). Nothing else moves a bolt's branch or main: no `wt merge`, `git merge`, `reset` or fast-forward there. An agent submits without waiting, `sluice submit <target> --no-wait --json`, and waits on it a call at a time, `sluice wait <n> --timeout 9m --json`, again for as long as it exits 5, never reading the outcome from `sluice status <target>`'s listing, which a decided submission leaves; a bolt's landing is `crew bolt submit`, run in the background and waited on to its end.
- **Never run `wt submit --help` in a worktree.** With sluice 0.3.1, `wt submit --help` prints its help, exits 0, and then removes the worktree it ran in as if the submission had landed: a unit's place is gone with its uncommitted work (read on mac-studio 2026-10-14 in a scratch repository; wldn's atl-1 lost a place the same day). The only `wt submit` an agent runs is its merge or landing command as crew gives it; for the usage, read `sluice submit --help` or `wt --help` instead, which remove nothing. Until sluice is fixed (the user's sluice work), this stands.

## Proving and landing a bolt

- **Before landing:** the bolt's proof is its verification: sluice's verdict on the bolt's last landing, the `Sluice-Result` trailer of the merge commit at the bolt's head, which `crew bolts` shows (`tests.5`, record 0025). The bolt only ever holds what passed its checks; there is nothing to deploy and nothing to run by hand. The landing's own submission runs the suite once more, on main with the bolt merged.
- **Landing:** a bolt lands by one procedure, main-level ops's, on the user's approval of its landing card (`plan.16`, the steps in `plugin/roles/main-ops.md`): ops submits the bolt with `crew bolt submit <bolt>`, which sluice lands on GitHub's main, then closes it with `crew bolt land <bolt>`; nobody else lands it, and nobody pushes main, pulls or levels a host for it. A landing that conflicts with main lands nothing: the team takes main into the bolt by a fix it submits to the bolt (`plan.8`).
- A standing agent loads its brief and crew's plugin when it starts. A change to them that reaches its host, by the timer moving `crew/live` on a live host or by swancloud's deploy of a new pin on a released one, makes each agent it touches due a restart, which crew gives it at its next stop, once it is idle, with its conversation, told what changed (`teams.19`); its band shows the crew it runs and when it is due. A landing alone reaches no released host.
