# crew

crew runs bolt teams of Claude agents in herdr, and each partition's main level. `README.md` says how it works; `openspec/` holds its changes, and the partition's plan their order.

## Rules

The rules every change holds to are in `docs/architecture/`: `core.md`, imported below, binds all of crew, and an area's page beside it binds that area, loaded when a file under its paths is read. A design or commit that relies on a rule cites its id (`state.1`); one that departs from a rule says which and why. Where `docs/architecture/` and README or a spec disagree, `docs/architecture/` wins. The reasoning behind a rule is in `docs/adr/`.

## Crew

What a crew team building crew needs to know. **The record**, in this order: `docs/architecture/` (the rules), `docs/adr/` (the reasoning), `openspec/specs/` (what each capability does), `README.md` and this file (the how-to), `openspec/explorations/` (readings and explorations, each saying so in its first line). **Where design is written**: a rule goes in `docs/architecture/core.md` if it binds all of crew, else on its area's page, with an id (`<area>.<n>`, the next free number in its area), one sentence, what it rules out and its source, amended in the same commit as the decision that changes it; a decision's reasoning is a record in `docs/adr/` (`adrs new`); how a capability behaves is its spec, changed only by a delta in the change that builds it.

## This checkout is live

On every host, the `crew` command and the plugin every Claude session loads run from that host's checkout of crew's `main`: mac-studio's is `~/Code/github_afterthought/crew/main`, the box's `/workspace/crew/main`. A commit on `main` there is live at once for every agent on that host, and a host gets crew's `main` by `git pull`, not a deploy. So work is built in a unit's or bolt's worktree, never in `main`, and a bolt lands only on the user's word.

## Tests

- crew's shell is devenv (`devenv.nix`). A Claude session in any crew checkout enters it at its start through the SessionStart hook in `.claude/settings.json` (`.claude/hooks/devenv-shell`), so every Bash command runs in it, with devenv's tools first on the path and the host's (herdr, wt, openspec, git) after them. A session that could not enter it is told so in one line, and says so rather than going on. No agent wraps a command in `devenv shell`: only the merge hooks in `.config/wt.toml` enter the shell themselves. `tests/suite` and `tests/run` refuse to start outside it. From a terminal, enter it with `devenv shell`, or direnv with the checkout's `.envrc`.
- While you work, run the tests that prove what you are changing, by name: `tests/suite <name>...`, or `tests/run <name>` for one on its own, with `CREW_TEST_SHOW=1` for its whole output. Run `tests/suite --affected` (against the merge-base with `main`, uncommitted edits counted) once, when the change is done, before its merge; an edit to crew's command core makes every test affected, so `--affected` while you iterate is the whole suite each time. Never run the whole suite by hand: every merge's gate runs it and replays what already passed, and the bolt's verification runs it after. `tests/suite` runs each test as a moon task, side by side, and replays a test whose inputs are identical to a run that passed on this host, in any worktree; `--force` runs without replaying. Every test on a host, whichever worktree or team runs it, waits for one of the host's test slots (`tests/slot`, two fewer than its cores), so a busy host queues tests rather than thrashing (`tests.9`).
- After adding or removing a test, or changing what one reads, run `tests/moon-tasks` and commit `tests/moon.yml`: a task's inputs are what its test's outcome depends on (`tests.10`). Every task takes crew's command core (`plugin/bin/` and the modules `plan.py` and `crew.py` import), `tests/run`, `tests/slot`, `tests/lib.sh`, `tests/stubs/`, the devenv files and itself; a test names anything else on a `# Reads:` line of its opening comment: `plugin/hooks/` when it starts an agent (the stub claude runs the session-start hook), `plugin/roles/` when it checks a brief's words, `plugin/lib/board.py`, `page.py`, `page.html` or `sites.py` when it runs them, and any other file of crew's it reads. `tests/suite` refuses to run while the tasks are out of step with the tests, or a test refers to a path its task leaves out.
- Run tests only through `tests/suite` or `tests/run`, from the worktree's root. Never run a `tests/t-*.sh` file with bash: `tests/run` is what puts stub herdr, ssh, claude and hostname first on the path and gives each test a scratch HOME and bare remotes. A test run outside it reaches the real agents, the real plan on GitHub and the real repos. Every test stops on its first line when `TESTS` is unset; a new test keeps that line.
- `tests/suite` and `tests/run` exit non-zero when any test fails, and print a summary line; only "0 failed" passes.
- Inside devenv's shell `sed` is GNU sed. A test edits a fixture in place with `rewrite` from `tests/lib.sh`, never `sed -i ''`.
- Every `wt merge` in crew, a unit's or a fix's into its bolt and a bolt's onto main, runs the whole suite as its gate (`.config/wt.toml`), `tests/suite --gate <target>`, in about the time of the longest test, less when it replays, and is refused with nothing landed when any test fails; a landing onto main replays nothing. An agent runs the merge in the background and waits for it to end.

## Proving and landing a bolt

- **Before landing:** the bolt's proof is its verification, green at the bolt's head; there is nothing to deploy. After each merge into a bolt the whole suite runs again on the revision the bolt then holds, replaying what the merge's gate passed on the same tree, and `sh .config/hooks/bolt-status.sh` from the bolt's worktree prints that run for the head, exiting 0 only when it is green. When the head's run was cut off, or a machine was fixed, and nothing has merged since, run it again there with `sh .config/hooks/bolt-verify.sh`. The landing's own gate runs the suite once more.
- **Landing:** a bolt lands by one procedure, main-level ops's, on the user's approval of its landing card (`plan.16`, the steps in `plugin/roles/main-ops.md`): ops merges it through the gate, pushes main and brings every host's checkout up to it; nobody else lands, pushes or pulls for it.
- **After landing:** a change's *Proof on real work* section needs the live system, so it is worked once the bolt has landed and every host has pulled: mac-studio's checkout at once, the box's with `git -C /workspace/crew/main fetch` and then `merge --ff-only origin/main` (its `main` tracks no upstream). Pull every host in the same step: a crew behind the others can refuse what a newer one writes.
- A standing agent loads its brief when it starts. A landing that changes a brief takes effect for each agent at its next fresh start, or by telling it what changed.
