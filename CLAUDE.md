# crew

crew runs bolt teams of Claude agents in herdr, and each partition's main level. `README.md` says how it works; `openspec/` holds its changes, and the partition's plan their order.

## Rules

The rules every change holds to are in `docs/architecture/`: `core.md`, imported below, binds all of crew, and an area's page beside it binds that area, loaded when a file under its paths is read. A design or commit that relies on a rule cites its id (`state.1`); one that departs from a rule says which and why. Where `docs/architecture/` and README or a spec disagree, `docs/architecture/` wins. The reasoning behind a rule is in `docs/adr/`.

## Crew

What a crew team building crew needs to know. **The record**, in this order: `docs/architecture/` (the rules), `docs/adr/` (the reasoning), `openspec/specs/` (what each capability does), `README.md` and this file (the how-to), `openspec/explorations/` (readings and explorations, each saying so in its first line). **Where design is written**: a rule goes in `docs/architecture/core.md` if it binds all of crew, else on its area's page, with an id (`<area>.<n>`, the next free number in its area), one sentence, what it rules out and its source, amended in the same commit as the decision that changes it; a decision's reasoning is a record in `docs/adr/` (`adrs new`); how a capability behaves is its spec, changed only by a delta in the change that builds it. **What each agent sees**: crew's mod (`plugin/hooks/status.js`) draws each conductor's, the planner's, the design agent's, main-level ops's and each operator's slice of the board above its prompt, from `board.agent_views`; a change to what crew models (bolts, units, stages, proposals, explorations and elaborations, cards, rail rows) updates both in the same change, with their cases (`code.8`).

## This checkout is live

On every host, the `crew` command and the plugin every Claude session loads run from that host's checkout of crew's `main`: mac-studio's is `~/Code/github_afterthought/crew/main`, the box's `/workspace/crew/main`. A commit on `main` there is live at once for every agent on that host, and a host gets crew's `main` by `git pull`, not a deploy. So work is built in a worktree of its own, never in `main`, and a bolt lands only on the user's word, through sluice. `main` moves only through sluice (`state.3`): a commit of anyone's, the user's own and the design agent's records among them, is made on a branch in a worktree of its own and submitted with `wt submit main` from there, and the main checkout is then brought level with `git -C <main> read-tree -m -u <old> main`, since sluice moves the branch and not the checkout's files.

## Tests

- crew's shell is devenv (`devenv.nix`): its system tools, proto among them, and the application tools crew's `.prototools` pins (moon, Python 3.13, the hosts' minor, and uv), which entering the shell installs into crew's own proto home in the git common dir when one is missing, and activates (`code.1`). No session is entered into it at its start (`tests.7`, record 0024): run crew's application tools through it per command, `devenv shell -- <command>` from the checkout, such as `devenv shell -- moon run tests:logic`. Each run reads the shell as the checkout's files stand, so an edit to `devenv.nix` or `.prototools`, or a rebase that changes them, reaches the next command; a warm entry costs about a third of a second. `tests/suite` and `tests/run` enter the shell themselves when started outside it, and sluice enters it through the toolchain `.config/sluice.toml` declares, so run them as they are. The host carries no moon, bun, node or proto of its own on a session's path, so a tool run outside the shell fails for want of it rather than running the host's copy. A person at a terminal enters the shell with `devenv shell`, or direnv with the checkout's `.envrc`.
- crew's tests are in three tiers (`tests.11`, record 0022). **Logic** (`tests/py/`): crew's decisions called in-process on plain facts, by pytest, starting no process; a case reads as its spec's scenario and runs in milliseconds. **Contract** (`tests/contract/`): git, recutils, worktrunk and moon run for real in a scratch directory, each case naming what in crew assumes the behaviour it pins. **End to end** (`tests/t-*.sh`): the `crew` command on stub herdr, ssh, claude and plannotator, proving its wiring. A decision is a function of facts that calls no tool (`code.7`): test it in the logic tier, and when a decision you change still reaches a tool, pull it out first. A fix's reproducing case goes in the lowest tier that can hold it (`tests.4`). crew's mod (`plugin/hooks/status.js`) has its own cases in `plugin/tests/`, run as the suite's task `mod` by `tests/mod` under Claude Code's test kit, with no session or model (`tests.11`).
- While iterating, run the logic tier: `tests/suite logic`, or `devenv shell -- moon run tests:logic` for its output (the tests' pytest is in `tests/.venv`, which moon syncs; the shell's `python3` has none). Run the contract tier, `tests/suite contract`, when you change how crew reads or writes git or the plan.
- While you work on the command itself, run the end-to-end tests that prove what you are changing, by name: `tests/suite <name>...`, or `tests/run <name>` for one on its own, with `CREW_TEST_SHOW=1` for its whole output. Run `tests/suite --affected` (against the merge-base with `main`, uncommitted edits counted) once, when the change is done, before its merge; an edit to crew's command core makes every test affected, so `--affected` while you iterate is the whole suite each time. Never run the whole suite by hand: sluice runs it afresh on every submission. `tests/suite` runs each test as a moon task, side by side, and replays a test whose inputs are identical to a run that passed on this host, in any worktree; `--force` runs without replaying. Every test on a host, whichever worktree or team runs it, waits for one of the host's test slots (`tests/slot`, its cores less two), so a busy host queues tests rather than thrashing (`tests.9`).
- After adding or removing a test, or changing what one reads, run `tests/moon-tasks` and commit `tests/moon.yml`: a task's inputs are what its test's outcome depends on (`tests.10`). Every task takes crew's command core (`plugin/bin/` and the modules `plan.py` and `crew.py` import), `tests/run`, `tests/slot`, `tests/lib.sh`, `tests/stubs/`, the toolchain files (`devenv.nix`, `devenv.lock`, `.prototools`, `.moon/toolchains.yml`, `tests/pyproject.toml`, `tests/uv.lock`) and itself; a test names anything else on a `# Reads:` line of its opening comment: `plugin/hooks/` when it starts an agent (the stub claude runs the session-start hook), `plugin/roles/` when it checks a brief's words, `plugin/lib/board.py`, `page.py`, `page.html` or `sites.py` when it runs them, and any other file of crew's it reads. `tests/suite` refuses to run while the tasks are out of step with the tests, or a test refers to a path its task leaves out.
- Run end-to-end tests only through `tests/suite` or `tests/run`, from the worktree's root. Never run a `tests/t-*.sh` file with bash: `tests/run` is what puts stub herdr, ssh, claude and hostname first on the path and gives each test a scratch HOME and bare remotes. A test run outside it reaches the real agents, the real plan on GitHub and the real repos. Every test stops on its first line when `TESTS` is unset; a new test keeps that line.
- `tests/suite` and `tests/run` exit non-zero when any test fails, and print a summary line; only "0 failed" passes.
- Inside devenv's shell `sed` is GNU sed. A test edits a fixture in place with `rewrite` from `tests/lib.sh`, never `sed -i ''`.
- Every merge in crew, a unit's, a chore's or a fix's into its bolt and a bolt's onto main, is a submission to sluice, `wt submit <target>`: sluice runs every `check-full` task on the target with the work merged, open on the host and none replayed, as `.config/sluice.toml` requires of `bolt/*` and `main`, in about two minutes, and lands it as a merge commit only when all pass, nothing landed otherwise (`tests.5`, `tests.10`). Nothing else moves a bolt's branch or main: no `wt merge`, `git merge`, `reset` or fast-forward there. An agent runs the submission in the background and waits for it to end.

## Proving and landing a bolt

- **Before landing:** the bolt's proof is its verification: sluice's verdict on the bolt's last landing, the `Sluice-Result` trailer of the merge commit at the bolt's head, which `crew bolts` shows (`tests.5`, record 0025). The bolt only ever holds what passed its checks; there is nothing to deploy and nothing to run by hand. The landing's own submission runs the suite once more, on main with the bolt merged.
- **Landing:** a bolt lands by one procedure, main-level ops's, on the user's approval of its landing card (`plan.16`, the steps in `plugin/roles/main-ops.md`): ops submits it to main through sluice with `crew bolt submit <bolt>`, pushes main and brings every host's checkout up to it; nobody else lands, pushes or pulls for it. A landing that conflicts with main lands nothing: the team takes main into the bolt by a fix it submits to the bolt (`plan.8`).
- **After landing:** every host takes crew's main at once: mac-studio's checkout is main itself, which the landing's submission brought level, and the box's is pulled with `git -C /workspace/crew/main fetch` and then `merge --ff-only origin/main` (its `main` tracks no upstream). Pull every host in the same step: a crew behind the others can refuse what a newer one writes.
- A standing agent loads its brief when it starts. A landing that changes a brief takes effect for each agent at its next fresh start, or by telling it what changed.
