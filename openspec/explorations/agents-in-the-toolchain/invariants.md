# Agents in their kit's toolchain: the invariants

## The goal in one sentence

Every Claude Code agent crew starts, and every agent flywheel will start after it, works inside its kit's toolchain, the exact tools the kit pins, from its first command to its last, however the session came to be, and the design is one a careful product would ship, resting on documented features of the tools we already run rather than on a trick of our own.

## What must hold

- **I1. The kit's tools, never the host's.** Every command the agent runs finds the kit's pinned tools first on its path: the system tools the kit's shell holds (devenv) and the application tools it pins (proto's `.prototools`: moon, bun, Python, Rust). A host's own copy of a tool never shadows them. Cases that broke this: mac-studio's path carries moon 1.41.7, which cannot run crew's suite; a workspace pinning bun 1.2.23 installed its dependencies with the host's bun 1.3.13; the Macs' system profile carries a secretspec without the credential helpers.
- **I2. The whole process tree.** What the session starts inherits the toolchain too: Bash commands, subagents, MCP servers, language servers (switchboard's typescript server needs the shell's node), hooks a kit or a plugin installs (breadboard runs prek after every edit), and the user's `!` commands in that session.
- **I3. No wrapping.** No agent is told to prefix a command with `devenv shell --` or the like, and a solution that relies on an agent remembering to is a failure. The user, 2026-10-08: "the whole point is that the agent should be launched inside the shell."
- **I4. Every way a session starts.** It holds when crew starts the agent, when herdr's server restarts and resumes the agent, when crew resumes it, and across Claude Code's own restarts of a session (`/clear`, compaction, `--resume`). A session the user starts by hand in a kit's checkout should get the same, by the same mechanism or the kit's own, without crew in the loop.
- **I5. One declaration, nothing kit-specific in crew.** The kit says once how its toolchain is set up, and crew and sluice read the same words: `.config/sluice.toml`, `[tests] toolchain = [<command that prints the toolchain as shell code>]` (record 0023). crew assumes neither devenv nor moon: the command may be `devenv print-dev-env`, `nix print-dev-env`, `direnv export bash`, `mise env -s bash` or `proto activate bash --export`. A kit that declares nothing gets nothing.
- **I6. The toolchain follows the worktree's files.** When the files the toolchain reads change in the worktree (a rebase onto the bolt bumps `.prototools`; the agent itself edits `devenv.nix`), the agent's later commands run on the new toolchain. Without a restart is the goal; at the latest at the session's next start, with crew saying so in the words that brought the change. The user: "their tests should run with the updated shells."
- **I7. Cheap, and cached with sluice.** A start adds under a second when this revision of the toolchain's files has been printed on the host before. The cold print, about 20 s for a devenv kit, happens once per revision per host, in a cache every worktree of the kit shares and sluice reads and writes too: the same key and the same place.
- **I8. The gate never depends on it.** sluice and the merge hooks print the toolchain fresh for each run and strip anything of a session's from a run's environment. A solution must not leak a session's environment into a run, and must not make the gate's correctness rest on the session's.
- **I9. Identity survives.** A crew agent keeps its name and partition (`CREW_AGENT`, `CREW_LABEL`, `SLUICE_AGENT`) and its herdr pane name across every start path above, as crew's session-start hook gives them back today.
- **I10. Nothing typed is lost.** Entering the toolchain at a start never reads the pane's input: crew types a stage's prompt as soon as the agent accepts input, and the fleet turned direnv's shell hook off in Claude sessions because an activation that reads stdin swallowed what was typed into a fresh pane.
- **I11. Refuse, never guess.** A session that could not enter its toolchain says so in one line and the agent stops rather than working on the host's tools; nothing falls back silently.

## What is fixed

- **Claude Code** is the agent runtime, as shipped: plugins loaded with `--plugin-dir`; hooks (`SessionStart` with sources `startup`, `resume`, `clear`, `compact`; `PreToolUse`, `PostToolUse`); `claude --resume <id>`; `--settings`; `CLAUDE_CONFIG_DIR`; and `CLAUDE_ENV_FILE`, a file whose contents run as shell code before each Bash command, which a SessionStart hook may append to or which may be set before launch. The docs say it applies to Bash commands and say nothing about subagents, MCP servers, language servers or other hooks. Nothing here changes Claude Code.
- **herdr 0.9.3** is the multiplexer on every host: panes, agent detection, its own Claude integration (a hook the fleet installs for every account, source `herdr:claude`, which reports state and the session id), and server restarts that resume each agent, by default with a bare `claude --resume <id>` found on the path. An agent may instead report its own resume command (`herdr pane report-agent <pane> --source <id> --agent <name> --state <s> -- <argv>`): a plain command name first, no apostrophes, at most 64 arguments, from a source that holds the pane by having reported state; herdr then runs it in the pane's folder after a restart (release 0.9.2; docs at `/docs/add-herdr-support/`). Which command herdr runs when both its Claude integration and a self-reporting source have spoken for one pane is not documented.
- **The fleet** is swancloud's Nix configuration: the `claude` on every path is its shim, which picks the account, sets `CLAUDE_CONFIG_DIR`, passes the generated settings and adds `--plugin-dir <crew main>/plugin` to every session it starts; direnv's zsh hook is off in Claude sessions and herdr panes. swancloud can change, as its own units; but crew and flywheel are meant to launch Claude themselves, so crew's correctness must not rest on the shim.
- **The toolchain split** (record 0023, sluice): devenv holds the system tools, proto among them; proto holds the application tools `.prototools` pins; `.moon/toolchains.yml` reads the pins; entering the shell runs `proto install` and activates the pins with `PROTO_HOME` and `MOON_HOME` of the kit's own under its git common dir.
- **The declaration and the adapter** (record 0023, built on `recovery/toolchain`): `plugin/lib/kit.py` reads `[tests]`; when crew makes a worktree ready it runs the toolchain command with a cleaned environment and keeps what it prints at `<worktree git dir>/crew/toolchain.sh`, then `moon setup` inside it. Later commands run as `bash -c 'source "$0" >&2; exec "$@"' <script> <command>`, by the bash on the path, since macOS's `/bin/bash` 3.2 cannot parse devenv's script.
- **sluice** sources the printed toolchain for every command of a run, outside any session's environment, and plans to cache the printed toolchain per revision of `devenv.nix`, `devenv.lock`, `devenv.yaml` and `.prototools` under the common dir (its piece 11, not built).
- **crew today**: `crew-role` sets `CREW_AGENT`, `CREW_LABEL` and execs `claude` bare in the role's folder; the plugin's session-start hook records the session and gives a resumed agent its names back through `CLAUDE_ENV_FILE`; every unit stage is a fresh agent in its slot, while a conductor, ops and the main-level roles live long; crew's and swancloud's repositories each carry a SessionStart hook that enters their devenv shell (`.claude/hooks/devenv-shell`), ruled by `tests.7`, which also rules out the shell entered by `crew-role` or by the plugin.
- **Hosts**: macOS (mac-studio, macbook-pro) and NixOS workspace boxes with nix-ld. Several Claude accounts per host, each with its own settings folder.

## What a solution is judged by

- **P1. Existing over invented.** Prefer a documented feature of Claude Code, herdr, devenv, nix, direnv, proto, mise or moon, or a known pattern other agent harnesses use, over a mechanism of our own, and cite the page. When the clean answer needs a feature a tool lacks, say so and put the feature request beside the best answer available now.
- **P2. Enter, then start.** Prefer entering the environment and starting the program inside it, as sandboxes do, over patching commands one by one.
- **P3. One mechanism** for every start path over one per path.
- **P4. Flywheel can take it over**: crew becomes flywheel-next, which composes sluice's SDK; a mechanism tied to crew's shape is worth less than one flywheel runs unchanged.
- **P5. Facts over belief.** Where a fact is unknown (herdr's precedence between reporters; whether the environment file reaches an MCP server), say how to find out and what the design does either way; never settle it by assumption.

## What the solver answers

1. For each start path in I4, how the session comes to be inside the toolchain, which feature it rests on, and its cost.
2. How I6 and I7 hold: how the toolchain follows the worktree's files, and what the cache's key and place are so sluice shares it.
3. What crew does, what the kit declares, what the fleet does, and what nothing has to do.
4. What stays uncovered, and why it is acceptable or what would cover it.
5. What becomes of `tests.7`, crew's and swancloud's repository hooks, and record 0023's held point.
