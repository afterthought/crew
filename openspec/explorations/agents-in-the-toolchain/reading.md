# Agents in their kit's toolchain

## The question

When crew starts an agent in a kit's worktree, which tools does it run: the ones the kit pins (its devenv shell, the versions in its `.prototools`), or whatever the host happens to have on its PATH? And if the kit's, how does the agent get them?

The user's doubt, on a first proposal that crew's plugin enter every session's devenv shell: "i'm not sure about this. seems like it's wrong. but i am probably missing something."

## How it works today

- **crew and swancloud** each carry a SessionStart hook in their own repository (`.claude/settings.json` running `.claude/hooks/devenv-shell`). At every start of a session in one of their checkouts, it enters that checkout's devenv shell once, dumps the environment, and writes it to the file Claude Code applies before every Bash command. crew's copy is handwritten; swancloud's is generated by its `devenv.nix`. Both cover every session in the checkout: crew's agents and the user's own.
- **Every other kit** has nothing. The fleet keeps direnv's hook off in Claude sessions and herdr panes (swancloud's `modules/home-shell.nix`), because devenv's activation swallows what is typed into a fresh pane. switchboard's CLAUDE.md says "Every tool comes from devenv (direnv, or `devenv shell -- <cmd>`)", and breadboard's says "Every tool comes from the devenv shell (`direnv allow` once)"; so an agent there either wraps each command or runs the host's tools.
- **crew-role** starts `claude` bare in the worktree. It sets crew's own variables (`CREW_AGENT`, `CREW_LABEL`, `SLUICE_AGENT`) and nothing of the kit's.
- **Merge hooks** enter the shell themselves (`devenv shell -- …` in each kit's `.config/wt.toml`), because worktrunk runs them for whoever merges.
- **sluice** never uses an agent's environment for a check. It runs the kit's declared toolchain command in its own place, keeps what it prints, and sources it before each command of the run; it strips anything of a session's from the run's environment (its clause 35).

## What goes wrong when an agent is not in its kit's toolchain

Instances read for this exploration:

- **The wrapping itself.** The user, 2026-10-08, on a crew agent wrapping its test command: "It is running the [devenv] shell for the test, but the whole point is that the agent should be launched inside the shell." (signal `2026-10-08-swancloud-planner-0ca5793d/01`). This is what crew's repository hook came from.
- **An older tool shadowing the pinned one.** mac-studio's PATH has moon 1.41.7 (`~/.bun/bin/moon`), which cannot run crew's suite at all (no task tags, no `moon exec`; sluice's `phase-1-integrations.md`, *What is installed*). In sluice's session on 2026-10-12, moon put `~/.proto/bin` (the user's moon 2.4.6) and `~/.moon/bin` (1.41.8) ahead of devenv's 2.6.1 on every task's PATH, until sluice gave itself its own `PROTO_HOME` and `MOON_HOME`.
- **A dependency installed with the host's tool.** In a scratch moon 2.6.1 workspace pinning bun 1.2.23, moon's dependency install ran `zsh -c "bun install"`, which found the host's bun 1.3.13, because proto's directories were not on the PATH (record 0023's probes). Inside a shell that activates proto, the pinned bun runs.
- **A second copy of a tool on the system path.** The Macs' system profile carries devenv's bundled secretspec 0.21.0 beside the fleet's 0.21.1, so anything with only the system PATH gets the old one, without the credential helpers (signal `2026-10-08-swc-2-ops-cc25cfbc/01`).
- **A kit hook that assumes the shell.** breadboard's `.claude/settings.json` runs `cd "$DEVENV_ROOT" && prek run` after every edit, which only does what it means when the session is in breadboard's shell. Read from the file; not run.
- **The reverse: the shell differs from what runs.** crew's tests run on its devenv's Python 3.14.7, while every host runs crew on its own `python3`, 3.13.15 on mac-studio. Being inside a shell is not enough if the shell pins something other than what production uses.

Not known: how often agents in switchboard or breadboard forget to wrap a command and run the host's tools. Their transcripts could be searched for `bun`, `moon` or `node` run without `devenv shell --`.

## What "the kit's toolchain" means now

sluice's split, which record 0023 adopts: devenv holds the system tools (git, nix, proto, the formatters); proto holds the application tools the kit pins in `.prototools` (moon itself, Rust, Python, bun); entering the devenv shell runs `proto install` and activates those pins. A kit declares the command that prints its toolchain as shell code (`[tests] toolchain = ["devenv", "print-dev-env"]` in `.config/sluice.toml`), and crew's toolchain adapter runs it when it makes a worktree, keeping the printed script in the worktree's git directory.

So "the agent is in its kit's toolchain" can mean either of two things: it entered the kit's shell, or it sourced the kit's printed toolchain. They give the same PATH; the second needs no devenv-specific step.

## The options

### A. A startup hook in crew's plugin

crew's plugin, which every session on crew's hosts loads, carries a SessionStart hook that enters the session's checkout's devenv shell (or sources its declared toolchain), and writes the result to the file Claude Code applies before each command.

- **Covers:** every session on the host in a kit's checkout, crew's agents and the user's own, at every start and resume. Could be limited to crew's agents (those with `CREW_AGENT`, or a session record).
- **Costs:** every such session waits for the shell at its start: about 20 s cold in a new worktree, under a second warm. One copy of the hook, tested in crew's suite.
- **Breaks:** `tests.7` rules out "the shell entered by crew-role or by the plugin", with the reason "the plugin is loaded by every session in every kit, and what the shell is belongs to the checkout". The user's own sessions change behaviour without the user asking, in every kit. Where a kit also carries its own hook (swancloud's), both run.

### B. The kit's own repository hook

Each kit commits the hook crew and swancloud have now, in `.claude/settings.json`.

- **Covers:** every session in that kit's checkouts, crew's agents and the user's own.
- **Costs:** a copy per kit, each maintained by its kit. crew's and swancloud's are already two forms (handwritten, generated).
- **Breaks:** nothing of crew's. A kit that has not added it leaves its agents on the host's tools, as switchboard and breadboard do today.

### C. crew's launcher wraps `claude`

crew-role starts `devenv shell -- claude …`, or `bash -c 'source <toolchain script>; exec claude …'`.

- **Covers:** crew's agents only, at their start.
- **Costs:** the pane shows nothing until the shell is up.
- **Breaks:** a herdr resume starts a bare `claude --resume`, so a resumed agent loses the shell; `tests.7` rules this out for that reason. crew's start command would name devenv for every kit, unless it sources the declared toolchain instead.

### D. The toolchain adapter's script given to the session

When crew makes a worktree ready, its toolchain adapter keeps the kit's printed toolchain in the worktree's git directory. crew's existing session-start hook, which already gives a resumed agent its crew name through the same file, also applies that script for a crew agent in a worktree crew made.

- **Covers:** crew's agents, at every start and resume, in any kit that declares a toolchain. No devenv-specific step in crew; the user's own sessions are unchanged.
- **Costs:** the script is as of when crew last made the worktree ready; a branch that changes `devenv.nix` or `.prototools` while an agent works leaves its session on the old tools until crew runs the toolchain again. Sourcing at start costs little, since the script is already printed.
- **Breaks:** devenv's `enterShell` lines run again when the script is sourced, in the agent's session (they are in the printed script: sluice found its `rm` lines there). An agent in a worktree crew did not make (the kit's main, a main-level role) gets nothing.

### E. sluice's per-run sourcing

No session environment at all: whatever needs the kit's tools runs through the toolchain each time, the way sluice runs a check. For example a crew command that runs one command in the worktree inside its declared toolchain, which briefs and kits' CLAUDE.md would tell agents to use for builds and tests.

- **Covers:** only the commands that go through it.
- **Costs:** each command pays the toolchain's sourcing (cheap once printed). Agents have to remember to use it, which is the wrapping the user objected to on 2026-10-08.
- **Breaks:** nothing at a session's start; an agent's plain `bun test` runs the host's bun.

## What is not known

- Whether Claude Code applies the start-time environment file to a subagent's Bash commands, to plugin and repository hooks (breadboard's `prek` hook), to MCP servers, and to language servers (switchboard enables `typescript-lsp`, which needs the shell's node).
- How long a cold shell entry, or a cold `devenv print-dev-env`, takes in switchboard or breadboard on the box, where most of those kits' agents run. sluice measured about 20 s for its own on mac-studio, and plans to cache the printed toolchain per revision of `devenv.nix`, `devenv.lock`, `devenv.yaml` and `.prototools` (its piece 11).
- Which Claude accounts on each host load crew's plugin. The box runs several accounts (`willdan-alex`, `ia`, `credits`), each with its own settings.
- Whether the user wants their own sessions in a kit's shell, given the fleet turned direnv off in Claude sessions on purpose.
- What a session started in a folder that holds several kits should get (a dispatcher's or operator's session in `/workspace` or `~/Code/github_afterthought`), and what a role that reaches other kits through `--add-dir` should get.
- What should happen when a worktree's toolchain changes under a running agent (a rebase that bumps `.prototools`).

## What an elaboration could settle

1. Whose sessions are in a kit's toolchain: crew's agents only, or every session in a kit's checkout.
2. Whether "in the toolchain" means entering the shell, or sourcing the declared toolchain crew already printed (option D), which ties the answer to record 0023's toolchain adapter rather than to devenv.
3. Where the mechanism lives: crew's plugin, each kit, or the fleet's home configuration (a hook installed in each Claude account's settings, outside crew).
4. What happens to `tests.7` and to crew's and swancloud's repository hooks.
5. Which of the unknowns above to measure first.
