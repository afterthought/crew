## Goals / Non-Goals

**Goals:**

- Nothing of the team machinery is left in crew: no conductor, team ops, dispatcher, unit slot, give, team tell, fix slot or per-team setting, in code, briefs, usage, docs or tests (record 0047 move 5; record 0050 part 3).
- One path: the one `teams-cross-to-flume-as-their-bolts-land` built behind the setting, which every team runs by the time this change lands.
- Every staying feature reads its facts without a team: the plan, the cards, the rail, the board, the page, the trace, `crew bolts`, `crew sites`, a landing, a batch, a hold, an update.
- The run record's and the plan's history stay readable as written (`record.4`, `state.2`).

**Non-Goals:**

- Any part of the crossed path beyond giving it, with no team, the three facts a team gave it: a kit's host and stream (Decision 4) and a bolt's start (Decisions 14 and 15). Launching through the runner, reading stages from its records, answering a place, a submission's failure sent back to code, are `teams-cross-to-flume-as-their-bolts-land`'s, and this change adds no second way to any of it.
- Move 6: the five roles keep standing as they do today (`roles-run-as-flume-kinds` is the bolt's change for that).
- A registry of repositories, or anything of the runner's own design: the runner's repository, how it pulls, which runner takes a launch.
- Amending `docs/architecture/` or `docs/adr/`: the design agent does it after the landing (`docs.7`); this change names what it retires.
- Rewriting the plan's records on an existing state branch.
- Choosing a place's base: a feature branch may hold nested feature branches and Flume has no opinion on a place's base (the user, 2026-10-31); removing the give removes the last place crew tied a place to its team's one bolt, and nothing here assumes one level of branch.

## What this change rests on

1. **`teams-cross-to-flume-as-their-bolts-land`, merged into the bolt first.** This change is placed `After` it, since it removes what that change leaves beside its own path. It needs, built there and proven by that change's own tests:
   - the per-team setting `flume` in `teams.json` version 3;
   - for a crossed team: a give that makes the bolt's branch and launches its units, chores and fixes through `requests.rec`, the plan's order of bolts their priority (`runner.priorities`); each stage's state read from the runner's `places.rec` (`runner.stage_of`); a place stopped short with its question shown to the planner, design or ops and answered by `crew answer`, a retry; a failed or conflicting submission sent back to code by Flume itself (flume record 0011); a fix on the bolt by `crew fix`; a landing that conflicts with main taking main in by a fix place; a fix of a red main by `crew main fix`; plan writes that reach launched work.

   Each of these becomes the only path once this change removes the off side. Where one of them is missing when this change is built, its removal would leave the feature with no path at all, so the coder stops short and says which (`flume needs --found`), rather than building the missing piece here.
2. **Every team's setting on, on every host.** A team moves on the user's word, one at a time (`roles.2`, `roles.8`); this change lands only once none runs the old path, since `roles.8` rules out a landing a team on today's path cannot run. Hosts run crew released at the tag swancloud pins (`plan.19`, record 0050 part 1), so the landing reaches a host only by the user's bump.
3. **The runner's records name what each host keeps, and its stream.** The runner, `flywheel` of agentplot/flywheel-runner, keeps only the repositories its configuration names (its `core.5`) and leaves where work runs to the control plane (its `core.1`). `teams-cross-to-flume-as-their-bolts-land` has its `runner.rec` name the host, the runner's version and when it began. This change needs one fact more there, the facts a team's `machine`, `repos` and `flume` gave crew until now: for each repository the runner keeps for the partition, its folders on the host (its clone and its view) and the Flume stream its work runs in there, none where the host keeps only a view. That is an ask of the runner's crew implementation, through its one interface (its `core.2`); crew reads it in `runner.py`.
4. **swancloud.** `lib/crew-teams.nix` writes `teams.json` version 4, partitions alone, in the same deploy as the bump of crew's pin to the release that carries this change (record 0050 part 2: the deploy that writes a field precedes the bump that requires it; here neither crew can read the other's file, so both go in one deploy). The deployer's after-deploy steps name no `dispatcher` as a doer. Both are swancloud units, which the planner proposes.

`roles-run-as-flume-kinds` touches the same launcher, greetings, briefs and hooks. Neither builds on the other's code; whichever merges second takes the other's words where they meet.

## Decisions

### 1. The crossed path is the only path, and it goes first

Every decision that branches on the per-team setting keeps the branch for a team with it on and loses the other; the setting is read nowhere. This is the first task group, so that everything after it removes code nothing reaches. A test that proved the off side is deleted with it; a test of a staying feature that set its work up through the old path, a landing, a batch, a card, is rewritten to set it up as the crossed path does, never deleted (`tests.4`: coverage is kept at the lowest tier that holds it).

Alternative: remove the machinery piece by piece with the setting still read. Rejected: each piece would need a decision on what a team with the setting off does meanwhile, which is the old path this change removes.

### 2. The teams file holds partitions only, at a new version

`teams.json` keeps `version` and `partitions[]`; `teams[]` leaves, and the per-team setting `flume` with it. The file moves to version 4, the next after `teams-cross-to-flume-as-their-bolts-land`'s 3, and crew reads version 4 alone: a file at version 2 or 3, or any other, is refused naming the machine's configuration (swancloud's `lib/crew-teams.nix`) as the fix, crew having done nothing (`code.5`). A partition's `roles` may override design, planner, main-ops, operator and reviewer; `dispatcher` is refused as a role with no definition, as any unknown role is.

Why a version: no field has a default (`code.5`), and reading a `teams` list in order to ignore it would make its absence a default; a file that still lists teams was written for a crew that runs them. Alternative: read both versions through a transition. Rejected: two readings of one file, when swancloud can carry the file and the pin in one deploy (*What this change rests on*, 4).

### 3. A partition's kits are the repositories its plan and its landings name

Where crew took a partition's kits from its teams (`partition_kits`, `kits_on`), it takes the repositories named by the `Repo` of the partition's Bolt and Unit records, together with the `Repo` of the `bolt.land` entries in its run record, read from the branch (`read.5`). A decision over plain facts (`code.7`): `partition_kits(plan, landings)`.

Why: there is no registry in crew (the user, 2026-10-31), the plan is the partition's record of its work (`state.2`), and every staying read of a kit is about a bolt or unit of the plan, a card about one, or the board's Inception lane, which the landings keep showing for a kit with nothing planned now. A new kit enters a partition with its first bolt. Alternatives: the hosts file's spaces, whose repository lists leave swancloud's configuration once the runner is deployed (record 0052's asks of swancloud); the runner's records, which say what a host keeps and know no partition.

### 4. A kit's work runs, and the kit is read and landed, where a runner keeps it with a stream

Every read, launch or act crew made on a kit's team's host takes the host from the runners' records (*What this change rests on*, 3): the one host whose runner keeps the kit with a stream, its work's stream that runner's; where several do, the partition's main-level host if it is one of them. A kit kept with a stream on several hosts, none of them the main level's, or on none, is named as unread with the hosts it found (`read.1`): nothing of it is launched or landed, and every other kit is still read and shown (`read.3`). A host that keeps the kit as a view alone is no host for its work. On that host crew reads the kit's repository where the runner's record puts its clone and view, `origin/<default>` after a fetch as every read of main is now (`plan.18`), and cuts a landing's short-lived worktree from that clone, as `plan.18` and `plan.16` have it, since sluice takes a submission only from a worktree on the branch. A decision over plain facts: `kit_host(kept, main_host, kit)`, `kept` being each host's runner record reduced to its repositories, folders and streams, answering the host, the folders and the stream, or a refusal.

This replaces `builder`, `bolt_team`'s machine, a launch's `Host` and `Stream` from a crossed team, `Stages.kit`, `survey`'s per-host kits, `landing_team`, `change_folder`, `made_read`'s host, the card preview's host and `sites.py`'s bolt rows. Why the main level's host first among several: it is where main-level ops lands and the cards are raised, so a kit kept there is read and landed without ssh (`code.3`). Why a refusal and not a choice among the others: which host's room a kit's work takes is the control plane's decision (flywheel-runner `core.1`), and with no registry its only facts are the runners' own configurations, which then disagree; the user settles it by a runner's configuration, never crew by a guess.

### 5. A partition's hosts are its main level's and its kits'

`partition_hosts` names the main level's machine and every host Decision 4 gives one of the partition's kits, each once. It feeds the readings' hosts (`read.3`), `crew hold`, `agents_here` and the board's `environments`.

### 6. What a conductor or a team held goes to the role record 0047 names, as the crossed path has it

Record 0047 move 5: within a partition, a stage speaks to the planner, design or ops, and nothing speaks team to team; ordering within a bolt, batches and amendments are the planner's; a landing is main-level ops's on the user's send. So:

- **A proposal** waits on no conductor's agreement: the user's approval is the one word (`roles.2`); `crew plan agree` and the `Agreed` write go, and the proposal card names no conductor it waits on.
- **Ordering within a bolt**, `unit split|order|after` and their chore forms, is the planner's by proposal; no agent but the user writes them directly (`roles.1`).
- **The bolt's reading and preview** (`land/<bolt>`), which `reading_owner`, `land_session` and `preview_owner` gave the bolt's conductor, are main-level ops's, the owner of the kit's landings card, as the crossed path already has them for a crossed bolt.
- **A question for the user** is asked by the planner, main-level ops or the design agent (`briefs.11`); `ASKERS` drops `conductor`, and `card_refusal`'s team, conductor and dispatcher branches go.
- **A batch's notes** go to the planner, who hands each unit's on as the crossed path does; no conductor runs construct again (`briefs.12`).
- **A landing's conflict with main**, forecast on the landings card or met at the submission, is answered as the crossed path answers it for a crossed bolt; no team's take-main fix is started and no conductor is told.

### 7. The stage briefs leave with the slots

`construct.md`, `coder.md` and `verify.md` brief the agent crew started in a unit slot (`crew-role <team>-unit-<n> <stage>`). On the crossed path a stage is a place of a Flume kind, prompted by the kind and briefed by the kit's own files, its `CLAUDE.md`, its `openspec/config.yaml` and its `.config/flume.toml`: this construct stage ran so, as Flume's change kind under crew's `openspec` profile, its stop-short `flume needs`. With no slot, crew starts no stage agent and has no stage brief to give, so the three leave, and `briefs.2` and `briefs.18`, which bind them, retire.

### 8. The run record keeps its history

crew writes no `slot.free`, `stage.start`, `stage.end`, `fix.start`, `fix.merge`, `fix.drop`, `bolt.give`, `team.up|close|rebuild|down`, `team.cross`, team-scoped `agent.start|restart|clear|resume`, team greeting, unit `forecast`, `amendment` or `plan.agree` entry, and no `main.up|down` for a dispatcher. The descriptor's fields stay, entries are never rewritten (`record.4`), and `crew trace` reads and prints the old acts as before, `team/` objects among them. A batch's `review.start` and `review.batch` name each unit with its bolt, `<unit>:<bolt>@<commit>`, where one written before named its team in the same place; the reader takes that name as written. `record.5` and `record.6` retire as rules about entries crew writes.

### 9. The plan's records keep their fields on the branch

A Bolt's `Team` and a Proposal's `Agreed` are never written or read again. A state branch's own descriptor keeps allowing them, so `recfix --check` passes on records that still carry one (`plan.1`); a new branch's descriptor (`HEADER`, `PROPOSALS`) drops them, `%unique: Repo Goal Team` becoming `%unique: Repo Goal`. No write strips them: a field nothing reads changes nothing, and a commit of crew's own making that touches every bolt to change nothing is noise in the plan's history (`state.2`).

### 10. A command that leaves is gone, not stubbed

Unlike `crew card wait`, which refused naming its successor for agents still carrying an old brief, no agent that ran these commands is left once the bump lands: crew starts no conductor, team ops, dispatcher or slot agent, and each main-level agent restarts at its next stop on the plugin's change with its new brief (`teams.19`). A removed command falls to crew's unknown-command answer, which prints the usage. Alternative: a refusal per command naming the rail. Rejected: code kept for agents that no longer exist.

### 11. The views follow (`code.8`)

`board.agent_views` gives the planner, the design agent, main-level ops and the operator their views, and no conductor's, team ops's or dispatcher's; `conductor_view` goes, and the crew-version lines `here_read` gave team agents and dispatchers go with them. `crew board --json` lists no `teams` per partition and no `teams` on any object, and the page's team control goes with it. A bolt's ledger shows its work as the crossed path reads it, with no slots, its head line naming its kit's host and stream (Decision 4), which the board's JSON gives the ledger where it gave a crossed team. A bolt's time (`plan.20`) keeps its holders' names, which the bands, the mod and every landing entry already carry: the `team` holder is the bolt's own work as the crossed path reads it, and the age runs from the run record's entry that made the bolt's branch, not from a give. Renaming the holder would change every band and entry for no behaviour, which the user's "nothing new invested" rules out. The cards drop the "a yes frees …" line (`teams.16`) and every conductor's name. The page drops its team docks and slot rows. A started bolt's ledger, and its entry in `crew sites`, show no dev server, since crew finds one only in a worktree of its own making and a started bolt's places are Flume's; the runner reporting a place's addresses from Flume's run record (record 0043) is an item of `_open.md` for its interface (the user, 2026-10-31). `plugin/hooks/status.js` draws what the views give and gains no case of its own beyond the views' new shape.

### 12. A hold and an update reach the main-level roles alone

`hold.py` stands down, holds and restarts the main-level roles and nothing of a team's or a dispatcher's; `renew` restarts no conductor fresh. The branch hint goes whole (`teams.20`): `crew-role`'s `SLUICE_BRANCH`, the pane's `sluice_branch` token, `CREW_BRANCH` at a start, `crew.py hint`, `branch_due`, `branch_now`. The stop hook's exclusion of `-unit-<n>` agents goes, since there are none.

### 13. The order of the build

One path first (Decision 1), then the machinery from its leaves in: stage driving and the fix slot; the give, the dispatcher and the conductor's part of the plan; the team's agents, tells and hint; then the reads that went through a team; then the views; then the teams file itself, which everything before stops reading; then the briefs; then the tests' tasks. Each group leaves the suite green, and each command's removal updates the usage header, README and the skill together (`docs.2`), so `t-docs` holds after every group.

### 14. A bolt's work starts by `crew bolt start`, the crossed give with no team

`crew bolt start <bolt>` does what a crossed team's give does, with no team: it checks the kit's policy and has sluice make `bolt/<bolt>` on the kit's host (Decision 4), is refused while that host is held (`teams.19`), has no runner branch, or keeps the kit with no stream, and in one plan write marks the bolt `Path: flume` and appends a launch request for each unit and chore of it, each with its `After` and the priority `runner.priorities` gives. It starts no agent. Every write that reached a crossed team's launched work reaches a started bolt's: an added unit is launched, an amendment is a retry of construct, a drop drops the place, a reorder sends the priorities that changed. A bolt in flight, wherever the specs and the views say so, is a started one, marked `Path: flume`. A bolt's age (`plan.20`) runs from its start's entry, `bolt.start`, which takes `bolt.give`'s place in the run record.

A proposal may hold `bolt start`, so the planner proposes which bolts run and the user approves (`roles.1`, the planner changing the plan only by proposal); the user runs it directly. No other agent runs it. Why a start at all, when record 0047 move 5 has every open bolt's work launched and Flume's room decide what runs: the plan holds bolts the planner has placed and the user has not chosen to run (the queue, planned bolts), and a launch makes a place at once; the user's words of 2026-10-28, "what I really want to be doing as a user is choosing what work is happening at any given time", make that choice the start, and the rail's order the priority after it. Alternative: launching every bolt's work at its approval. Rejected: it makes every planned bolt's places at once, and turns the order of the plan's bolts, which is the planner's to propose, into the only choice the user has.

### 15. A fix names its bolt, and a fix of main its kit alone

`crew fix <bolt> <name> "<words>"` launches a fix place on the bolt as a crossed team's `crew fix` does, on the kit's host with its stream, and is the planner's, design's or ops's, as the crossed path has it; `--drop` drops its launch, as the crossed form does, and `--merge`, `--wait` and `--bolt` are no options it has (Flume submits and tells, and the bolt is named first). `crew main fix <kit> <name> "<words>"`, with its `--drop` and `--send`, takes no `--team`: its host and stream are the kit's (Decision 4), and a kit no runner keeps with a stream is refused, naming it, so a red main's fix of such a kit stays what `state.3` says until one does. The landing read's take-main fix launches on the kit's host the same way.

### Rules relied on

`state.1` and `plan.1` (plan writes unchanged), `state.2`, `state.4`, `read.1`, `read.3`, `read.5`, `code.2`, `code.5`, `code.7`, `code.8`, `roles.2`, `roles.5`, `roles.8`, `plan.16`, `plan.18`, `plan.19`, `teams.19`, `docs.2`, `docs.4`, `docs.7`, `tests.4`, `tests.10`, `tests.11`.

The user settled on 2026-10-31 that there is no registry of repositories in crew and that the runner's own configuration names what each host keeps; this change builds no registry and reads the runner's records instead (Decisions 3 and 4). Amending `roles.9` and record 0052 is the design agent's.
- **`docs.7`** (proposed): this change names the rules it retires and edits no rule page.

## Risks / Trade-offs

- **The crossed path's requirements stand in the specs this change starts from.** `teams-cross-to-flume-as-their-bolts-land`, archived on the bolt before this change, adds the crossed team's requirements: its path, its due state and crossing, its give, launches, answers and fixes, the fix of main where a crossed team builds the kit, its rows, ledger, bands, batches and `team.cross` entry. A delta can remove or rewrite a requirement only once it stands in the specs, so this change's deltas carry each of them: those that exist only for a team (a team's path, its due state, its crossing, its closing, its standing agents, its `team.cross` entry) are removed, and every other is renamed and said of a started bolt, its kit's host and the stream that host's runner keeps the kit with (Decisions 4, 14 and 15), keeping what it asks: launches carrying stream, priority, intent and recipient; dependents launching after their After work lands; plan writes reaching places; answers by retry; fix places on a bolt, dropped by `--drop`; a conflicting landing taking main in by a fix place; a red main's fix as a fix place on main; the board's, the bands' and the rail's reads from the runner's records. A kit's host is a flywheel-state requirement of its own. Task notes 1.1's first check finds none of them left speaking of a team.
- **Specs this change leaves to the crossed path.** The deltas remove every requirement of the old path and rewrite each staying one whose rule names a team, a conductor, a dispatcher or a team's host. Three groups are left as they stand, since what replaces their words is the crossed path's reading and this change would only guess at it: `card-sessions`' owner of a bolt's reading (`land/<bolt>`, the bolt's conductor there, main-level ops by Decision 6), the bolt-time requirements of `crew-board` (`plan.20`'s holders, read from stage entries crew no longer writes), and the scenarios of `rail-cards` and `card-sessions` that use a conductor as any card's owner. Mitigation: `teams-cross-to-flume-as-their-bolts-land` re-owns them for a crossed bolt; where its deltas do not, the planner proposes a chore to bring the specs level with the code, which follows Decision 6 (`docs.3`: code follows the design where they disagree).
- **The installed OpenSpec keeps every scenario of a MODIFIED requirement.** A requirement whose scenarios leave is removed and its successor added under a new name, so the archive shows those as a removal and an addition, not an edit; each removal's Migration names its successor.
- **A test of a staying feature built on the old path.** Deleting it would lose the feature's coverage. Mitigation: Decision 1 rewrites it on the crossed path's setup; the deleted tests are only those whose subject leaves.
- **The board's Inception lane** shows a kit only once the partition has planned or landed work in it. Accepted: a kit with neither has no bolt to read anything for.
- **The teams file and the crew that reads it change together.** A host with the new file and the old crew, or the reverse, refuses every command. Mitigation: one swancloud deploy carries both; its rollback reverts both.
- **A team agent or a dispatcher still standing at the bump** keeps running the old brief, unknown to the new crew, which neither restarts nor ends it (`read.4`). Mitigation: *After deploy*.
