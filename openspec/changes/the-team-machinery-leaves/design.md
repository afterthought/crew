## Goals / Non-Goals

**Goals:**

- Nothing of the team machinery is left in crew: no conductor, team ops, dispatcher, unit slot, give, team tell, fix slot or per-team setting, in code, briefs, usage, docs or tests (record 0047 move 5; record 0050 part 3).
- One path: the one `teams-cross-to-flume-as-their-bolts-land` built behind the setting, which every team runs by the time this change lands.
- Every staying feature reads its facts without a team: the plan, the cards, the rail, the board, the page, the trace, `crew bolts`, `crew sites`, a landing, a batch, a hold, an update.
- The run record's and the plan's history stay readable as written (`record.4`, `state.2`).

**Non-Goals:**

- Any part of the crossed path beyond giving it, with no team, the three facts a team gave it: a kit's host and stream (Decision 4) and a bolt's start (Decisions 14 and 15). Launching through the runner, reading stages from its records, answering a place, a submission's failure sent back to code, are `teams-cross-to-flume-as-their-bolts-land`'s, and this change adds no second way to any of it.
- Move 6: the five roles keep standing as they do today (`roles-run-as-flume-kinds` is the bolt's change for that).
- A registry of repositories, or anything of the runner's own design: the runner's repository, how it pulls, which runner takes a launch.
- Amending `docs/architecture/` or `docs/adr/`: the design agent does it after the landing (`docs.7`); this change names what it retires.
- Rewriting the plan's records on an existing state branch.
- Choosing a place's base: a feature branch may hold nested feature branches and Flume has no opinion on a place's base (the user, 2026-10-31); removing the give removes the last place crew tied a place to its team's one bolt, and nothing here assumes one level of branch.

## What this change rests on

1. **`teams-cross-to-flume-as-their-bolts-land`, merged into the bolt first.** This change is placed `After` it, since it removes what that change leaves beside its own path. It needs, built there and proven by that change's own tests:
   - the per-team setting `flume` in `teams.json` version 3;
   - for a crossed team: a give that makes the bolt's branch and launches its units, chores and fixes through `requests.rec`, the plan's order of bolts their priority (`runner.priorities`); each stage's state read from the runner's `places.rec` (`runner.stage_of`); a place stopped short with its question shown to the planner, design or ops and answered by `crew answer`, a retry; a failed or conflicting submission sent back to code by Flume itself (flume record 0011); a fix on the bolt by `crew fix`; a landing that conflicts with main taking main in by a fix place; a fix of a red main by `crew main fix`; plan writes that reach launched work.

   Each of these becomes the only path once this change removes the off side. Where one of them is missing when this change is built, its removal would leave the feature with no path at all, so the coder stops short and says which (`flume needs --found`), rather than building the missing piece here.
2. **Every team's setting on, on every host.** A team moves on the user's word, one at a time (`roles.2`, `roles.8`); this change lands only once none runs the old path, since `roles.8` rules out a landing a team on today's path cannot run. Hosts run crew released at the tag swancloud pins (`plan.19`, record 0050 part 1), so the landing reaches a host only by the user's bump.
3. **Each machine's runner configuration names what it keeps, Flume's host configuration its streams, and a runner takes a kit's work by its repository.** The runner, `flywheel` of agentplot/flywheel-runner, keeps only the repositories its configuration names (its `core.5`, landed at its main 3e61c31, `~/.config/flywheel/config.toml`), with their folders, and names no stream. The user ruled on 2026-11-01 (Pending You req_4c3980ac) that crew models no account and looks up no kit's host, and settled the same day that streams are defined on each host in Flume's host configuration, each with its bound, priority and pool, a repository mapped to its stream there, that a launch may name another stream the host defines (`--stream`), and that runners pull work under a lease and take it only while the host's stream has room. So crew records work against its repository and names no stream, and a runner whose configuration names that repository takes it and launches it there, in the stream its host maps the repository to; several hosts may keep one repository, and the lease decides which takes each launch. So the facts a team's `machine`, `repos` and `flume` gave crew are the runners' and Flume's host configurations', and crew reads none of them: where it must say or act where a kit's work runs, it reads what the runner reported for the work it took, its answers and Flume's status of its places on `<label>/runner/<host>`. This asks of the runner's crew implementation, `the-runner-carries-crews-work-into-flume` (proposed at 818b10d), through its one interface (its `core.2`): taking each launch whose `Repo` its configuration names, under its lease and while its host's stream has room, by forge address or by the name alone as crew's plan names a kit, with no `Host` or `Stream` on it, and a retry, drop or priority of a launch it took; ignoring, rather than refusing, a launch of a repository it does not keep, which another host's runner takes; and carrying Flume's status of each place with its `repository` and `stream`. crew builds none of it, and a repository's stream is Flume's host configuration's, not the runner's or crew's.
4. **swancloud.** `lib/crew-teams.nix` writes `teams.json` version 5, partitions alone, each with its `flume`, in the same deploy as the bump of crew's pin to the release that carries this change (record 0050 part 2: the deploy that writes a field precedes the bump that requires it; here neither crew can read the other's file, so both go in one deploy). The deployer's after-deploy steps name no `dispatcher` as a doer. Both are swancloud units, which the planner proposes.

`roles-run-as-flume-kinds` touches the same launcher, greetings, briefs and hooks. Neither builds on the other's code; whichever merges second takes the other's words where they meet. It landed on the bolt first, at 9913f249: teams file version 4, each partition naming `flume` for its five main-level roles, `false` while a role stands or the stream its runs run in; a tell, a send or crew's notice to a role that runs as its kind an ask of it; and a role that runs as its kind given no tab, start, greeting or revive by `crew main up`. So this change's deltas carry those words where they change the same requirements, and its teams file is the next version after that change's.

## Decisions

### 1. The crossed path is the only path, and it goes first

Every decision that branches on the per-team setting keeps the branch for a team with it on and loses the other; the setting is read nowhere. This is the first task group, so that everything after it removes code nothing reaches. A test that proved the off side is deleted with it; a test of a staying feature that set its work up through the old path, a landing, a batch, a card, is rewritten to set it up as the crossed path does, never deleted (`tests.4`: coverage is kept at the lowest tier that holds it).

Alternative: remove the machinery piece by piece with the setting still read. Rejected: each piece would need a decision on what a team with the setting off does meanwhile, which is the old path this change removes.

### 2. The teams file holds partitions only, at a new version

`teams.json` keeps `version` and `partitions[]`, each partition with its `flume` naming its five main-level roles as `roles-run-as-flume-kinds` has it; `teams[]` leaves, and the per-team setting `flume` with it. The file moves to version 5, the next after `roles-run-as-flume-kinds`'s 4, and crew reads version 5 alone: a file at version 2, 3 or 4, or any other, is refused naming the machine's configuration (swancloud's `lib/crew-teams.nix`) as the fix, crew having done nothing (`code.5`). A partition's `roles` may override design, planner, main-ops, operator and reviewer; `dispatcher` is refused as a role with no definition, as any unknown role is.

Why a version: no field has a default (`code.5`), and reading a `teams` list in order to ignore it would make its absence a default; a file that still lists teams was written for a crew that runs them. Alternative: read both versions through a transition. Rejected: two readings of one file, when swancloud can carry the file and the pin in one deploy (*What this change rests on*, 4).

### 3. A partition's kits are the repositories its plan and its landings name

Where crew took a partition's kits from its teams (`partition_kits`, `kits_on`), it takes the repositories named by the `Repo` of the partition's Bolt and Unit records, together with the `Repo` of the `bolt.land` entries in its run record, read from the branch (`read.5`). A decision over plain facts (`code.7`): `partition_kits(plan, landings)`.

Why: there is no registry in crew (the user, 2026-10-31), the plan is the partition's record of its work (`state.2`), and every staying read of a kit is about a bolt or unit of the plan, a card about one, or the board's Inception lane, which the landings keep showing for a kit with nothing planned now. A new kit enters a partition with its first bolt. Alternatives: the hosts file's spaces, whose repository lists leave swancloud's configuration once the runner is deployed (record 0052's asks of swancloud); the runner's records, which say what a host keeps and know no partition.

### 4. A kit's work is taken by a runner whose configuration names its repository, and crew reads where it runs from that runner's report

Every launch of a kit's work, a start's, an added unit's, an amendment's, `crew fix`'s, `crew main fix`'s and a take-main fix's, names the kit's repository as the plan names it and no `Host` or `Stream`; a runner whose configuration names the repository takes it, under a lease and while its host's stream has room, in the stream its host's Flume configuration maps the repository to (*What this change rests on*, 3). A retry, drop or priority names the launch it acts on and no host, and the runner that took the launch takes it. A role's work that lands keeps the host and stream its role runs in (`roles-run-as-flume-kinds`). crew's rules refuse a kit's launch naming a host or a stream (`runner.request_refusal`).

A launched piece's stage is read from the runner whose answers hold its launch (`runner.taken`), launching while none does; where two runners hold it, or none crew read holds it and a runner could not be read, it reads unknown, naming them (`read.1`, `read.3`).

Where crew must act on or say where a started bolt's work runs, its landing, its reads of the bolt and the kit (stages, verification, forecast, the bolt's own work since a send), its reading and preview, the made-read of a batch, the sweep after a landing or a drop, the rail's read of landings nothing recorded, its site row, and its ledger's and rail line's host and stream, it reads what the runner reported for the work it took (`runner.where`): the host whose runner took the newest of the bolt's launches taken, and the kit's folder there and the stream as Flume's status of that runner's place of it names them (`repository`, `stream`); while no runner has taken any of the bolt's own work, where the runner that took the kit's newest work taken reported the kit. crew acts in that folder, `origin/<default>` after a fetch as every read of main is now (`plan.18`), and cuts a landing's short-lived worktree under it, `<folder>/places/land-<bolt>`, beside Flume's own places, as `plan.18` and `plan.16` have it. A bolt or kit no runner has reported is named as unread, nothing of it landed, every other read as it stands. A decision over plain facts: `runner.where(reads, launches, what)`, wrapped as `plan.bolt_at`, `kit_at`, `launched_at` (a bolt gone from the plan, whose launches `requests.rec` keeps) and `batch_unit_at` (a batch's unit, by the bolt its entry names). A kit's forge address, for its landing's pull request, is the plan's `Repo` where it names an owner, else its folder's configured origin (`forge`).

This replaces `builder`, `bolt_team`, `kit_team`, a launch's `Host` and `Stream` from a crossed team, `Stages.kit`'s team, `survey`'s per-team kits, `landing_team`, `unit_kit_team`, `at_work`, `batch_team`, the card preview's team and `sites.py`'s bolt rows. Why no lookup: there is no registry of repositories in crew (the user, 2026-10-31), and which host's room a kit's work takes is the runners' to settle, each pulling under a lease while its host's stream has room (settled with the user 2026-11-01); the work's own report is the one fact crew holds of where it ran. Two runners answering one launch is a lease that failed, which crew reads unknown, naming both, never settling by a guess.

What crew does on a kit before any runner has taken the work in hand is done on the partition's main-level host, in the checkout that host keeps of the kit, refused where it keeps none (the user's ruling of 2026-11-01): `crew bolt start`'s `sluice branch create` and its policy and sluice checks, a new unit's or chore's name checked against the kit's main (`name_free`), a bolt never started landed by its close alone, `crew record`'s kit and a proposal's records (`record_kit`, `record_items`), the board's explorations on each kit's main, and the main level's kit folders, its roles' `--add-dir` and the brief's `KIT_CHECKOUTS` (`crew.kits_on`). These are asked from the main level, so nothing is asked of a runner for them. The checkout is the one the host's spaces in the hosts file keep, the first session whose space keeps the kit by its forge address or, for a kit the plan names by its name alone, by that name, as crew finds its own checkout and the blueprints' there (`crew.kit_kept`, `plan.main_kit`); two repositories by a bare name are refused, naming both (`read.1`). The main level's kit folders are the partition's kits (Decision 3) that host keeps, read from the branch as crew's cache holds it at each stop's due check (`plan.12`), and fetched once at a role's start, so a kit entering the partition makes the main level's agents due a restart that reaches it. A kit's first records come before its first bolt, so `crew record` takes any kit the host keeps, not only the partition's kits.

### 5. A partition's hosts are its main level's and its runners'

A partition's hosts are its main level's machine and every host whose runner answers for it, `<label>/runner/<host>` in its state repository, each once: `plan.partition_hosts`, from the branches a command's fetch brought or, for the follower's look, as crew's cache holds them with no fetch (`plan.12`), and `plan.hosts_of`, from the runners a read read beside its plan. They feed the board's hosts and attention, the rail's sweep of card sessions and landings, the follower's readings stamps and `crew sites`.

### 6. What a conductor or a team held goes to the role record 0047 names, as the crossed path has it

Record 0047 move 5: within a partition, a stage speaks to the planner, design or ops, and nothing speaks team to team; ordering within a bolt, batches and amendments are the planner's; a landing is main-level ops's on the user's send. So:

- **A proposal** waits on no conductor's agreement: the user's approval is the one word (`roles.2`); `crew plan agree` and the `Agreed` write go, and the proposal card names no conductor it waits on.
- **Ordering within a bolt**, `unit split|order|after` and their chore forms, is the planner's by proposal; no agent but the user writes them directly (`roles.1`).
- **The bolt's reading and preview** (`land/<bolt>`), which `reading_owner`, `land_session` and `preview_owner` gave the bolt's conductor, are main-level ops's, the owner of the kit's landings card, as the crossed path already has them for a crossed bolt.
- **A question for the user** is asked by the planner, main-level ops or the design agent (`briefs.11`); `ASKERS` drops `conductor`, and `card_refusal`'s team, conductor and dispatcher branches go.
- **A batch's notes** go to the planner, who hands each unit's on as the crossed path does; no conductor runs construct again (`briefs.12`).
- **A landing's conflict with main**, forecast on the landings card or met at the submission, is answered as the crossed path answers it for a crossed bolt: forecast, it is recorded once on the bolt, whose row takes main first until a fix taking main in moves its head, and nothing is started; met, sluice's refusal launches the take-main fix on the bolt. No conductor is told, and no row names a team that takes main in.

### 7. The stage briefs leave with the slots

`construct.md`, `coder.md` and `verify.md` brief the agent crew started in a unit slot (`crew-role <team>-unit-<n> <stage>`). On the crossed path a stage is a place of a Flume kind, prompted by the kind and briefed by the kit's own files, its `CLAUDE.md`, its `openspec/config.yaml` and its `.config/flume.toml`: this construct stage ran so, as Flume's change kind under crew's `openspec` profile, its stop-short `flume needs`. With no slot, crew starts no stage agent and has no stage brief to give, so the three leave, and `briefs.2` and `briefs.18`, which bind them, retire.

### 8. The run record keeps its history

crew writes no `slot.free`, `stage.start`, `stage.end`, `fix.start`, `fix.merge`, `fix.drop`, `bolt.give`, `team.up|close|rebuild|down`, `team.cross`, team-scoped `agent.start|restart|clear|resume`, team greeting, unit `forecast`, `amendment` or `plan.agree` entry, and no `main.up|down` for a dispatcher. The descriptor's fields stay, entries are never rewritten (`record.4`), and `crew trace` reads and prints the old acts as before, `team/` objects among them. A batch's `review.start` and `review.batch` name each unit with its bolt, `<unit>:<bolt>@<commit>`, where one written before named its team in the same place; the reader takes that name as written. `record.5` and `record.6` retire as rules about entries crew writes.

### 9. The plan's records keep their fields on the branch

A Bolt's `Team` and a Proposal's `Agreed` are never written or read again. A state branch's own descriptor keeps allowing them, so `recfix --check` passes on records that still carry one (`plan.1`); a new branch's descriptor (`HEADER`, `PROPOSALS`) drops them, `%unique: Repo Goal Team` becoming `%unique: Repo Goal`. No write strips them: a field nothing reads changes nothing, and a commit of crew's own making that touches every bolt to change nothing is noise in the plan's history (`state.2`).

### 10. A command that leaves is gone, not stubbed

Unlike `crew card wait`, which refused naming its successor for agents still carrying an old brief, no agent that ran these commands is left once the bump lands: crew starts no conductor, team ops, dispatcher or slot agent, and each main-level agent restarts at its next stop on the plugin's change with its new brief (`teams.19`). A removed command falls to crew's unknown-command answer, which prints the usage. Alternative: a refusal per command naming the rail. Rejected: code kept for agents that no longer exist.

### 11. The views follow (`code.8`)

`board.agent_views` gives the planner, the design agent, main-level ops and the operator their views, and no conductor's, team ops's or dispatcher's; `conductor_view` goes, and the crew-version lines `here_read` gave team agents and dispatchers go with them. The planner's band draws each bolt in flight as the ledger a conductor's did, since ordering within a bolt, batches and amendments are the planner's (Decision 6), a place waiting on an answer on its line with its question; the operator's draws each bolt in flight on one line. `crew board --json` lists no `teams` per partition and no `teams` on any object, and the page's team control goes with it. A bolt's ledger shows its work as the crossed path reads it, with no slots, its head line naming its kit's host and stream (Decision 4), which the board's JSON gives the ledger where it gave a crossed team. A bolt's time (`plan.20`) keeps its holders' names, which the bands, the mod and every landing entry already carry: the `team` holder is the bolt's own work as the crossed path reads it, and the age runs from the run record's entry that made the bolt's branch, not from a give. Renaming the holder would change every band and entry for no behaviour, which the user's "nothing new invested" rules out. The cards drop the "a yes frees …" line (`teams.16`) and every conductor's name: a landings row names no conductor and a defect note goes to main-level ops, a held row waits for a fix on the bolt, and a batch card names each unit with its bolt, its notes reaching the planner, who hands them on. The page drops its team docks, its team control and its slot rows; a subscription's dock, which a team's dock opened, lists the main level's sessions on the account and is opened from the fleet page's subscription, whose partition links carry it. The fleet page drops its teams and slots, listing each partition's kits as `plan.partition_kits` names them (Decision 3), which the board's JSON gives each partition. A started bolt's ledger, and its entry in `crew sites`, show no dev server, since crew finds one only in a worktree of its own making and a started bolt's places are Flume's; the runner reporting a place's addresses from Flume's run record (record 0043) is an item of `_open.md` for its interface (the user, 2026-10-31). `plugin/hooks/status.js` draws what the views give and gains no case of its own beyond the views' new shape.

### 12. A hold and an update reach the main-level roles alone

`hold.py` stands down, holds and restarts the main-level roles and nothing of a team's or a dispatcher's; `renew` restarts no conductor fresh. The branch hint goes whole (`teams.20`): `crew-role`'s `SLUICE_BRANCH`, the pane's `sluice_branch` token, `CREW_BRANCH` at a start, `crew.py hint`, `branch_due`, `branch_now`. The stop hook's exclusion of `-unit-<n>` agents goes, since there are none.

### 13. The order of the build

One path first (Decision 1), then the machinery from its leaves in: stage driving and the fix slot; the give, the dispatcher and the conductor's part of the plan; the team's agents, tells and hint; then the reads that went through a team; then the views; then the teams file itself, which everything before stops reading; then the briefs; then the tests' tasks. Each group leaves the suite green, and each command's removal updates the usage header, README and the skill together (`docs.2`), so `t-docs` holds after every group.

### 14. A bolt's work starts by `crew bolt start`, the crossed give with no team

`crew bolt start <bolt>` does what a crossed team's give does, with no team: it checks the kit's policy and has sluice make `bolt/<bolt>` from the kit's main, is refused while the host it makes the branch on is held (`teams.19`) or no runner answers for the partition (`runner.runnerless`), and in one plan write marks the bolt `Path: flume` and appends a launch request for each unit and chore of it in its repository (Decision 4), each with its `After` and the priority `runner.priorities` gives. It makes the branch in the checkout the partition's main-level host keeps of the kit, since no runner has taken any of the bolt's work yet (Decision 4), and is refused where that host keeps none. It starts no agent. Every write that reached a crossed team's launched work reaches a started bolt's: an added unit is launched, an amendment is a retry of construct, a drop drops the place, a reorder sends the priorities that changed. A bolt in flight, wherever the specs and the views say so, is a started one, marked `Path: flume`. A bolt's age (`plan.20`) runs from its start's entry, `bolt.start`, which takes `bolt.give`'s place in the run record.

A proposal may hold `bolt start`, so the planner proposes which bolts run and the user approves (`roles.1`, the planner changing the plan only by proposal); the user runs it directly. No other agent runs it. Why a start at all, when record 0047 move 5 has every open bolt's work launched and Flume's room decide what runs: the plan holds bolts the planner has placed and the user has not chosen to run (the queue, planned bolts), and a launch makes a place at once; the user's words of 2026-10-28, "what I really want to be doing as a user is choosing what work is happening at any given time", make that choice the start, and the rail's order the priority after it. Alternative: launching every bolt's work at its approval. Rejected: it makes every planned bolt's places at once, and turns the order of the plan's bolts, which is the planner's to propose, into the only choice the user has.

### 15. A fix names its bolt, and a fix of main its kit alone

`crew fix <bolt> <name> "<words>"` launches a fix place on the bolt as a crossed team's `crew fix` does, in the kit's repository (Decision 4), and is the planner's, design's or ops's, as the crossed path has it; `--drop` drops its launch, as the crossed form does, and `--merge`, `--wait` and `--bolt` are no options it has (Flume submits and tells, and the bolt is named first). `crew main fix <kit> <name> "<words>"`, with its `--drop` and `--send`, takes no `--team`: it launches in the kit's repository as the partition's kits name it (Decision 4), and is refused where no runner answers for the partition, naming it, so a red main's fix there stays what `state.3` says until one does. The landing read's take-main fix launches in the kit's repository the same way.
